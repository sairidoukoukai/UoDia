## 1. 概要

### 1.1 目的

UoDia は、大阪大学の学内連絡バス（通称「再履バス」）の運行ダイヤを設計・検証・可視化するためのアプリケーションである。**デスクトップ版（Tauri）と Web 版を同一のコードベースから提供する。**

### 1.2 設計方針 — 汎用ダイヤソフトではない

本ソフトウェアは **再履バス専用ツール**である。OuDia のような汎用ダイヤ作成ソフトの UI を参考にしつつ、対象を限定することで得られる以下の前提を**積極的に利用して単純化する**。

| 前提 | 帰結 |
| --- | --- |
| 系統は 1 つで固定 | 系統の切り替え・複数系統の管理が不要。 |
| **区間所要時間は経由方法によらず一定** | 所要時間を区間表に一元管理できる（[§5.2](#52-区間所要時間)）。 |
| 全時刻が 5 分刻み | 入力・ドラッグのスナップ単位が一意。中間時刻に端数が出ない。 |
| 便は「停車パターン + 基準時刻 1 点」で完全に決まる | 便内の時刻矛盾が**構造的に発生しない**。スジの傾きが変わらない。 |
| 回送も停車パターンの一種 | 出入庫・営業所待機のための専用データ構造が不要。 |
| **出区・入区は 0 分折返し** | 回送便に固有の情報が 1 つも無く、営業便の真偽値 2 つから**導出できる**（[§6.1.7](#617-出区入区)）。 |
| 1 日 100 便程度 | 描画・検証の性能要件が緩い。Web Worker や高度な最適化が不要。 |
| 折返し時分の下限は 0 分 | 折返しの検証が時刻の前後関係だけで済む。 |
| 車両数の管理は不要 | 車両エンティティが不要。運用番号の記入と整合性検証で足りる。 |

**自由度を上げないことが本ソフトの品質である。** 汎用性のために抽象化を持ち込むことは、この文脈では誤りとみなす。

ただし例外が 1 つある。**将来の GTFS 出力に向けたデータモデルの命名・構造の準拠**（[§5.9](#59-gtfs-との対応)）は、v1 の実装コストをほとんど増やさずに将来の実装コストを大きく下げるため、採用する。

### 1.3 名称

**UoDia** — *University of Osaka Diagram*。

### 1.4 想定利用者

再履バスのダイヤを設計・記録する少人数。専門的な運行管理知識を前提としてよい。初心者向けの手厚いガイダンスは不要。

## 2. 用語定義

GTFS に対応する概念には GTFS の識別子を用いる（[§5.9](#59-gtfs-との対応)）。

| 用語 | 識別子 | 定義 |
| --- | --- | --- |
| **プロジェクト** | `Project` | 1 つの `.uodia` ファイルに対応する編集単位。 |
| **ネットワーク定義** | `NetworkDef` | 停留所・区間所要時間・停車パターンを定義した固定データ。`route.json` として保持する（[§5.1](#51-ネットワーク定義-routejson)）。 |
| **停留所** | `Stop` | バスの停車地点。千里営業所も停留所の一種として扱う。 |
| **区間** | `Segment` | 隣接する 2 停留所を結ぶ有向の辺。所要時間を持つ（[§5.2](#52-区間所要時間)）。 |
| **方向** | `directionId` | `0` = 吹田方面（ダイヤグラム縦軸を下向き）、`1` = 豊中方面（上向き）。 |
| **停車パターン** | `StopPattern` | 便が経由する停留所の並びと、各停留所での取扱区分。回送もパターンの一種。 |
| **取扱区分** | `Handling` | その停留所で乗客の乗降をどう扱うか（[§5.4](#54-handling取扱区分)）。 |
| **便** | `Trip` | 1 回分の運行。**停車パターンと基準時刻 1 点のみで完全に決まる。** |
| **基準時刻** | `Anchor` | 便の時刻を決める唯一の入力。「どの停留所が何時か」の組。 |
| **ダイヤ** | `Service` | 便の集合。運行日種別ごとに 1 つ持つ。GTFS の `service_id` に対応。 |
| **運用** | `blockId` | 同一車両が 1 日に連続して担当する便のまとまり。**便に記入する運用番号**で表す。GTFS の `block_id` に対応。 |
| **スジ** | *(trip line)* | ダイヤグラム上で 1 つの便を表す折れ線。 |
| **回送** | *(deadhead)* | 営業所と停留所の間の非営業移動。`isDeadhead: true` のパターンを持つ便として表すが、**保存はしない**。営業便の `pullOut` / `pullIn` から導出する（[§6.1.7](#617-出区入区)）。 |

### 2.1 時刻の表現

- 内部表現は **「その運行日の 00:00 からの経過秒数」を表す整数**。
- **24 時を超える時刻を許容する**（例: 25:30 → `91800`）。
- **すべての時刻は 300 秒（5 分）の倍数**である。これは不変条件であり、システム全体で保証する。
- UI の入力単位は分。秒は表示しない。

### 2.2 停車時分の扱い

**便の内部に停車時分は存在しない。** バスは着即発として扱い、1 つの便における各停留所の着時刻と発時刻は同一である。

**停車時分は便と便の間に現れる。** 同一運用の連続する 2 便について、

```
停車時分（折返し時間）= 次便の始発時刻 − 当便の終着時刻
```

として導出される。下限は 0 分であり、これを下回る（負になる）場合のみ検証エラーとする（[§6.6](#66-ダイヤ検証) V-02）。

例: 工学部前に 8:55 着の便と、工学部前を 9:05 発の便が同じ運用番号を持つとき、工学部前での停車時分は 10 分である。この値はどこにも永続化されず、常に導出される。

## 4. ユースケース

### UC-1: 現行ダイヤの入力

設計者は新規プロジェクトを作成する。時刻表エディタの空の列に始発時刻を打つと、その列が便になる。中間停留所の時刻は自動で埋まる。100 便を入力するのに要するのは「時刻 1 つ + 必要ならパターンの変更 + 運用番号」× 100 回のみ。

### UC-2: 増発案の検討

設計者は既存の便を複製し、ダイヤグラム上でスジをドラッグして 15 分後ろにずらす。スジは水平に平行移動し、傾きは変わらない。運用が破綻すれば検証パネルに警告が出る。

### UC-3: 途中停留所を基準にした時刻調整

「箕面学舎を 9:00 発にしたい」という要求に対し、設計者は時刻表エディタの該当セルに `900` と入力する。始発を含む他のすべての停留所の時刻が、この 1 点を基準に再計算される。以前に始発時刻で指定していた基準は破棄される。

### UC-4: 運用の確認

設計者は各便に運用番号を記入する。昼間の閑散時間帯には、入庫回送の便と出庫回送の便を挟むことで営業所待機を表現する。同一運用内で停留所や時刻が繋がっていなければ、検証パネルがエラーを表示する。

### UC-5: 区間所要時間の改定

道路事情の変化により豊中学舎〜箕面学舎の所要時間が変わった。設計者は設定ダイアログの区間所要時間タブで該当区間の値を書き換える。この区間を通るすべての便の時刻が、各便のアンカーを基準に再計算される。

## 5. データモデル

### 5.1 ネットワーク定義 (`route.json`)

停留所・区間所要時間・停車パターンを定義する固定データ。プロジェクトファイルには含めない。

> **命名について**: 型名を `RouteDef` ではなく `NetworkDef` としたのは、GTFS の `route`（＝路線）と衝突するためである。ファイル名は `route.json` のままとする。

```typescript
interface NetworkDef {
  version: number;             // 本ファイルの版数。プロジェクトとの整合性検査に使う
  name: string;
  timeGrain: number;           // 時刻の刻み（秒）。300 固定。

  stops: Stop[];
  segments: Segment[];         // 区間所要時間の表
  patterns: StopPattern[];
}
```

### 5.2 区間所要時間

**所要時間は停留所でも停車パターンでもなく、「隣接する 2 停留所を結ぶ有向の区間」が持つ。**

```typescript
interface Segment {
  fromStopId: string;
  toStopId: string;
  runMinutes: number;          // 5 の倍数
}
```

**なぜ区間が持つのか**

区間所要時間は経由方法によらず一定である。したがって:

- **停留所が持つ設計は誤り。** 「豊中学舎から次まで N 分」と書けない。次が箕面学舎か（三点間）コンベンションセンター前か（直行）で値が違う。
- **停車パターンが持つ設計も誤り。** `箕面学舎 → コンベンションセンター前` は `S2` と `S3` の両方に現れる。パターンごとに持つと同じ値が重複し、片方だけ改定してしまう事故が起きる。
- **区間が持つのが正しい。** 各区間の所要時間はネットワーク上で一意に定まり、重複がない。

なお、`豊中学舎 → 箕面学舎` と `箕面学舎 → 豊中学舎` は**別の区間**として定義する（有向）。往復で所要時間が異なる可能性を排除しないため。

**累積所要時間の導出**

停車パターン内での始発停留所からの累積所要時間は、パターンの停留所列に沿って区間表を引きながら累積して求める。

```
offsetFromOrigin(pattern, stopId) = Σ segment(pattern[i], pattern[i+1]).runMinutes
                                    （先頭から stopId の直前まで）
```

この値はネットワーク定義の読込時に一度だけ計算し、キャッシュする。

### 5.3 Stop（停留所）

```typescript
interface Stop {
  stopId: string;              // 例: "1_0"        → GTFS stop_id
  stopName: string;            // 例: "豊中学舎"    → GTFS stop_name
  shortName: string;           // 例: "豊中"（画面に出す名前。UoDia 独自）
  area: string;                // 例: "豊中地区"
  /** ダイヤグラム縦軸の座標（任意単位）。表示専用で、便の時刻を拘束しない。 */
  axisPosition: number;
  gridStyle: "bold" | "normal" | "dashed";
  /** true の停留所は時刻表・ダイヤグラムに表示しない。内部データとしてのみ保持する。 */
  hiddenInEditor: boolean;
  /** true の停留所は営業所。GTFS 出力から除外される。 */
  isDepot: boolean;
}
```

**画面に出すのは `shortName` である**（v4.26）。ダイヤグラムの縦軸、時刻表の行見出し、検証の指摘、ステータスバーのカーソル位置——利用者が停留所を指して読む場所はすべて略称で揃える。`stopName` は GTFS `stop_name` として持ち続けるが、画面には出さない。

正式名を画面に出すと、**一番長い名前がそのまま欄の幅になる。** 「コンベンションセンター前」に合わせると縦軸の欄だけで 144px を占め、そのぶんダイヤグラムの描ける幅が狭くなる（[§6.2.2](#622-描画要素)）。

### 5.4 Handling（取扱区分）

**その便がその停留所で、乗客の乗り降りをどう扱うかを表す。**

```typescript
type Handling =
  | "stop"        // 乗降可
  | "boardOnly"   // 乗車専用（乗れるが降りられない）
  | "alightOnly"  // 降車専用（降りられるが乗れない）
```

| 区分 | GTFS `pickup_type` | GTFS `drop_off_type` | 主な用途 |
| --- | --- | --- | --- |
| `stop` | 0（通常） | 0（通常） | 通常の停留所 |
| `boardOnly` | 0 | 1（扱わない） | 始発停留所 |
| `alightOnly` | 1（扱わない） | 0 | 微生物研究所前、終着停留所 |

**時刻表には出さない**（v4.13、[§6.1.1](#611-レイアウト)）。

**このフィールドの存在理由**

主目的は将来の GTFS 出力である。GTFS の `stop_times.txt` は `pickup_type` / `drop_off_type` を必須の概念として持つため、これを表現できないデータモデルからは正しい GTFS を生成できない。

**v1 では画面に現れない。** 値は `route.json` の停車パターンに固定値として書かれ、エディタ UI から編集することはない。実質的には「微生物研究所前は降車専用である」という事実を記録するためのフィールドと考えてよい。

パターンに含まれない停留所は、その便が経由しないことを意味する（時刻表では `−` を表示）。「通過」という区分は設けない。

**回送パターンにおける `handling` は意味を持たない。** 回送は営業運行ではなく乗降が発生しないため、本来はいずれの区分にも当てはまらない。しかし回送便は GTFS 出力から除外される（[§5.9](#59-gtfs-との対応)）ため、この値が `pickup_type` / `drop_off_type` として出力されることはない。`route.json` では営業パターンと同じ規則（始発 `boardOnly`・終着 `alightOnly`）を機械的に適用し、値を参照しないことで一貫性を保つ。専用の区分を設けないのは、営業便の処理に「回送のときは無視する」という分岐を持ち込まないためである。

### 5.5 StopPattern（停車パターン）

```typescript
interface StopPattern {
  patternId: string;           // 例: "S1"
  patternName: string;         // 例: "直行吹田"        → GTFS trip_headsign
  routeName: string;           // 例: "豊中吹田線"       → GTFS route_long_name の生成元
  directionId: 0 | 1;          // 0 = 吹田方面 / 1 = 豊中方面  → GTFS direction_id
  color: string;               // #RRGGBB。ダイヤグラムのスジ色。
  isDefault: boolean;          // 便の新規作成時に選ばれる（方向ごとに 1 つ）
  /** true なら回送。営業運行ではない。GTFS 出力から除外される。 */
  isDeadhead: boolean;
  /** 各駅（local）か通過（express）か。**回送は持たない**（v4.29、R-12）。 */
  serviceType?: "local" | "express";
  stopSequence: PatternStop[]; // 通過順。先頭が始発、末尾が終着。
}

interface PatternStop {
  stopId: string;
  handling: Handling;
}
```

**設計上の要点**

- **パターンは所要時間を持たない。** 停留所の並びのみを持ち、所要時間は区間表から引く（[§5.2](#52-区間所要時間)）。
- **路線を独立したエンティティにしない。** 系統は 1 つで固定であり、路線名（豊中吹田線など）はパターンに付随するラベルに過ぎない。GTFS の `routes.txt` は出力時に `routeName` でグルーピングして生成する。
- **回送を専用のデータ構造ではなくパターンとして扱う。** 出庫・入庫は「千里営業所を始発または終着とする便」であり、営業便と同じ `Trip` で表現できる。これにより出入庫ブロックのような専用構造が不要になる。
- 直行便（`S1`）は箕面学舎を経由しないため、その停留所列に箕面学舎が現れない。**便ごとに経由地が異なる事実は、方向別のフラグでは表現できず、パターンでしか表現できない。**
- **各駅か通過かはデータが持つ**（v4.29）。停留所の並びから推し量ると、実装が特定の停留所 ID（箕面学舎）を名指しすることになる。各駅・通過の別は路線側の事実であり、`route.json` に書く。回送は持たない——客を乗せない便に「各駅か通過か」は無い。

#### 5.5.1 微生物研究所前の扱い

微生物研究所前 (`6_0`) は `hiddenInEditor: true` とし、**時刻表・ダイヤグラムのいずれにも表示しない**。ダイヤ作成上は存在しないものとして扱う。

ただし内部データとしては保持する。コンベンションセンター前を発車して工学部前へ向かうパターンにおいて、停留所列を以下のように構成する。

```
コンベンションセンター前 → 微生物研究所前 → 工学部前
```

区間表で `微生物研究所前 → 工学部前` を **0 分**と定義することにより、微生物研究所前の時刻は工学部前の到着時刻と常に一致する。これは将来の GTFS 出力において、実際の運行経路上の降車専用停留所を `stop_times.txt` に含めるために必要となる。

#### 5.5.2 ネットワーク定義の検証

読込時に以下を検証し、違反があれば起動時にエラーを表示する。

| ID | 内容 |
| --- | --- |
| R-01 | すべての `runMinutes` が 5 の倍数であること（5 分刻みの不変条件を保つため） |
| R-02 | すべての `stopSequence[].stopId` が `stops` に実在すること |
| R-03 | **すべてのパターンの隣接する停留所対が `segments` に存在すること** |
| R-04 | `segments` に同じ `(fromStopId, toStopId)` の重複がないこと |
| R-05 | 各 `directionId` に `isDefault: true` かつ `isDeadhead: false` のパターンがちょうど 1 つ存在すること |
| R-06 | すべてのパターンの `stopSequence` が 2 要素以上であること |
| R-07 | `isDepot: true` の停留所を含むパターンは `isDeadhead: true` であること（およびその逆） |
| R-08 | `stops` に `stopId` の重複がないこと |
| R-09 | `patterns` に `patternId` の重複がないこと |
| R-10 | 1 つのパターンの `stopSequence` に同じ `stopId` が 2 回以上現れないこと |
| R-11 | すべての営業パターンについて、その**始発停留所を終着とする回送パターン**と、**終着停留所を始発とする回送パターン**が存在すること |
| R-12 | 営業パターンが `serviceType` を持ち、回送パターンが持たないこと（v4.29） |

> **R-11 は回送の導出が必ず成功することを定義の側で保証する**（v4.6）。回送便は保存されず、出区・入区のたびに営業便の始発・終着停留所から引かれる（[§6.1.7](#617-出区入区)）。引けないパターンがあると、利用者が押した瞬間に「作れません」と言うほかなくなる。それは編集中に起こる不具合ではなく `route.json` の不備であり、起動時に判る場所へ移す。
>
> R-08 と R-09 は実装時（T-06）に追加した規則である。ID が重複すると検索が先勝ちになり、参照の意味が静かに壊れる。スキーマ検証（[§7.4](#74-検証)）は配列の要素数を見るだけで重複を検出できないため、ここで検査する必要がある。
>
> R-10 は実装時（T-07）に追加した規則であり、**アンカー方式の前提そのもの**である。`Trip.anchor` は停留所を `stopId` だけで指すため（[§5.6](#56-trip便)）、同じ停留所が 1 つのパターンに 2 回現れると、アンカーがどちらの通過を指すのかが決まらず、時刻の導出が定義できない。始発と終着が同じ停留所になる循環経路もこの規則で禁じられる。再履バスの経路にそのような運行は存在しないため、実データに影響はない。

### 5.6 Trip（便）

```typescript
interface Trip {
  tripId: string;              // UUID v4              → GTFS trip_id
  patternId: string;           // 方向・行先・経由地を兼ねる
  anchor: Anchor | null;       // 時刻を決める唯一の入力。null は時刻が未入力。
  blockId: string;             // 運用番号。空文字は未割当。 → GTFS block_id
  pullOut: boolean;            // この便の前に車庫から出る（§6.1.7）
  pullIn: boolean;             // この便の後に車庫へ入る（§6.1.7）
  note?: string;
  // 便番号は持たない。始発時刻から導出する（§6.1.6）。
  // 回送便は持たない。pullOut / pullIn から導出する（§6.1.7）。
}

interface Anchor {
  stopId: string;              // パターンに含まれる停留所であること
  time: number;                // 秒。300 の倍数。
}
```

**出区・入区は便の属性である**（v4.6）

`pullOut` / `pullIn` は「この便の前に車庫から出るか」「この便の後に車庫へ入るか」だけを持つ。**回送便そのものは保存しない。** 0 分折返しの制約下では回送便に固有の情報が 1 つも無く（[§6.1.7](#617-出区入区)）、パターンも時刻も運用番号もこの便から決まるためである。

回送便を独立した `Trip` として保存すると、**営業便を動かしたときに置いていかれる。** 時刻をずらせば継ぎ目が離れ、パターンを変えれば始発停留所が食い違い、便を消せば行き先を失った回送だけが残る。どれも「導出できるものを状態として持った」ことの帰結であり、便番号（[§6.1.6](#616-便番号の採番)）・運用の順序（[§5.8](#58-運用の導出)）・運用の色と同じ扱いに揃える。

回送便が要る場面（運用の導出・ダイヤグラム描画・検証）では、その時点で展開する。展開した回送便も `Trip` であり、`pullOut` / `pullIn` は `false`、`blockId` は展開元の便と同じ、アンカーは**営業便と接する停留所**に置く。

**アンカー未設定（`null`）**

便の追加は「既定パターンの空便を挿入する」操作であり（[§6.1.4](#614-便の操作)）、その時点では時刻が決まっていない。これを表現できないと、時刻を入れるまで便を作れないか、あるいは仮の時刻を入れて「本当に 0:00 発なのか、まだ入力していないのか」を区別できなくなる。

`anchor` が `null` の便は、経路（`patternId`）は決まっているが時刻が決まっていない。全停留所の時刻が `null` となり、時刻表・ダイヤグラムでは空欄として扱われる。時刻を 1 つ設定すれば通常の便になる。パターンの変更は未設定のまま行える — 引き継ぐ時刻が無いのだから、仮の時刻を作ってはならない。

**時刻の導出**

```
timeAt(trip, stopId) = trip.anchor.time
                     + offsetFromOrigin(pattern, stopId)
                     - offsetFromOrigin(pattern, trip.anchor.stopId)
```

すべての停留所時刻はこの純関数で計算され、**永続化されない**。

**アンカーの更新規則**（[UC-3](#uc-3-途中停留所を基準にした時刻調整)）

利用者が停留所 *S* の時刻を *T* に設定したとき、`trip.anchor = { stopId: S, time: T }` とし、**前のアンカーは破棄する**。マージも、複数アンカーの保持も行わない。これにより:

- 便内で時刻が矛盾することが**原理的に起こり得ない**。
- スジの傾きが変わり得ないため、ダイヤグラム編集は水平スライドのみとなる。
- 便の全時刻がアンカー 1 点から決まるため、Undo/Redo の粒度が自明になる。

**なぜ始発時刻を直接持たないのか**

`anchor` を始発時刻に正規化すると、区間所要時間を改定した際に「利用者が意図して固定した停留所の時刻」が動いてしまう。アンカーを保持すれば、その 1 点は改定後も動かない（[UC-5](#uc-5-区間所要時間の改定)）。

### 5.7 Service（ダイヤ）

```typescript
interface Service {
  serviceId: string;           // → GTFS service_id
  serviceName: string;         // 例: "授業期間平日ダイヤ"
  trips: Trip[];               // 両方向の営業便。回送便は含まない（導出値）
}
```

### 5.8 運用の導出

営業便に回送便を展開したうえで（[§6.1.7](#617-出区入区)）、同一 `blockId` を持つ便を始発時刻の昇順に並べたものが、その車両の 1 日の行路である。以下の値が導出される（永続化しない）。

| 値 | 算出方法 |
| --- | --- |
| 折返し時分 | 次便の始発時刻 − 当便の終着時刻（[§2.2](#22-停車時分の扱い)） |
| 出庫時刻 | 先頭便（回送便）の始発時刻 |
| 入庫時刻 | 末尾便（回送便）の終着時刻 |
| 営業所待機時間 | 入庫回送便の終着時刻から次の出庫回送便の始発時刻までの間隔 |

運用番号ごとの表示色は、運用番号の一覧上の位置から自動的に割り当てる。

**選んだ色だけをプロジェクトに保存する**（v4.40、#148）

利用者が色を選んだ運用は、その色で描く（`view.blockColors`）。選んでいない運用は、これまでどおり一覧上の位置から決まる。

**選んだものだけを覚える。** 全部を持つと、運用番号を打ち替えるたびに色の管理が要る。選んだものだけなら、**運用を足しても選んだ色は動かない**——自動割り当ての代償（番号の増減で色がずれる）を、必要なところだけ打ち消せる。

**設定ではなくプロジェクトに置く。** 運用番号はその文書のものであり、`A` という運用はダイヤが違えば違う車の動きを指す。設定に持つと、別のファイルを開いたときに無関係な `A` の色を引き継ぐ。色を決めるのは「この日のダイヤを説明するため」であり、渡した相手の画面でも同じ色で見えてほしい。**停車パターンの色（[§6.5.3](#653-表示タブ)）を設定に置いたのとは逆の判断であり、理由も逆である**——パターンは路線の事実、運用番号はその文書の中だけの名前である。

### 5.9 GTFS との対応

将来の GTFS 出力（v2 予定）に向け、データモデルの命名と構造を GTFS に準拠させる。**v1 では出力処理を実装しないが、実装時に構造変換を要さないことを設計目標とする。**

| UoDia | GTFS ファイル | GTFS フィールド |
| --- | --- | --- |
| `Stop.stopId` / `stopName` | `stops.txt` | `stop_id` / `stop_name` |
| `StopPattern.routeName` | `routes.txt` | `route_long_name`（グルーピングして `route_id` を生成） |
| `Trip.tripId` | `trips.txt` | `trip_id` |
| `Service.serviceId` | `trips.txt` | `service_id` |
| `StopPattern.directionId` | `trips.txt` | `direction_id` |
| `StopPattern.patternName` | `trips.txt` | `trip_headsign` |
| 便番号（導出値。[§6.1.6](#616-便番号の採番)） | `trips.txt` | `trip_short_name` |
| **`Trip.blockId`（運用番号）** | `trips.txt` | **`block_id`** |
| 導出される停留所時刻 | `stop_times.txt` | `arrival_time` / `departure_time` |
| `PatternStop` の順序 | `stop_times.txt` | `stop_sequence` |
| `Handling` | `stop_times.txt` | `pickup_type` / `drop_off_type` |
| `Service` | `calendar.txt` | `service_id` ほか（v2 の運行日カレンダーで補完） |

**出力時の除外規則**

- 回送便は出力しない（回送は公共サービスではない）。**回送便は保存されていない**ため（[§6.1.7](#617-出区入区)）、展開せずに書き出せば足りる。
- `Stop.isDepot: true` の停留所は `stops.txt` に出力しない。
- `Stop.hiddenInEditor: true` の停留所は**出力する**（微生物研究所前は実際の運行経路上の停留所であるため）。

**v1 で不足するもの**（v2 の GTFS 出力実装時に追加）

`agency.txt` の全項目、`stops.txt` の `stop_lat` / `stop_lon`、`calendar.txt` の運行日情報。前者 2 つは `route.json` に静的データとして追加すればよく、モデル変更を伴わない。

### 5.10 Project（全体構造）

```
Project
├── meta            : Meta            形式・アプリ版数、依存する route.json の version
├── document        : DocumentInfo    名称・作成者・コメント
├── services        : Service[]
│   └── trips       : Trip[]
└── view            : ViewSettings
```

停留所・区間・パターンの定義は**含まない**（`route.json` から読む）。`meta.routeVersion` が現在の `route.json` と一致しない場合、開く際に警告を表示する。

すべてのエンティティは文字列 ID で参照する。配列インデックスによる参照は行わない。

## 6. 機能仕様

### 6.1 時刻表エディタ

#### 6.1.1 レイアウト

行 = 停留所、列 = 便のグリッド。方向ごとにタブで切り替える（**最大化している間は 2 方向を並べる**。v4.43）。

吹田方面のタブ（上から下へ時刻が進む）。運用 A は昼に一度車庫へ帰っている:

```
 便番号                 │  E1   │  E2   │  E3   │       │       │  ← 列見出し
────────────────────────┼───────┼───────┼───────┼───────┼───────┤
 パターン               │  S1   │  S3   │  S1   │       │       │
 運用                   │  A    │  B    │  A    │       │       │
────────────────────────┼───────┼───────┼───────┼───────┼───────┤
 前運用                 │ 7:40  │  W2   │ 13:40 │       │       │  ← 出区なら車庫発時刻、でなければ前便
 豊中学舎               │  8:00 │  8:30 │ 14:00 │       │       │
 箕面学舎               │   −   │  8:50 │   −   │       │       │
 コンベンションセンター前│  8:25 │  9:05 │ 14:25 │       │       │
 工学部前               │  8:30 │  9:10 │ 14:30 │       │       │
 後運用                 │ 8:50  │  W5   │  W12  │       │       │
                                                └───────┴───────┘
                                                   便でない空の列
```

豊中方面のタブでは、停留所の並びが上下逆になる（工学部前が上）。前運用は常に上端、後運用は常に下端にある。

**選んでいる方向をはっきり出す**（v4.37、#136）

選んでいるタブは、選んでいない側より弱く見せない。**色だけに頼らず**、太字と地色も併せて変える（[§9.4](#94-アクセシビリティ)）。

**最大化している間は 2 方向を同時に出す**（v4.43、#145）

時刻表を最大化しているあいだ（[§6.4](#64-画面レイアウト)）は、吹田方面と豊中方面を**上下に並べて同時に出す**。運用は方向をまたぐ（豊中方面で着いた便が折り返して吹田方面へ出る）ため、繋がりを追うのに切り替えを繰り返すことになるからである。

- **上が吹田方面（豊中発）である。** ダイヤグラムの縦軸は豊中が上であり（[§6.2.1](#621-座標系)）、絵と表の上下が揃う
- **上下の配分を決める仕掛けは置かない。** 行は停留所、列は便であり、**便が何本あっても表の高さは変わらない**。2 枚をそのまま積めば、それぞれ自然な高さに収まる
- **どちらの表でも時刻を打てる。** 打った先の方向は、選んでいる方向とは限らない
- 触れば「触っている方向」がその表へ移る

**2 枚あるあいだ、方向タブは表を切り替えていない。** 示すのは**どちらを触っているか**である。方向を 1 つ選んでいる状態そのものは無くせない——**ダイヤグラムの作図がどちらの便を作るかを決めている**（[§6.3.3](#633-スジの作成)）。

最大化を解けば 1 枚に戻り、出るのは触っていた側である。最大化は保存しない画面の姿であり（[§6.4](#64-画面レイアウト)）、2 枚並んでいることも保存しない。

**2 枚あるあいだ、選択に追随して方向を切り替えない**（[§6.3.1](#631-選択の連動)）。切り替える先が既に画面にあり、選ばれた便の列はその表が自分で寄せる。

**方向タブの行に、表の外の操作をまとめる**（v4.38）

並べ替えと、直前の操作の知らせも同じ行に載せる。**行を 1 本増やすたびに、表に使える高さがそのぶん減る。** 時刻表は縦に詰まっているほど多くの停留所が一度に見える。別のダイヤが無いあいだ、複製の行は出さない——押せない操作のために高さを使わない。

**升目の幅は決めた字数で固定する**（v4.41、#137・#146）

幅を中身に任せると、**時刻の無い升目だけが左右の余白ぶんまで縮み、狙って押せなくなる**。入っていても空でも同じ幅にする。

決めるのは**字数**（5.5 文字ぶん）である。表に並ぶのは時刻であり、決めたいのは「時刻が何文字ぶん入るか」だからである。最長の時刻（`47:55`）は 5 文字であり、それに少し余裕を持たせている。**px では決めない**——字の幅は環境で変わり、px を決め打ちにすると、ある環境でだけ `25:30` がはみ出す。

**決めた字数は、字の入る場所である。** 左右の余白はその外側に付く。

**列の幅を決めるのは時刻である。** 見出しの部品（運用番号の欄・パターンの選択欄）が、時刻より広い場所を要求してはならない。

**表示領域は空の列で埋める**（v4.7）

便が 3 本しかなくても、表計算ソフトのように**表示領域いっぱいまで列を並べる**。右へスクロールすれば空の列が続く。

**これにより「便を追加する」という操作が要らなくなる。** 表計算ソフトに「行を追加」ボタンが無いのと同じ理由である。空の列に時刻を打てば、その時点でそれが便になる（[§6.1.2](#612-時刻入力)）。操作の名前を覚える必要も、どのボタンがどの列に効くのかを考える必要も無い。

空の列は便ではない。したがって:

- 便番号・パターン・運用・前運用・後運用の欄はすべて空欄であり、**押しても何も起きない**
- 停留所の行はすべて空欄で、**どの行にも打てる**。`−`（経由しない）は出さない。パターンが決まっていない以上、経由するともしないとも言えないためである
- 選択できない。列見出しを押しても選択は変わらない

**左の列は行の名前を並べる。** 便番号・パターン・運用・前運用・停留所名（**略称**。v4.26）・後運用が縦に並ぶ。停留所名だけの列ではないため、左上に「停留所」とは書かない（v4.14）。停留所名の升目そのものが行見出しであり、この列に列見出しは要らない。

**見出しは 3 行。列を指す名前は便番号だけとする。**

「1 便」「2 便」のような**列の位置を示す見出しは置かない**。それは便番号でも運用番号でもなく、並べ替えれば変わり、ダイヤグラムとも共有されない。同じ便が画面によって違う名前で呼ばれると、口頭でも文書でも指せなくなる。便番号（[§6.1.6](#616-便番号の採番)）が列見出しを兼ね、ここを選ぶことが便を選ぶことである。

**行先の行は置かない。** 行先は停車パターンと 1 対 1 であり、パターン欄と同じことを 2 行使って言っている。パターン欄の補助表示（ツールチップ）として残す。

- **列は営業便だけ。回送便は列にしない**（[§6.1.7](#617-出区入区)）。回送は前運用・後運用の行に時刻として現れる。
- 表示する停留所は、その方向の**営業パターン**に含まれる停留所の和集合。ただし `hiddenInEditor: true` の停留所（微生物研究所前）は除く。**千里営業所の行は無い**（回送が列でなくなったため、営業便の列では常に空欄になる）。
- **行の並びは、その方向の進行方向に従う。** 吹田方面は `axisPosition` の昇順（豊中学舎が上）、豊中方面は降順（工学部前が上）。どちらのタブでも、時刻は上から下へ進む。表を縦に読む動きと、便が走る向きを一致させるためである。
  - **ダイヤグラムの縦軸は反転しない。** 両方向を 1 枚に重ねて描くため、向きを決められない（[§6.2.1](#621-座標系)）。時刻表とダイヤグラムで停留所の上下が一致しない場合があるが、両者の選択は停留所ではなく便どうしで結ぶため（[§6.3](#63-ダイヤグラム上での編集)）支障はない。
- **パターンに含まれない停留所のセルは `−` を表示し、編集不可。** 上例の `E1`（直行）は箕面学舎が `−` であり、`E2`（箕面経由）と区別できる。**便ごとに経由地が異なる事実は、この表示で判別できる。**
- **取扱区分の記号（△・▽）は出さない**（v4.13）。表に出ている範囲では、記号は位置から決まる——始発が `boardOnly`、終着が `alightOnly` であり、例外は `hiddenInEditor: true` の微生物研究所前だけである。**列を見れば分かることを升目ごとに繰り返すと、時刻の桁がずれて読みにくい。** ダイヤは数字を縦に読むものであり、揃っていることに価値がある。区分そのものはデータに残る（[§5.4](#54-handling取扱区分)。GTFS 出力で要る）。
- **アンカーとなっているセルは背景色で明示する。** どの時刻を基準に他が計算されているかが一目で分かること。
- 着発を分けて表示しない（[§2.2](#22-停車時分の扱い)）。
- **前運用・後運用の行は、同じ運用の直前・直後にあるものを映す**（[§6.1.7](#617-出区入区)）。

#### 6.1.2 時刻入力

セルへの入力は、その便のアンカーを当該停留所に移すことを意味する（[§5.6](#56-trip便)）。

| 入力 | 解釈 |
| --- | --- |
| `830` | 8:30 |
| `8:30` | 8:30 |
| `2530` | 25:30（翌 1:30） |
| `45` | 分のみ。時は同じ行の直前の便から補完し、その値以下なら +1 時間する。 |

- **入力値は 5 分単位に四捨五入する。** `8:32` の入力は `8:30` になる。丸めが発生した場合はセルを一瞬ハイライトして知らせる。
- <kbd>Enter</kbd> で下のセル、<kbd>Tab</kbd> で右のセルへ移動。
- 矢印キーでセル移動、直接タイプで上書き入力を開始（表計算ソフトと同じ挙動）。
- 入力を確定すると、**同じ列の他のすべてのセルが即座に再計算される**。

**空の列に打つと便になる**（v4.7）

空の列（[§6.1.1](#611-レイアウト)）のセルに時刻を打つと、その時点で便ができる。

| 決まるもの | 決まり方 |
| --- | --- |
| 停車パターン | **打った行の停留所を経由する**営業パターンのうち、その方向の既定パターン。既定がその停留所を経由しないときは、定義順で最初に経由するもの |
| アンカー | 打った停留所に、打った時刻で置く |
| 運用番号 | [§6.1.5](#615-運用番号の自動採番) が決める（継げる運用の番号、無ければ新しい運用番号） |
| `pullOut` / `pullIn` | ともに `false` |
| 列の位置 | **便の右端**。飛び離れた空の列に打っても、間が空くことはない |

パターンを打った行から決めるのは、**経由しない停留所に時刻を入れさせないため**である。吹田方面の既定は S1（直行）だが、箕面学舎の行に打った利用者が求めているのは箕面学舎を通る便である。打ったあとにパターンを押して変えられる（[§6.1.4](#614-便の操作)）。

**選択中の便がまとめて動く**（v4.7）

複数の便を選んだ状態で、そのうち 1 つのセルに時刻を打つと、**選択中のすべての便が同じ差分だけ動く**。打った便は打った時刻になる。

これが一括シフトの置き換えである。**ずらす分を数えなくてよい。** 30 分遅らせたい便が 8:00 発なら、`830` と打つ。

- 選択に含まれない便は動かない
- 打った便が選択に含まれていないときは、その便だけが動く（選択は無視する）
- **1 便でも 0:00〜47:55 を外れるなら、何も動かさない。** 一部だけ動いた状態は、利用者が求めたものではない

**時刻を消す**（v4.7）

セルで <kbd>Delete</kbd> / <kbd>Backspace</kbd> を押すと、**その便の時刻が消える**（アンカー未設定。[§5.6](#56-trip便)）。便は残り、列も残る。時刻は便に 1 つしかないため、1 つのセルを消すことは列全体を消すことである。

便ごと消すには列見出しを選んで <kbd>Delete</kbd> を押す（[§6.1.4](#614-便の操作)）。**消す対象は焦点のある場所で決まる** — セルなら時刻、列見出しなら便。

#### 6.1.3 運用番号欄

便ごとに運用番号（`blockId`）を記入する行を、時刻表の上部（便番号の下）に設ける。

- 自由記入のテキスト。書式は制約しない。
- 空欄は未割当を意味し、検証で情報レベルの指摘となる（V-07）。
- 同じ運用番号の便は、時刻表・ダイヤグラムの双方で同系色にハイライトできる（[§6.2.4](#624-表示フィルタ着色)）。
- 運用番号のセルにフォーカスすると、同じ運用番号を持つ他の便の列が強調表示される。

#### 6.1.4 便の操作

**便の操作はすべてセルの上で行う**（v4.7）。「便を追加」「削除」「一括シフト」「パターン変更」といった**名前の付いた操作は持たない**。

| したいこと | 操作 |
| --- | --- |
| 便を作る | 空の列のセルに時刻を打つ（[§6.1.2](#612-時刻入力)） |
| 便を消す | 列見出し（便番号）を選んで <kbd>Delete</kbd> |
| 時刻を変える | セルに打つ。アンカーがその停留所へ移る（[§5.6](#56-trip便)） |
| 時刻を消す | セルで <kbd>Delete</kbd>。アンカー未設定に戻る |
| まとめてずらす | 複数の列を選び、そのうち 1 つのセルに時刻を打つ |
| パターンを変える | パターン欄を押す（一覧から選ぶ）か、パターン欄に直接打つ |
| 運用番号を変える | 運用欄に打つ（[§6.1.3](#613-運用番号欄)） |
| 出区・入区を付ける | 前運用・後運用の欄を押す（[§6.1.7](#617-出区入区)） |
| 便を複製する | 列をコピーして貼り付ける（<kbd>Ctrl</kbd>+<kbd>C</kbd> / <kbd>V</kbd>） |

**パターン欄**

- **押すと一覧が出る。** 出るのはその方向の営業パターンだけである（回送は出さない。[§6.1.7](#617-出区入区)）。出すのは `S1` `T1` のような**記号だけ**とする。行先を併記すると列が広がり、時刻の列が押し出される。行先は升目のツールチップで読める（[§6.1.1](#611-レイアウト)）
- **キーを打てばその文字で選べる。** `S3` と打てば S3 が選ばれる。**存在しないパターンは選べない**（打ち込めない）
- **アンカー停留所が新しいパターンに含まれない場合**は、新パターンの始発停留所を新しいアンカーとし、元の始発時刻を引き継ぐ
- 空の列のパターン欄は押せない。便は時刻を打つことで生まれる
- **選択は要らない。** 触っている列が対象である

> **押すたびに順送りする形は採らない。** 一覧と同じ「押す」という動作を取り合うためである。設定で選べるようにもしない。設定を置くことは「どちらでもよい」と言うに等しく、後から一方に決められなくなる。
>
> v4.7 では「キーを打てば直接入力になり、存在しないパターン ID は色で示す」と定めたが、**実装時（T-52）に改めた**。一覧から選ぶ形にすれば、受け付けられない入力そのものが起こらない。打ち込めるようにすることは、不正な状態を作れるようにすることでもある（[§1.2](#12-設計方針--汎用ダイヤソフトではない)）。キーボードだけで完結する点は変わらない。

**コピー・切り取り・貼り付け**（T-53）

- 写るのは**便そのもの**である。パターン・時刻・運用番号・出区/入区のすべてを引き継ぐ
- 貼り付けは**末尾に足す**。便の並びは利用者が決めたものであり、貼り付け先を推測するとその意図を壊す。時刻もずらさない——ずらしたければ、貼ったあとに選んで打てばよい（[§6.1.2](#612-時刻入力)）
- **便 ID は振り直す。** 同じ ID の便が 2 つあると、GTFS へ書き出せないだけでなく、選択も検証の指し先も意味を失う
- 切り取りは「写してから消す」である。**履歴に載るのは削除だけ**であり、取り消しても写したものは消えない。貼り直せる
- 写したものはファイルにも履歴にも入らない。**別のダイヤへ切り替えて貼れば、そちらへ増える**
- 記入欄（時刻・運用番号・パターン）に焦点があるあいだは、そこでの<kbd>Ctrl</kbd>+<kbd>C</kbd> は**文字のコピー**である。表の操作として横取りしない

> **「N 分ずらして複製」という 1 つの操作は持たない。** 複製とシフトの 2 つに分ける（T-52 の一括反映）。1 つにまとめると、ずらす分を入れる欄が要り、そこに何が入っているかを覚えていなければ結果を予想できない。

**メニューに残る操作**（[§8.1](#81-主要キーボードショートカット)・T-37）

セルの上に自然な置き場所が無いものだけを、メニューに置く。

| 操作 | 内容 |
| --- | --- |
| 並べ替え | 便を始発時刻順に整列する。列の並びは利用者が決めるものであり、自動では行わない |
| ダイヤ間コピー | あるダイヤの便を別のダイヤへ複製する。写す先が今の画面に無いため、セルでは表せない |

> **なぜ操作列を廃止するのか。** 操作列のボタンは「今どの列が選ばれているか」を利用者に覚えさせる。押した結果がどの列に出るのかは、押してみるまで分からない。セルの上で操作すれば、**触っている場所が対象そのもの**であり、覚えることが無くなる。一括シフトの「±N 分」も同様で、ずらす分を数えるかわりに**行き先の時刻を打つ**ほうが、利用者が本当に知っていることに近い。

#### 6.1.5 運用番号の自動採番

便ができたとき（[§6.1.2](#612-時刻入力)）、運用番号を自動で入れる。

| 場合 | 入れる番号 |
| --- | --- |
| 継げる運用がある | その運用番号 |
| **継げる運用が無い** | **まだ使われていない新しい運用番号** |
| 時刻や経路が解決できない | 空欄（何に継げるかを決めようがない） |

**継げる運用**とは、「終着停留所が当該便の始発停留所と一致し、かつ終着時刻 ≦ 当該便の始発時刻」を満たす運用である。複数あれば終着時刻が最も遅いものを採る。運用の**末尾に継ぐことしかしない** — 途中に割り込めば後続との繋がりが崩れ、V-01 か V-02 を必ず生む。

新しい運用番号は `A` `B` … `Z` `AA` `AB` … の順に、**まだ使われていない最初のもの**を採る。

提案値は通常の編集と同様に上書きでき、自動で入ったことを UI 上で区別しない。区別すると「これは自分が書いたのか」を利用者に覚えさせることになる。

> **v4.11 で「該当が無ければ空欄のまま」を改めた。** 空欄のままにする規則は「間違った提案より、提案しないほうがよい」という考えに基づいていたが、**白紙から作るかぎり運用番号が 1 つも付かない**という結果を生んでいた。継げる運用が存在しないのだから、最初の便には提案が出ず、2 便目もその 1 便目が運用を持たない以上どこにも継げない。以下ずっと空欄である。
>
> どこにも継げない便が**新しい運用を始める**のは、間違った提案ではない。継げないとは「その車両ではもう走れない」ということであり、別の車両が要る。運用番号が必ず在れば、前運用・後運用の欄（[§6.1.7](#617-出区入区)）も運用の色（[§6.1.3](#613-運用番号欄)）も最初から働く。
>
> 空欄そのものは無くならない。利用者は消せるし、消したものを書き戻すことはしない。空欄の便は引き続き V-07（情報）で拾われる。

#### 6.1.6 便番号の採番

便番号は**始発時刻から導出する**（GTFS `trip_short_name`）。利用者は記入しない。

| 便の種別 | 並べ方 | 接頭辞 | 例 |
| --- | --- | --- | --- |
| 営業便・`directionId: 0`（吹田方面） | 方向ごとに始発時刻の昇順 | `E` | `E1` `E2` `E3` … |
| 営業便・`directionId: 1`（豊中方面） | 方向ごとに始発時刻の昇順 | `W` | `W1` `W2` `W3` … |

**回送便は番号を持たない**（v4.6）。番号は便を**指すため**にあり、指す必要が生じるのは画面に出るものだけである。回送便は列にならず（[§6.1.7](#617-出区入区)）、時刻表では前運用・後運用の欄に時刻として、ダイヤグラムでは営業便に続く破線として現れる。どちらも隣の営業便を指せば足りる。

> v4.4 では回送便にも `D1` `D2` … と採番していたが、v4.5 で回送便を列から外した時点で**表示先が無くなっていた**。回送便が導出値になった今（v4.6）、番号を振る対象そのものが編集のたびに作り直される。廃止する。

**採番は導出であり、既存の番号に依存しない。** 便を追加・削除・移動すれば、常に時刻順に詰め直される。前回の番号を見て空き番号を探すような処理を持つと、履歴に依存して結果が変わり、同じダイヤから同じ番号が得られなくなる。

**便番号は永続化しない。** 保存すると、便を 1 つ動かすたびに全便の番号を書き換えることになり、取り消しの単位（[§6.7](#67-undoredo)）が「1 便の移動」ではなく「全便の書き換え」になってしまう。ファイルに持たないことで、この問題そのものが消える。GTFS へ書き出す際（v2）に導出して埋める。

番号が付かない便がある。表示は `―` とする。

- **時刻が未入力の便**（`anchor: null`）— 時刻順に並べようがないため
- 参照が壊れていて時刻を導出できない便

始発停留所が違う便（豊中学舎発・箕面学舎発・工学部前発）も、同じ方向であれば始発時刻で一列に並べて採番する。

#### 6.1.7 出区・入区

回送便は**列にせず、営業便に結合して表示する**。前運用・後運用の行がそれである。

| 欄 | 条件 | 表示 |
| --- | --- | --- |
| 前運用 | `pullOut: true` | 車庫を出る時刻 |
| 前運用 | 同じ運用の直前に営業便がある | その便の便番号（`W2` など） |
| 前運用 | どちらでもない | 空欄 |
| 後運用 | `pullIn: true` | 車庫に着く時刻 |
| 後運用 | 同じ運用の直後に営業便がある | その便の便番号 |
| 後運用 | どちらでもない | 空欄 |

**出区・入区の表示は運用番号に依存しない。** その便自身の `pullOut` / `pullIn` を映すだけであり、運用番号が空欄でも切り替えられ、時刻が出る。**繋がる相手を映すほう**（営業便の便番号）だけが運用を要する。空欄の便どうしが繋がらないのは変わらない（[§6.1.3](#613-運用番号欄)）。

**「どの便と繋がるか」は指定しない。** 同じ運用番号を持つ便を始発時刻の昇順に並べたものが行路であり（[§5.8](#58-運用の導出)）、前後関係はそこから決まる。利用者が指定するのは運用番号と、この出区・入区の**有無だけ**である。

**欄に営業便の便番号が出ていても切り替えられる**（v4.6 の規定を T-51 で撤回）。

v4.6 では「既に前後の便と繋がっている便が、同時に車庫を出入りすることはあり得ない」として押しボタンを無効にすると定めた。**これは誤りである。** 運用の途中で一度車庫へ帰る運用（[後述](#一度入区してから再び出区する運用)）は、まさに**繋がっている 2 便の間に車庫を挟む**操作であり、その第一歩が「後運用に次便の番号が出ている欄を押す」ことになる。無効にすると、その運用を作る手立てが無くなる。

押した直後は繋がりが切れた状態になるが、それは V-01 が伝える。もう一方の便にも切り替えを入れれば繋がりが戻る。**手順の途中で止まっても、何が足りないかは検証が伝える。**

#### 出区・入区は 0 分折返し

**出区した車はその場で折り返して営業を始め、入区する車は営業を終えた場所からそのまま車庫へ向かう。** 待ち合わせは車庫で行う（[§5.8](#58-運用の導出) の営業所待機）。

この制約により、回送便に決めるものが残らない。

| 決めるもの | 決まり方 |
| --- | --- |
| 停車パターン | 営業便の始発（出区）・終着（入区）の停留所から一意に決まる。例: 豊中学舎発の便の出区は「車庫発豊中」 |
| 時刻 | 営業便の始発時刻・終着時刻と同じ（0 分折返し）。車庫側の時刻は区間所要時間から導出される |
| 運用番号 | 営業便と同じ |

したがって出区・入区は**有無を切り替えるだけ**でよい。利用者が持つのは真偽値 2 つ（`Trip.pullOut` / `pullIn`）である。

#### 回送便は保存せず、展開する（v4.6）

回送便が要る場面 — 運用の導出（[§5.8](#58-運用の導出)）・ダイヤ検証（[§6.6](#66-ダイヤ検証)）・ダイヤグラム描画（[§6.2](#62-ダイヤグラム描画)）・前運用/後運用の欄 — では、営業便から回送便を**その時点で展開する**。

| 展開した回送便の項目 | 値 |
| --- | --- |
| `patternId` | 営業便の始発（出区）・終着（入区）停留所から一意（R-11 が存在を保証する） |
| `anchor` | **営業便と接する停留所**に、営業便の始発時刻・終着時刻と同じ時刻で置く |
| `blockId` | 営業便と同じ |
| `tripId` | 営業便の ID から決まる（`<tripId>#out` / `<tripId>#in`） |
| `pullOut` / `pullIn` | ともに `false`（回送の回送は無い） |

アンカーを車庫側ではなく接点に置くのは、区間所要時間を改定したときに**動いてほしくないのが接点だから**である（[§5.6](#56-trip便)、[UC-5](#uc-5-区間所要時間の改定)）。車庫側の時刻はそこから導出され、ひとりでに追随する。

`tripId` を新しい UUID にせず元の便から決めるのは、保存されない値だからである。**同じ入力から同じ ID が出る**ことで、検証の指摘やダイヤグラムの選択が再描画をまたいで同じものを指し続ける。

展開しない場合が 2 つある。

- **時刻が未入力の便**（`anchor: null`）— 回送の時刻も決まらない。前運用・後運用の欄は空欄
- **車庫側の時刻が表せる範囲（0:00〜47:55）を外れる便** — 0:10 発の便の出区は前日 23:50 となる。V-04 で報告する

#### 営業便を動かすと回送も動く（v4.6）

回送が導出値であることの見返りがこれである。営業便を編集するとき、回送のための処理は要らない。

| 営業便への操作 | 回送 |
| --- | --- |
| 時刻をずらす | 同じだけ動く |
| 途中停留所の時刻を入れ直す | 始発・終着が動いた分だけ動く |
| パターンを変える | 始発・終着停留所が変われば、繋がる回送パターンも変わる |
| 便を消す | 一緒に消える |
| 運用番号を変える | 一緒に変わる |
| 取り消す | 一緒に戻る |

#### 一度入区してから再び出区する運用

同じ運用が日中に一度車庫へ帰ることを表せる。**前の便の `pullIn` と、次の便の `pullOut` を立てる**だけでよい。前の便の後運用に車庫着時刻が、次の便の前運用に車庫発時刻が出る。その間が営業所待機であり（[§5.8](#58-運用の導出)）、待機そのものは 2 つの列の間にあるため表には出ない。短すぎる待機は V-09 が知らせる。

片側だけを切り替えた状態（入区したのに次の便が車庫発でない、など）は V-01 が拾う。**手順の途中で止まっても、何が足りないかは検証が伝える。**

#### 保存されたファイルに回送便がある場合

版数 2 以前のファイルには回送便が `Trip` として入っている。読込時に**営業便の `pullOut` / `pullIn` へ畳む**（[§7.3](#73-バージョン互換性)）。

### 6.2 ダイヤグラム描画

#### 6.2.1 座標系

- **横軸**: 時刻。左から右。**表示範囲は 7:00〜22:00。**
- **縦軸**: 停留所。上から下へ、`Stop.axisPosition` に比例した間隔で配置。`hiddenInEditor: true` の停留所は表示しない。**方向によって反転しない**（両方向を 1 枚に重ねて描くため、向きを決められない）。時刻表は方向ごとに並びを変える（[§6.1.1](#611-レイアウト)）ため、上下が一致しない場合がある。
- **軸位置は所要時間に合わせる**（v4.28）。ダイヤグラムは傾きで速さを読むものであり、同じ所要時間の区間が違う傾きで描かれれば誤読の元になる。区間所要時間 1 分 = 軸 1 単位を原則とする（付録 A.1）。
- **同じ軸位置の停留所があり得る**（v4.28）。コンベ前と人科前はどちらも工学部前から 5 分であり、同じ高さに置く。微生物研究所前と工学部前は 0 分の区間で結ばれており、やはり同じ高さになる。
  - 線は停留所ごとに引く（同じ高さ・同じ `gridStyle` なら見た目は 1 本）。
  - **名前は線を挟んで上下に振り分ける**。近すぎる名前を落とす規則（[§6.2.2](#622-描画要素)）は当てはめない——重ならない置き方があるのに消すと、その停留所はどの拡大率でも読めないままになる。
  - **1 本の線が 2 つの停留所を指す。** 作図（[§6.3.3](#633-新規便の作図)）では、時刻表で開いている方向が通るほうの停留所に便を作る。
- **網目の路線を 1 本の縦軸に潰す以上、すべての区間は合わせられない**（v4.28）。直行（豊中学舎↔コンベ前、25 分 = 35 単位）は箕面学舎を経由しないぶん速く、箕面を通る軸の上では必ず寝る。**往復で同じ食い違いに揃う**ことが、実現できる最善である。人科前→箕面学舎（20 分 = 15 単位）も、箕面学舎と工学部前の位置が先に決まっている以上、動かす余地が無い。
- **千里営業所は縦軸に並べない**（v4.27）。営業所は 3 拠点（豊中学舎・箕面学舎・工学部前）のいずれからも 20 分にあり、**縦軸のどの位置に置いても等距離を表せない**。位置に意味が無い点へ線を引けば、その線の傾きにも交差にも意味が無い。それでいて豊中行きの回送は縦軸の全域を横切り、最も目立つ線になっていた。**見にくさに見合う情報が入っていない。** 専用レーン（帯・境界線・縦軸ラベル。v4.15）も併せて廃する。回送は営業便の端から伸びる「ヒゲ」で示す（[§6.2.2](#622-描画要素)）。
- `directionId: 0` の便は左上→右下、`directionId: 1` の便は左下→右上のスジとなる。
- **罫線は表示範囲（7:00〜22:00）の中だけに引く**（v4.15）。範囲の外まで格子を伸ばすと、表示範囲がどこまでなのかが絵から分からない。

#### 6.2.2 描画要素

| 要素 | 仕様 |
| --- | --- |
| 停留所線 | `gridStyle` に従う横罫線。 |
| 時刻線 | 60 分線（実線・濃）、30 分線（実線・淡）、10 分線（点線）、5 分線。拡大率に応じて間引く。 |
| スジ | パターンの `color` で描画。停留所で折れ点を打つ。**線種も併せて変える**（下記）。 |
| 停車の点 | 折れ点それぞれにスジと同じ色の丸を打つ（v4.30）。半径は px で持ち、拡大しても変わらない。回送には打たない。 |
| 回送スジ | 破線で描画し、**営業スジより細くする**（v4.16）。営業便の端から営業所側へ短く伸ばす「ヒゲ」とする（v4.27）。営業便から展開する（[§6.1.7](#617-出区入区)）。 |
| 便番号ラベル | スジの始点近傍。重なる場合は間引く。回送は番号を持たないため付けない。 |
| 選択ハイライト | 選択中のスジを太線＋端点ハンドル表示。 |
| 停留所名 | **略称**（`shortName`、v4.26）を縦軸の左に右揃えで置く。**欄の幅は一番長い略称から決める。** |
| 時刻目盛 | 横軸の上。60 分線に添える。**線の右側に置く**（中央に揃えると左端の目盛が停留所名の欄にはみ出す）。 |

**時刻線の最小粒度は 5 分とする。** 全時刻が 5 分刻みである以上、1 分線に情報価値がない。

**ラベルは重ねない**（v4.15）

縮めた画面では、線を引ける間隔と文字を置ける間隔が食い違う。**線は残し、文字だけを間引く。**

| ラベル | 間引き方 |
| --- | --- |
| 時刻目盛 | 1 → 2 → 3 → 6 → 12 時間ごとと粗くしていき、隣と触れない刻みを採る |
| 停留所名 | 直前に置いた名前と近すぎるものを落とす。線は残るため、拡大すれば名前が戻る |

停留所名を落とすことは、その停留所を消すことではない。**読めない字を 2 つ重ねるより、1 つを読めるほうがよい。** 便番号ラベルも同じ扱いとする（v4.16）——番号は時刻表にも出ているため、落ちても失われる情報は無い。

**スジの線種**（v4.16、[§9.4](#94-アクセシビリティ)）

パターンの識別を色だけに依存させない。**線種が担うのは「各駅か通過か」の 1 点だけである**（v4.29）。

| 種別 | 線種 | パターン |
| --- | --- | --- |
| 各駅（`local`） | 実線 | S3・S2・M2・T3・T2・M4 |
| 通過（`express`） | 破線 | S1・T1 |

線種を 4 種類配っていた（方向ごとの定義順で 実線 → 破線 → 点線 → 一点鎖線）のを改めた。**線種が 4 つあると、どの線が何を意味するのかを覚えていないと読めない。** 実際に見分けたいのは「箕面学舎に寄るか、直行か」であり、区間便かどうかは**スジの端がどこにあるか**で読める。区別する必要の無いものに別の記号を与えると、記号のほうが多くなる。

方向は線の傾きで分かるため、線種は方向をまたいで使い回す。**定義の順には左右されない**——並べ替えても絵は変わらない。

**回送スジは営業スジより細くする。** 運用で着色すると（[§6.2.4](#624-表示フィルタ着色)）回送は元の便と同じ色になり、破線どうしの違いは刻みの長さだけになる。太さを変えておけば、色をどう塗っても営業便でないことが読める。

**停車する停留所に点を打つ**（v4.30、[§9.4](#94-アクセシビリティ)）

**折れ角だけでは、箕面学舎に寄るかどうかが読めない。** 豊中学舎→箕面学舎が 20 分、箕面学舎→コンベ前が 15 分であり、軸位置を引き直した後（v4.28）でも傾きの差は小さく、拡大率によってはほとんど直線に見える。

打つのは**折れ点すべて**である。パターンに含まれる停留所はすべて乗り降りのできる停留所であり（[§5.4](#54-handling取扱区分)に「通過」は無い）、「経由するが停まらない」点は存在しない。直行便に箕面学舎の点が出ないのは、そこを**通っていない**からである。

線種（v4.29）が種別を、点が停車の事実を示す **2 段**になる。どちらも色に頼らない。

**回送スジは「ヒゲ」とする**（v4.27）

営業所には縦軸上の置き場所が無い（[§6.2.1](#621-座標系)）。回送スジは、営業便に繋がる側の端点から**営業所の方向へ一定の長さだけ伸ばして打ち切る。**

| 決め | 理由 |
| --- | --- |
| 伸ばす長さは **px で決める**（15px） | 軸の単位で決めると、縦に拡げるたびにヒゲが伸び、横断が戻ってくる。線幅や破線の刻みと同じ**絵の記号の大きさ**であって、距離でも時間でもない |
| 向きは下（縦軸の外側） | v4.15 の営業所レーンが下にあった読み方を引き継ぐ |
| **横（時刻）は正直に置く** | 7:40 出庫なら、ヒゲの端は 7:40 の位置にある。出入庫の時刻は目盛から読める |
| ヒゲも掴める | 選択の単位は保存されている便であり、ヒゲを掴めば元の営業便が選ばれる（[§6.3.1](#631-選択)） |

**消すのではなくヒゲにする。** 表示フィルタで回送を隠すのと違い、出入庫の**有無・時刻・向き**は絵に残る。付け忘れた出入庫が絵から消えては、ダイヤグラムを見て気づけない。

**スジは表示範囲（7:00〜22:00）の中だけに描く。** 範囲の外へ出た便は、そのままでは停留所名の欄や目盛の帯に線を引く。格子と同じ範囲に収める。

**選択の単位は保存されている便である。** 営業便を選ぶと、そこから展開された出区・入区のスジも一緒に強調される。回送は便の一部であって、別に選べるものではない（[§6.1.7](#617-出区入区)）。

#### 6.2.3 拡大縮小・スクロール

- <kbd>Ctrl</kbd> + ホイール: 横方向（時間軸）の拡大縮小
- <kbd>Ctrl</kbd>+<kbd>Shift</kbd> + ホイール: 縦方向の拡大縮小
- ホイール: 縦スクロール / <kbd>Shift</kbd> + ホイール: 横スクロール
- 中ボタンの引きずり、または <kbd>Space</kbd> + 引きずりで掴んで動かす
- **送りのつまみ**（canvas の右と下）で送る（v4.39、#143）
- <kbd>Ctrl</kbd>+<kbd>0</kbd> で既定の視野に戻す

**送りのつまみは、動かせるときにだけ出す**（v4.39）

全体が画面に入っているなら、その向きに送る先は無い。押しても何も起きないつまみを置くと、**動かないのは壊れているからだ**と読まれる。

つまみを足したあとも、掴んで引きずる・ホイールで送るはそのまま残す。**つまみが与えるのは、覚えていなくても動かせる道と、いまどのあたりを見ているかの手がかり**であり、速く動かす道を取り上げる理由にはならない。縦のつまみは**上が豊中側**とする（縦軸の並びと上下を揃える）。

**拡大の中心はカーソルに固定する。** 掴んでいる場所が動くと、拡げるたびに見ていた便を探し直すことになる。

**拡大率には下限と上限を設ける**（v4.17）。下限は 1 日分がおよそ画面に収まるところ、上限は 1 分が指で掴める幅になるところに置く。際限なく縮められると、格子も文字も潰れた灰色の帯だけが残り、戻す手立てが分からなくなる。範囲外の値を持つファイルは**拒まずに収めて開く**。

| | 下限 | 上限 |
| --- | --- | --- |
| 横（1 分あたり px） | 0.5 | 40 |
| 縦（軸位置 1 単位あたり px） | 1 | 60 |

**送りは描くものの範囲に収める**（v4.17）。表示範囲（7:00〜22:00）と縦軸の外へは送れない。**全体が入っているときは端に寄せる** — 全部見えているのに更に送れると、何も無い場所へ迷い込み、戻る手立てが分からなくなる。

**スクロール位置は 5 分の倍数に縛らない**（v4.17）。5 分刻みの決まり（[§2.1](#21-時刻の表現)）は便の時刻についてのものであって、画面をどこまで送ったかについてのものではない。縛ると、拡大の中心をカーソルに合わせられず、送りも 5 分単位に飛ぶ。

**視野を変えることは編集ではない**（v4.17）。

- **取り消しの対象にしない**（[§6.7](#67-undoredo)）。undo が「さっき縮めたぶん」を戻し始めたら、便を直した記憶にたどり着けない
- **未保存にしない。** 視野はファイルに保存されるが（[§5.10](#510-project全体構造)）、それは開き直したときの便宜であって、保存を促すほどの中身ではない。画面を送っただけで、閉じるたびに保存を尋ねられるのは誤りである

| 横方向拡大率（1 分あたり px） | 表示する時刻線 |
| --- | --- |
| < 0.5 | 60 分 |
| 0.5 以上 2 未満 | 60 分, 30 分 |
| 2 以上 6 未満 | 60 分, 30 分, 10 分 |
| 6 以上 | 上記 + 5 分 |

**境目は下限を含む**（v4.15）。ちょうど 0.5 なら 30 分線を描く。どちらとも取れる書き方では、実装ごとに違う絵が出る。

#### 6.2.4 表示フィルタ・着色

- パターン / 方向 / 運用ごとの表示・非表示
- 回送便の表示・非表示
- 着色モード: **パターンで着色** / **運用で着色**

**営業便を隠すと、その出区・入区も消える**（v4.16）。回送は営業便から展開された線であり、元の便が画面に無いのに残っていては、どこへ繋がる回送なのかが分からない。

**運用の色は隠されている便も数えて割り当てる**（v4.16、[§5.8](#58-運用)）。色は運用番号の昇順の位置で決まるため、表示を切り替えるたびに残った運用の色が入れ替わっては、色で運用を追えない。運用番号が空欄の便は数に入れず、パターンの色で描く。

**持つのは「隠しているもの」の一覧である**（v4.21）。「表示しているもの」を持つと、`route.json` にパターンが 1 つ増えた瞬間、既存のプロジェクトではそれが隠れて現れる。隠す側を持てば、増えたものは既定で見える。

**切替はそれぞれの一覧に置く**（v4.21、[§6.4](#64-画面レイアウト)）。パターンと運用はサイドパネルに一覧として並ぶため、表示・非表示のチェックもその行に置く。同じ切替を 2 か所に出すと、どちらが効いているのかを利用者が確かめなければならない。一覧を持たない方向と回送、そして着色モードだけが独立した節に残る。

#### 6.2.5 実装方式

HTML Canvas 2D で描画する。DOM 要素によるスジ描画は行わない。再描画は `requestAnimationFrame` に集約し、1 フレーム 1 回までとする。高 DPI 環境では `devicePixelRatio` を反映する。

### 6.3 ダイヤグラム上での編集

#### 6.3.1 選択

- スジのクリックで選択。<kbd>Ctrl</kbd> + クリックで複数選択。矩形選択に対応。
- 選択状態は時刻表エディタと**双方向に同期**する。時刻表側の該当列が自動でスクロール表示される。

**掴む単位は保存されている便である**（v4.18）。回送スジを掴んでも、選ばれるのはそれを生んだ営業便である（[§6.1.7](#617-出区入区)）。回送は便の一部であって、別に選べるものではない。

**重なっていれば最も近いものを選ぶ**（v4.18）。密集した領域では複数のスジが許容範囲に入る。手前から順に見て最初に見つけたものを選ぶと、同じ場所を押すたびに違う便が選ばれるように見える。

| 操作 | はたらき |
| --- | --- |
| クリック | そのスジだけを選ぶ。何も無い場所なら選択を解く |
| <kbd>Ctrl</kbd> + クリック | 選択に足す。**既に選ばれているものなら外す** |
| <kbd>Ctrl</kbd> + 何も無い場所 | 何もしない（外した拍子に積み上げた選択を消さない） |
| 引きずる | 矩形選択。**触れているスジを選ぶ**（囲み切らなくてよい） |
| <kbd>Ctrl</kbd> + 引きずる | 囲んだものを選択に足す |

**わずかに動いてもクリックとして扱う**（v4.18）。押して離すまでに指がまったく動かないことはない。動いた量がしきい値を超えて初めて矩形選択に移る。

**掴めるスジの上ではカーソルの形を変える。** 押せば選べることが、押す前に分かる。

**囲んでいる最中の枠は破線の輪郭だけとし、塗り潰さない**（v4.18）。中を塗ると、いま選ぼうとしているスジが枠の下に隠れる。

**選択はどちらの画面にも 1 つしかない**（v4.23）。時刻表とダイヤグラムはどちらも同じ選択を見ているだけであり、**同期のための状態を持たない**。「どちらで選んでも他方が追う」のは、追わせているのではなく、初めから 1 つだからである。

追随して動くのは選択そのものではなく、**見せ方**である。

| 選ばれたとき | 起きること |
| --- | --- |
| 時刻表 | 該当の列を画面に入れる。**焦点は移さない**（利用者の手はまだそこに無い） |
| 時刻表 | 選ばれた便が別方向なら、その方向タブを開く。ただし**今の方向に 1 本でもあるなら動かさない**。**2 方向が並んでいるときは動かさない**（v4.43） |
| ダイヤグラム | 該当のスジを太く描く。**画面の外にあるときだけ**視野を寄せる |

**寄せるのは見えていないときだけである**（v4.23）。選ぶたびに視野が飛ぶと、時刻表とダイヤグラムを見比べられない。**一部でも見えていれば動かさない**——全体が入ることまで求めると、長い便を選ぶたびに縮尺の合わない位置へ飛ぶ。送りきれない便（表示範囲の外）では動かさない。

**方向タブの切り替えは履歴に載せない**（v4.23）。同じダイヤの別の面を見るだけであり、しかも選択に追随して自動で切り替わる。履歴に載せると、**利用者が押していない操作**が取り消しの段に積まれる。

**押して方向を切り替えたときだけ選択を解く**（v4.23）。見えていない便を一括シフト（[§6.1.2](#612-時刻入力)）の巻き添えにしないためである。選択に追随して切り替わった場合は解かない——そちらは「選ばれた便を見せる」ための切り替えである。**2 方向が並んでいるときも解かない**（v4.43）——隠れる便が無く、切り替えは「どちらを触っているか」を移すだけである。

#### 6.3.2 スジの移動

**スジ上のどこをドラッグしても、便全体が水平に平行移動する。**

- **頂点（折れ点）を個別に動かす操作は存在しない。** 傾きは区間所要時間で決まり、便ごとに変えられないため。
- スナップ単位は **5 分**。
- ドラッグ中はシフト量を数値で表示（例: `+15 分`）。
- 縦方向のドラッグは無視する。
- <kbd>Esc</kbd> でドラッグを取り消す。
- アンカー停留所は変えず、`anchor.time` のみを更新する。

**選んである便はまとめて動く**（v4.19）。掴んだ便が選択に入っていなければ、**まずその便を選んでから**動かす。何が動くのかを見せずに動かし始めては、意図しない便を動かしていても気づけない。

**1 便でも 0:00〜47:55 を外れるなら、何も動かさない**（[§6.1.2](#612-時刻入力) の一括シフトと同じ）。一部だけ動いた状態は、利用者が求めたものではない。

**引きずっている最中も、便そのものが動いている**（v4.19）。途中経過の絵を別に持たない——見えているものが状態そのものであり、「途中の絵」と「確定した値」が食い違う余地が無い。履歴の上では引きずり全体が **1 回の取り消しで戻る**（[§6.7](#67-undoredo) の `mergeKey`）。<kbd>Esc</kbd> はその 1 回を取り消すことで元の位置へ戻す。

**画面に出す数字は、実際に動いた分とする。** 範囲を外れて動かせなかったとき、求めた分を出すと、数字と便の位置が食い違う。

#### 6.3.3 新規便の作図

「スジ作成」モードで停留所線上をクリックすると、その時刻（5 分丸め）にその停留所を通る便が作成される。終点を指定する操作は不要である（パターンが終点を決めるため）。

**始発に限らない**（v4.24）。仕様書は当初「始発停留所線上」としていたが、アンカーはどの停留所にも置ける（[§5.6](#56-trip便)）。時刻表の升目に打ったときと**同じ規則**にするほうが、覚えることが少ない（[§6.1.2](#612-時刻入力)）——打った停留所を、打った時刻に通る便ができる。

経路は**押した停留所と、時刻表で開いている方向**から決まる（§6.1.2 と同じ `patternForStop`）。同じ停留所を両方向の便が通るため、方向を決める手立てが要る。

**運用番号も提案される**（[§6.1.5](#615-運用番号の自動採番)）。作られた便はそのまま選択される。

**引きずっても線は伸びない**（v4.24）。終点はパターンが決めており、引き伸ばす操作に意味を持たせようがない。

**停留所線から離れた場所を押しても何も起きない**（v4.24）。押した覚えのない便ができるより、押しても何も起きないほうがよい。作れる場所ではカーソルを十字にして示す。

**営業所の帯には引けない**（v4.24）。車庫発の便は出区として作るものであり（[§6.1.7](#617-出区入区)）、営業便の始発にはならない。

<kbd>Esc</kbd> で「選択」モードへ戻る。持ち続けるつもりの無い道具から抜ける手立てを、手元に残しておく。

**いまどちらの道具を持っているかを画面に出す**（v4.42、#144）

出さないと、**押しても何も起きない**か、**押した覚えのない便ができる**かのどちらかが起きる。場所はステータスバーと編集メニューの印である（[§8.1](#81-主要キーボードショートカット)）。

#### 6.3.4 コンテキストメニュー

スジの右クリックで、便の複製・削除・パターン変更・運用番号の設定・時刻表エディタへジャンプ、を提供する。

**押したスジをまず選ぶ**（v4.25）。何に効く操作なのかを見せないままメニューを出すと、選んだつもりの無い便が消える。既に選ばれている便を押したときは選択を崩さない——まとめて効かせるための選択を、メニューを開いただけで失わない。

**選ばれている便すべてに効く**（v4.25）。1 本だけに効かせると、複数選んだ意味が消える。何便に効くのかをメニューの見出しに出す。

**揃っていない値は出さない**（v4.25）。パターンや運用番号がまちまちの選択で 1 つの値を出すと、開いただけで揃ってしまったように見える。

「時刻表エディタへジャンプ」がするのは**焦点を移すこと**である（v4.25）。列を画面へ入れるのは選択への追随（[§6.3.1](#631-選択)）が済ませており、選択は右クリックの時点で移っている。

**メニューは canvas に描かない**（v4.25）。押しボタンも記入欄も DOM に置く——焦点の移動も読み上げも、既にあるものが働く（[§9.4](#94-アクセシビリティ)）。<kbd>Esc</kbd> と外側のクリックで閉じ、閉じたら焦点はダイヤグラムへ返す。

### 6.4 画面レイアウト

**ダイヤグラムを上、時刻表を下とする上下 2 分割を基本レイアウトとする。**

**ツールバーは置かない**（v4.42、#144）。操作はすべてメニューから行う（[§8.1](#81-主要キーボードショートカット)）。

```
┌───────────────────────────────────────────────┐
│ メニューバー  ファイル 編集 表示 設定 ヘルプ      │
├────────┬──────────────────────────────────────┤
│        │                                      │
│ サイド │      ダイヤグラム（Canvas）           │
│ パネル │                                      │
│        │                                      │
│ ・ダイヤ├══════ ドラッグで高さ調整 ═══════════─┤
│ ・パターン│  方向タブ: [吹田方面] [豊中方面]      │
│ ・運用 ├──────────────────────────────────────┤
│ ・表示 │                                      │
│  フィルタ│      時刻表エディタ                  │
│        │                                      │
├────────┴──────────────────────────────────────┤
│ 検証パネル（折りたたみ可）                      │
├───────────────────────────────────────────────┤
│ ステータスバー  カーソル時刻・停留所 │ 道具 │ 便数 │ 運用数 │
└───────────────────────────────────────────────┘
```

- 上下の境界はドラッグで高さを調整できる。比率はプロジェクトの `view` に保存する。
- 上下いずれかを最大化するトグルを用意する（<kbd>Ctrl</kbd>+<kbd>1</kbd> / <kbd>Ctrl</kbd>+<kbd>2</kbd>）。
- ダイヤグラムと時刻表は常に同じダイヤ・同じ選択状態を表示する。

**画面全体は窓に収める**（v4.39、#143）

**溢れるのは中身であって、窓ではない。** 便が増えて時刻表が窓より広くなっても、送るのは時刻表の中だけである。窓ごと横に動くと、メニューバーもサイドパネルも画面の外へ出ていき、**どこにも戻る手がかりが無くなる。**

**高さは比率で持つ**（v4.20）。px で持つと、窓の大きさが変わるたびに持っている値が意味を失い、保存された値と画面の高さが食い違う。

**どちらも潰しきれない**（比率は 0.1〜0.9）。潰しきれると、境界だけが残った画面から元に戻す手立てが分からなくなる。片方だけを見たいときは最大化を使う——こちらは押し直せば必ず戻り、**保存されている比率を書き換えない**。

**最大化は保存しない**（v4.20）。比率はファイルに残るが（[§5.10](#510-project全体構造)）、最大化は「いま片方をじっくり見ている」というだけの姿である。開き直した画面が片側の潰れた形で始まると、壊れたように見える。最大化している間は境界を出さない（分ける相手が画面に無い）。

**最大化は場所が空くだけではない**（v4.43、#145）。時刻表を最大化しているあいだは、空いた縦の場所に**2 方向を並べて出す**（[§6.1.1](#611-レイアウト)）。同じものを大きくするより、そこでしか見られないものを見せるほうが、最大化する理由になる。

**境界はキーボードでも動かせる**（[§9.4](#94-アクセシビリティ)）。矢印キーで 5% ずつ、<kbd>Home</kbd> / <kbd>End</kbd> で端まで動く。

**分割比率を変えることは編集ではない**（v4.20）。視野と同じく（[§6.2.3](#623-拡大縮小スクロール)）履歴に載せず、未保存にもしない。

ステータスバーのカーソル時刻は**5 分に丸めて出す**（v4.20）。1 分刻みで出すと、そこに便を置けるように見える（[§2.1](#21-時刻の表現)）。

#### 6.4.1 サイドパネル

上から順に「何を編集しているか（ダイヤ）→ 何が描かれるか（停車パターン・運用）→ どう描かれるか（表示）」を並べる。

- **ダイヤ**: 一覧・切替・追加・改名・削除。**最後の 1 つは消せない**（v4.21）——ダイヤが 0 本のプロジェクトには便の置き場所が無く、時刻表も出せない。名前を空にもできない——保存はできても読み込めないファイルになる（[§7.4](#74-検証)）
- **停車パターン**: 色と線種の見本を添えた読み取り専用の一覧。定義を直すのは隠し設定（[§6.5.4](#654-停車パターンタブ隠し設定)）の仕事である。**回送のパターンは並べない**（v4.21）——回送スジは営業便から展開された線であり（[§6.1.7](#617-出区入区)）、パターンの絞り込みは保存されている便にしか掛からない。押しても何も起きないチェックになる。回送はまとめて 1 つの切替で消す
- **運用**: 運用番号・稼働時間帯・便数。**便数に回送は数えない**（v4.21）——回送は営業便から展開された線であり（[§6.1.7](#617-出区入区)）、数えると 1 便の運用が 3 便に見える
- **表示**: 着色モード・方向・回送便

**ダイヤグラムと時刻表の外に置く**（v4.21）。どちらにも同じように効く設定であり、中に入れると片方を最大化したときに消える。

**色見本には線種を添える**（[§9.4](#94-アクセシビリティ)）。ダイヤグラムのスジと同じ規則で作ることで、一覧と画面の見え方が必ず一致する。

**ダイヤを切り替えたら選択は解く**（v4.21）。選択は便を指しており、別のダイヤに移れば指す先が画面に無い。

### 6.5 設定ダイアログ

メニューまたは <kbd>Ctrl</kbd>+<kbd>,</kbd> から開く。

#### 6.5.1 区間所要時間タブ

区間表（[§5.2](#52-区間所要時間)）を一覧で表示し、**所要時間を一括で編集できる。**

```
 区間                                        所要時間
 ────────────────────────────────────────────────────
 豊中学舎          →  箕面学舎                [20] 分
 箕面学舎          →  豊中学舎                [20] 分
 豊中学舎          →  コンベンションセンター前  [25] 分
 箕面学舎          →  コンベンションセンター前  [15] 分
 コンベンションセンター前 → 微生物研究所前       [ 5] 分
 微生物研究所前     →  工学部前                [ 0] 分
 工学部前          →  人間科学部前             [ 5] 分
 人間科学部前      →  豊中学舎                [25] 分
 人間科学部前      →  箕面学舎                [20] 分
 （回送区間 6 件）                            [20] 分
```

- 入力は 5 の倍数に制限する（R-01）。**受け取れない値では適用そのものを止める**（v4.32）。
- **変更を適用すると、その区間を通るすべての便の時刻が、各便のアンカーを基準に再計算される。** 影響を受ける便数を適用前に提示する。
- 変更は `route.json` に書き戻す。書き戻し前に [§5.5.2](#552-ネットワーク定義の検証) の検証を行い、違反があれば保存を拒否する。
- この操作は Undo 可能とする。

**打った値は適用するまで状態に触れない**（v4.32）

打ちかけの「1」で全便の時刻が動いては、直している最中に画面が跳ね回る。適用を押し、**何便に効くかを見てから**確かめる。履歴に載るのはその 1 回である。

**時刻を「作り直す」処理は無い**（v4.32）

便が持つのはアンカー 1 点だけであり（[§5.6](#56-便の時刻導出)）、ほかの停留所の時刻は区間表から毎回導かれる。区間所要時間を変えれば、その区間を通る便の時刻は**次に引いたときにもう新しい**。アンカーの時刻が動かないことも、作り直しを書かないことから従う。

**「既定値に戻す」は入力を戻すことである**（v4.32）

戻す先は**今の `route.json` の値**であり、出荷時の値ではない。書き戻したあとの `route.json` に元の値は残っておらず、戻すにはファイルを差し替えるほかない。

#### 6.5.2 動作タブ

- **Undo 履歴の保存段数**（既定 100、範囲 10〜1000）
- 自動バックアップの間隔（既定 5 分、範囲 1〜60 分）

**時刻の丸め方は設定にしない**（v4.36、#134）

丸めは常に**近いほう**（四捨五入。[§6.1.2](#612-時刻入力)）であり、切り上げ・切り捨て・拒否は選べない。

時刻を 5 分に丸める道は 4 つある——時刻表の升目に打つ、ダイヤグラムのカーソル、作図、スジの引きずり。**丸め方を選べるようにすると、どの道に効くのかを決めなければならない。** 打つときは切り上げたいが掴んで動かすときは近いほうがよい、という人もいれば、揃っていないと混乱する人もいる。どちらが正しいかは分からず、**一度出した選択肢は後から片方へ寄せられない。**

丸め方が 1 つなら、経路ごとに食い違いようがない。決める場所も 1 つとする（`roundMinutesToGrain`）。

#### 6.5.3 表示タブ

- テーマ（ライト / ダーク / システムに従う。[§9.4](#94-アクセシビリティ)）
- ダイヤグラムの既定拡大率（<kbd>Ctrl</kbd>+<kbd>0</kbd> が戻す先。v4.32）
- 停留所の線種（`gridStyle`）の上書き（v4.35）

**停車パターンの色と線種も上書きできる**（v4.40、#147）

同じ理屈である。どのパターンが直行かは路線の事実であり、その線が見分けやすいかはその人の目の話である。

**色と線種は独立に選ぶ。** 片方だけ変えても、もう片方は `route.json` のままである。線種は**実線 / 破線 / 1 点鎖線**の 3 つから選ぶ——刻みを打ち込める形にすると、線種が「見分けるためのもの」から「飾り」に変わる（[§6.2.2](#622-スジの描画)、#114）。**回送の線種は選べない**（回送かどうかはパターンの好みではない）。

選んだ色も、地色に対して読めるよう出すときだけ調える（[§9.4](#94-アクセシビリティ)）。**運用の色はここではない**（§5.8。文書のものであり、プロジェクトに保存する）。

**線種の上書きで `route.json` は書き換わらない**（v4.35）

どの停留所が幹線か（`gridStyle`）は路線の事実であり、書き換えてよいものではない。一方で「この線が細くて見失う」はその人の目の話である。上書きは設定に持ち、**当てるのは描く直前だけ**とする。同じファイルを渡した相手の画面が、こちらの好みで変わることもない。

表は**上書きした停留所だけ**を持つ。全停留所ぶんを持つと、`route.json` 側で線種を直したときに古い値で上書きし続け、路線図を直したのに画面が変わらないという食い違いになる。選び直せるよう「路線図のまま」を残し、その横に `route.json` の値を出す。

**設定はプロジェクトとは別に保存する**（v4.34）

履歴段数もバックアップ間隔もテーマも「この道具をどう使うか」であり、開いたファイルによって変わるものではない。デスクトップ版は設定ディレクトリの `settings.json`、Web 版はブラウザの保存領域に置く。

**隠し設定を有効にしたことは保存しない**（[§6.5.4](#654-停車パターンタブ隠し設定)）。起動のたびに閉じることがその機能の一部である。

読めなかった設定は既定に倒す。**壊れた設定ファイルで起動できなくなるのは、失うものに対して代償が大きい。**

#### 6.5.4 停車パターンタブ（隠し設定）

<kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>Alt</kbd>+<kbd>D</kbd> で有効化されるまで表示しない。

- 停車パターンの追加・編集・削除（停留所の並び、取扱区分）
- 変更は `route.json` に書き戻す。
- パターンを編集すると、そのパターンを使う既存の便の時刻がアンカーを基準に再計算される。影響を受ける便数を事前に提示する。

停留所そのもの（名称・順序・軸位置）は設定ダイアログから編集できない。`route.json` を直接編集する。

**なぜ隠すのか**（v4.33）

危ないからではない。停車パターンは**普段の作図で触る場所ではない**——路線の定義であり、便を作る操作とは別の頻度で変わる。並べておくと、探しものの途中で押されてしまう。

| 決め | 理由 |
| --- | --- |
| 有効化の鍵は[§8.1](#81-主要キーボードショートカット)の表に載せない | **隠してあるものを鍵の一覧に出しては隠したことにならない。** メニューにも出さない |
| 有効にしたことは保存しない | 起動のたびに閉じる。覚えさせて開いたままにすると、隠した意味が薄れる |
| **直したそばから検証する** | 区間表に無い停留所対を並べると、その便の時刻は計算できない（R-03）。適用のときだけ知らせるのでは、どの操作が壊したのかを戻って探すことになる。**足りない区間をそのまま出す** |
| 追加は「複製」とする | 路線名も色も回送かどうかも、ここでは編集できない項目である。写せば、触れない項目にも意味のある値が入る。白紙から作ると、そこに何を入れるかを決められない |
| 編集できるのは 名前・方向・種別・停留所の並び・取扱区分 | それ以外（`patternId`・色・既定・回送かどうか）は、**変えると別のものになる**か、ほかの規則（R-05・R-07）が縛っている |

#### 6.5.5 Web 版での制約

Web 版では `route.json` を直接書き戻せないため、区間所要時間・停車パターンの編集結果はファイルとしてダウンロードする（[§10.4](#104-プラットフォーム抽象化)）。編集内容はセッション中のみブラウザ上で有効であり、`route.json` を差し替えるまで永続化されない旨を UI で明示する。

### 6.6 ダイヤ検証

編集のたびに検証を実行し、検証パネルに一覧する。項目クリックで該当箇所へジャンプする。

**便内の時刻矛盾はデータモデル上発生し得ないため、検証項目に含めない。** 検証は運用の整合性と便同士の関係に絞られる。

| ID | 重大度 | 検証内容 |
| --- | --- | --- |
| V-01 | エラー | 同一運用内で、前便の終着停留所と次便の始発停留所が不一致 |
| V-02 | エラー | 同一運用内で、前便の終着時刻 > 次便の始発時刻（折返し時分が負） |
| V-03 | エラー | 同一運用内で、2 便の運行時間帯が重複している |
| V-04 | エラー | 便の参照が壊れていて時刻を導出できない（`patternId` が存在しない、アンカー停留所が経路に無い、時刻が表現できる範囲外）。**出区・入区の車庫側の時刻が範囲外になる場合を含む**（[§6.1.7](#617-出区入区)） |
| V-05 | 警告 | 運用の先頭便が出庫回送でない、または末尾便が入庫回送でない |
| V-06 | 警告 | 同方向の便の間隔が極端（既定: 5 分未満、または 120 分超） |
| V-07 | 情報 | 運用番号が空欄の便が存在する |
| V-08 | 情報 | アンカーが未設定（時刻が未入力）の便が存在する |
| V-09 | 情報 | 営業所待機が短い（既定 30 分未満）。入庫せず停留所で待機できる可能性がある。 |

**検証は回送便を展開したうえで行う**（[§6.1.7](#617-出区入区)）。V-01・V-02・V-05・V-09 はいずれも回送便を含む行路を見る項目であり、展開前の営業便だけでは判定できない。

検証は 300ms のデバウンスを挟んで同期実行する。100 便規模では Web Worker は不要である。

**遅らせるのは計算が重いからではない**（v4.22）。時刻を 1 文字打つたびに検証すると、まだ意味を成さない途中の状態について指摘が現れては消える。**手が止まってから 1 回**走らせる。

#### 6.6.1 検証パネル

画面の下に置き、折りたたみできる（[§6.4](#64-画面レイアウト)）。

- **畳んでも件数は見える**（v4.22）。閉じているあいだに増えたエラーに気づけないのでは、畳むことが「見ないことにする」になる
- 重大度は**記号・言葉・色の 3 つ**で示す（[§9.4](#94-アクセシビリティ)）。色だけではエラーと情報を取り違える
- 一覧は**重い順、同じ重さなら項目番号の順**に並べる（v4.22）。検証の実行順に並べると、便を 1 つ足すたびに順序が入れ替わり、直した結果を追えない
- **エラーが 0 件のときはそう書く**（v4.22）。空欄は「まだ検証していない」に見える
- 重大度で絞り込める。絞り込みは**保存しない**——開き直したときに指摘が隠れたままだと、「指摘が出ない」と受け取られる。件数の表示は絞り込んでも変わらない
- 項目を押すと**その便が選ばれ、時刻表の方向タブが切り替わり、ダイヤグラムがその時刻へ送られる**。運用を指す指摘（V-01・V-02・V-05）では**その運用の便をすべて選ぶ**（v4.22）——2 便の関係が問題であり、片方だけを選んでも何が起きているのか分からない
- 送り先は**少し手前**にする（v4.22）。左端ちょうどに置くと、その便へ入ってくる回送や 1 本前の便が画面の外に残る

**パネルの開閉はプロジェクトに保存するが、履歴には載せない**（v4.22）。どこを見ているか（送り・分割・パネルの開閉）は編集ではない。何を見るか（着色・表示フィルタ・編集中のダイヤ・方向）は編集として履歴に載る。

> **追い越しの検査を廃止した（v4.3）**: v4.2 まで「同一パターンの便が追い越している」を警告項目としていたが、**検査すべき条件が残らない**ため項目ごと削除した。
>
> - 同一パターンの便は区間所要時間も同じであり、先に出た便が必ず先に着く。追い越しは起こり得ない。
> - パターンが違う便どうしの追い越しは**正常な運行**である。直行便は箕面学舎を経由しないため、箕面学舎経由の便を追い抜いてよい。経路が違う以上、追い抜かれた便の利用者が不利益を被ることもない。
>
> **V-04 を新設した（T-43）**: `Trip.anchor` を nullable にしたことで、「時刻が未入力」と「参照が壊れている」を区別できるようになった。前者は入力の途中である正常な状態（V-08・情報）、後者はデータの破損（V-04・エラー）であり、利用者が取るべき行動が違う。
>
> 番号は最終的に V-01〜V-09 の 9 項目となり、ID の昇順が重大度の順（エラー → 警告 → 情報）と一致する。
>
> **V-03 の範囲（T-10 で明確化）**: 隣り合う便どうしの重複は「折返し時分が負」と同じ事象であり、V-02 が報告する。V-03 は 1 つ以上離れた便との重複だけを見る。両方で報告すると同じ問題が 2 度並ぶ一方、離れた便との重複（長い便 1 本の途中に短い便が 2 本収まっている等）は V-02 では捉えられないため、両者で漏れなく重複せず覆う。
>
> **V-06 の測り方（T-10 で明確化）**: 便間隔は**停留所ごとに**測る。便によって始発停留所が異なるため（豊中学舎発・箕面学舎発・工学部前発）、始発時刻の差を間隔と呼ぶと利用者から見た待ち時間とかけ離れる。

### 6.7 Undo / Redo

- すべての編集操作を対象とする。区間所要時間・停車パターンの変更も含む。
- **履歴の保存段数は設定可能**（既定 100、範囲 10〜1000）。
- 履歴はメモリ上のみ。ファイルには保存しない。
- 連続する同種の操作（同一セルへの連続入力、ドラッグ中の中間状態）は 1 操作にまとめる。

### 6.8 ファイル操作

- 新規作成 / 開く / 上書き保存 / 名前を付けて保存
- 最近使ったファイル（最大 10 件）
- **自動バックアップ**: 編集がある場合、既定 5 分ごとに保存する。異常終了後の起動時に復元を提案する。保存先はプラットフォームにより異なる（[§10.4](#104-プラットフォーム抽象化)）。
- 未保存の変更がある状態で閉じる際は確認ダイアログを表示する。
- ウィンドウ／タブのタイトルは `ファイル名 [*] — UoDia` の形式。

## 7. ファイル形式仕様

### 7.1 概要

| 項目 | 内容 |
| --- | --- |
| 拡張子 | `.uodia` |
| 形式 | JSON |
| 文字コード | UTF-8（BOM なし） |
| 改行 | LF |
| 整形 | インデント 2 スペース（差分を取りやすくするため圧縮しない） |
| キーの並び | 辞書順（再帰的） |
| 末尾 | 改行を 1 つ置く |

**同じ内容からは常に同じバイト列が出る。** 保存のたびに差分が出ると、実際に何を変えたのかが git のログから読み取れなくなるためである。キーの並びを構造体ごとに書き下すのではなく辞書順に整列させるのは、スキーマに項目を足したときに書き漏らして**データが静かに消える**ことを防ぐためである。配列の順序は保つ（便の並びは利用者が並べ替えた結果であり、意味がある）。

### 7.2 ルート構造

```jsonc
{
  "meta": {
    "format": "uodia",
    "formatVersion": 1,
    "appVersion": "1.0.0",
    "routeVersion": 1,           // 依存する route.json の version
    "createdAt": "2026-07-25T10:00:00+09:00",
    "updatedAt": "2026-07-25T12:34:56+09:00"
  },
  "document": { "name": "2026年度 授業期間ダイヤ", "author": "", "comment": "" },
  "services": [
    {
      "serviceId": "weekday", "serviceName": "授業期間平日ダイヤ",
      "trips": [
        { "tripId": "...", "patternId": "S1",
          "anchor": { "stopId": "1_0", "time": 28800 },
          "blockId": "A", "pullOut": true, "pullIn": false }
      ]
    }
  ],
  "view": { /* ViewSettings */ }
}
```

**1 便あたりの永続化データは 6 フィールドのみ**である。100 便でもファイルは数十 KB に収まり、git での差分管理にも適する。便番号（[§6.1.6](#616-便番号の採番)）と回送便（[§6.1.7](#617-出区入区)）は導出値であり、保存しない。

### 7.3 バージョン互換性

- `meta.formatVersion` がアプリの対応版数より新しい場合、読込を拒否してアプリの更新を促す。
- 古い場合はマイグレーション処理を順次適用する。
- `meta.routeVersion` が現在の `route.json` と不一致の場合、「ネットワーク定義が変更されています。時刻が再計算されます」と警告したうえで開く。アンカーは保持されるため、各便の基準停留所の時刻は変わらない。
- 未知のキーは無視して読み込む（警告のみ）。

**版数 2**（v4.4）: `Trip.tripShortName` を廃止した。版数 1 のファイルにある値は**読み捨てる**。便番号は始発時刻から導出されるため、保存されていた値を復元する必要がない。

**版数 3**（v4.6）: 回送便を保存しないことにした（[§6.1.7](#617-出区入区)）。版数 2 以前のファイルにある回送便は、次の規則で営業便の `pullOut` / `pullIn` へ畳む。

1. 同じ `blockId` の便を始発時刻順に並べる
2. 回送便のうち、**車庫を始発とし、直後の営業便の始発停留所・始発時刻と終着が一致する**ものを、その営業便の `pullOut: true` に畳んで取り除く
3. 同様に、**車庫を終着とし、直前の営業便の終着停留所・終着時刻と始発が一致する**ものを `pullIn: true` に畳んで取り除く
4. 畳めなかった回送便は**取り除き、読込時の警告に挙げる**（[§7.4.1](#741-読込時の警告)）

畳めない回送便とは、運用番号が空欄のもの・接点が繋がっていないもの・車庫を経由しないものである。いずれも本アプリでは作れず、破綻したデータとして V-01 や V-07 が既に報告していたものである。**黙って捨てず、何を捨てたかを必ず伝える。**

### 7.4 検証

読込は 4 段階で行い、**どの段階で失敗したかを型で区別する**（ネットワーク定義の読込と同じ方針）。

| 段階 | 内容 | 失敗時 |
| --- | --- | --- |
| `json` | JSON として解釈できるか | 開かない |
| `version` | 版数を読み取り、必要な変換を適用できるか | 開かない |
| `schema` | Zod スキーマに適合するか | 不正なパスを示して開かない |
| 参照整合性 | `patternId` / `stopId` が実在するか | **既定値へ倒して開く**（警告） |

壊れた参照でファイルを開けなくすることはしない。`route.json` を書き換えたあとに古いプロジェクトを開く状況は普通に起こり、そこで「開けません」とだけ言われても利用者は手を打てないためである。

#### 7.4.1 読込時の警告

| ID | 内容 |
| --- | --- |
| W-01 | `route.json` の版数がプロジェクトの想定と違う |
| W-02 | 停車パターンが見つからず、既定のパターンへ倒した |
| W-03 | アンカー停留所が経路に無く、時刻を未入力へ倒した |
| W-04 | 知らないキーがあったので読み飛ばした |
| W-05 | マイグレーションを適用した |
| W-06 | 営業便に畳めない回送便があったので取り除いた（版数 3 への移行。[§7.3](#73-バージョン互換性)） |

**W-03 で時刻を捨てるのは意図的である。** 始発へ寄せるなどして時刻を残すと、利用者が入力した覚えのない時刻がダイヤに紛れ込む。時刻が消えたことは検証（V-08）にも現れるため、見落とされることはない。

**W-04 は黙って捨てない。** スキーマ検証が知らないキーを捨てること自体は正しい振る舞いだが、黙っていると「保存し直したら項目が消えた」という結果だけが残る。検証の前後を突き合わせ、入力にしか無いキーを報告する。既定値の補完で出力にだけ現れるキーは対象外である。

## 8. 操作仕様

### 8.1 主要キーボードショートカット

**鍵の定義は 1 か所に置く**（v4.31、T-37）。メニューに並ぶ項目も、押したときに走るものも、同じ表（`features/shell/commands.ts`）を読む。2 か所に書くと、メニューには「Ctrl+S」と出ているのに押しても何も起きない、という食い違いが**画面を見ても分からない形で**生まれる。

| キー | 動作 |
| --- | --- |
| <kbd>Ctrl</kbd>+<kbd>N</kbd> / <kbd>O</kbd> / <kbd>S</kbd> | 新規 / 開く / 保存 |
| <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>S</kbd> | 名前を付けて保存 |
| <kbd>Ctrl</kbd>+<kbd>Z</kbd> / <kbd>Y</kbd> | Undo / Redo |
| <kbd>Ctrl</kbd>+<kbd>C</kbd> / <kbd>V</kbd> / <kbd>X</kbd> | 便のコピー / 貼付 / 切取（[§6.1.4](#614-便の操作)） |
| <kbd>Delete</kbd> | **焦点のある場所で決まる。** 列見出しなら選択便の削除、セルなら時刻を消す（[§6.1.2](#612-時刻入力)） |
| <kbd>Ctrl</kbd>+<kbd>,</kbd> | 設定ダイアログ |
| <kbd>Ctrl</kbd>+<kbd>1</kbd> / <kbd>2</kbd> | ダイヤグラム / 時刻表を最大化（トグル） |
| <kbd>Ctrl</kbd>+<kbd>0</kbd> | ズームを既定に戻す |
| <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>Alt</kbd>+<kbd>D</kbd> | 隠し設定を有効化 |

**記入欄の中では横取りしない**（v4.31）

時刻・運用番号・文書名を打っている最中の <kbd>Ctrl</kbd>+<kbd>Z</kbd> は**文字の取り消し**であり、便の取り消しではない。写す・切り取る・貼るも同じで、記入欄の中では文字が相手である（[§6.1.4](#614-便の操作)）。

一方、保存や最大化は記入欄の中でも効く。**文字の編集としての意味を持たない操作は、焦点がどこにあっても同じように働く。**

**メニューバー**（v4.31）

見出しは ファイル / 編集 / 表示 / 設定 / ヘルプ の 5 つ。<kbd>Tab</kbd> で見出しへ、<kbd>↓</kbd> で開き、<kbd>↑</kbd><kbd>↓</kbd> で項目を選び、<kbd>←</kbd><kbd>→</kbd> で隣のメニューへ移る。<kbd>Esc</kbd> で閉じ、**焦点は開いた見出しへ戻す**（§9.4）。

| 決め | 理由 |
| --- | --- |
| **使えない操作も薄く出す** | 消すと並びが押すたびに変わり、位置で覚えられなくなる |
| <kbd>Delete</kbd> は表に載せない | 焦点のある場所で意味が変わり、全体で 1 つの動きに結び付けられない |
| 隠し設定の鍵も載せない | **隠してあるものをメニューに並べては隠したことにならない** |
| **今その状態の項目には印を付ける**（v4.42） | 作図の道具と最大化は操作ではなく状態である。押しボタンの「押されている」に当たるものを、メニューでは印で示す（読み上げにも `menuitemradio` として伝わる） |

**操作はすべてメニューから行う**（v4.42、#144）

ツールバーは置かない。**同じ操作を 2 か所に置かない**——ツールバーとメニューに同じ押しボタンが並ぶと、どちらが正なのかを利用者が確かめる羽目になる。行が 1 本減るぶん、ダイヤグラムと時刻表に使える高さも増える。

ファイルのメニューには**文書情報**（文書名・作成者・メモ）を置く。打った時点で効き、続けて打った分は 1 回の取り消しにまとまる。

作図の道具（選択 / スジ作成）には鍵を与えない。**作図をやめる <kbd>Esc</kbd> は既にあり**（[§6.3.3](#633-新規便の作図)）、始める側だけに鍵を足すと釣り合わない。
| ツールバーは残す | よく押すものを手の届く所に置くためであり、**どちらから押しても同じものが走る** |

### 8.2 UI 言語

日本語のみ。文言のリソース分離は行わない（対象利用者が限定されるため、過剰な抽象化を避ける）。

## 9. 非機能要件

### 9.1 性能

1 日 100 便程度を前提とし、余裕を持って以下を目標とする。

| 項目 | 目標値 |
| --- | --- |
| アプリ起動時間 | 2 秒以内（コールドスタート） |
| プロジェクト読込（150 便） | 300ms 以内 |
| ダイヤグラムのパン・ズーム | 60fps 維持 |
| 時刻セル入力から画面反映まで | 16ms 以内 |
| 検証の実行時間（150 便） | 50ms 以内 |
| デスクトップ版バイナリサイズ | 30MB 以内 |
| Web 版の初回ロード | 1MB 以内（gzip 後） |

計測結果は [performance.md](performance.md) に記録する（T-40）。

### 9.2 信頼性

- 自動バックアップ（[§6.8](#68-ファイル操作)）を必須とする。
- デスクトップ版の保存はアトミックに行う（一時ファイルへ書き出してからリネーム）。
- 未捕捉例外はエラーダイアログで通知し、アプリを即座に終了させない。

### 9.3 保守性

- TypeScript の `strict` を有効にし、`any` の使用を原則禁止する。
- ドメインロジック（時刻計算・検証・運用の導出）は UI とプラットフォームから分離し、純関数として単体テスト可能にする。
- ドメインロジックのテストカバレッジは 80% 以上を目標とする。
- **不変条件「全時刻が 300 秒の倍数」は型レベルまたはコンストラクタで保証する。** 生の `number` を時刻として引き回さない。

### 9.4 アクセシビリティ

- すべての主要機能をキーボードのみで操作できること。
- パターンの識別を色のみに依存させない（線種を併用する）。
- ライト / ダークテーマに対応する。

**色は 1 か所にしか置かない**（v4.34）

配色は CSS カスタムプロパティが持ち、ダイヤグラムの canvas もそこから読む。JS 側にも色を書くと、片方だけ直した配色が生まれ、格子とスジで違う灰色が並ぶ。

| 選択 | 出るもの |
| --- | --- |
| システムに従う（既定） | 根に属性を付けない。媒体問い合わせが決める |
| 明るい | `[data-theme='light']`。**OS が暗くても明るいまま** |
| 暗い | `[data-theme='dark']` |

**スジの色は出すときだけ調える**（v4.34）

スジの色は路線の持ち物である（`route.json` の `color`）。暗い配色に切り替えたからといって、その値を書き換えるわけにはいかない——同じ便が環境によって違う色のデータになる。

そこで**描くときにだけ明るさを調え**、地色に対する明暗の比が **3**（WCAG 1.4.11 の図形の下限）を下回らないようにする。色相は動かさないため、見分けの手がかりは保たれる。直行吹田（`#1a4f8a`）は暗い地色に対して 2.1 しかなく、1.5px の線では沈んでしまう。

**焦点の枠は全体に敷く**（v4.34）

部品ごとに書くと、書き忘れた 1 つが「キーボードで辿ると行方不明になる場所」になる。`:focus-visible` で全体に敷き、部品側は位置の調整だけを行う。

## 10. 技術構成

### 10.1 スタック

| レイヤ | 技術 | 選定理由 |
| --- | --- | --- |
| デスクトップシェル | Tauri v2 | 軽量なバイナリ、安全なファイル I/O、マルチプラットフォーム |
| フロントエンド | React 18 + TypeScript 5 | エコシステムの厚さ、型安全性 |
| ビルド | Vite 5 | 高速な HMR、Tauri の標準構成、Web 版と共通 |

### 10.4 プラットフォーム抽象化

デスクトップ版と Web 版を同一コードベースから提供するため、環境依存の処理を `PlatformAdapter` インタフェースに集約する。**`src/domain/` と `src/features/` はこのインタフェースにのみ依存し、Tauri API とブラウザ API を直接呼ばない。**

```typescript
interface PlatformAdapter {
  /** この実装の識別子。作る FileHandle の kind と一致する。 */
  readonly kind: string;

  openProject(): Promise<{ handle: FileHandle; content: string } | null>;
  saveProject(handle: FileHandle, content: string): Promise<void>;
  saveProjectAs(content: string, suggestedName: string): Promise<FileHandle | null>;

  loadNetworkDef(): Promise<string>;
  saveNetworkDef(content: string): Promise<void>;
  canSaveNetworkDef(): boolean;        // Web 版は false

  writeBackup(content: string): Promise<void>;
  readBackup(): Promise<string | null>;
  clearBackup(): Promise<void>;        // 正常終了時に呼ぶ

  listRecentFiles(): Promise<readonly RecentFile[]>;
  addRecentFile(handle: FileHandle): Promise<void>;
}

interface FileHandle {
  readonly kind: string;   // 実体を作ったアダプタの識別子
  readonly name: string;   // 利用者に見せる名前
  readonly ref: unknown;   // アダプタだけが解釈する実体
}

interface PlatformCapabilities {
  readonly saveInPlace: boolean;        // 上書き保存できるか
  readonly recentFiles: boolean;        // 最近使ったファイルを保持できるか
  readonly networkDefWritable: boolean; // route.json を書き戻せるか
}
```

**できないことは `capabilities` で事前に伝える。** 呼んでから失敗するのでは、メニューを出してよいかを判断できず、利用者は押してから断られることになる。ブラウザの種類ではなく**機能の有無**で表す。「Firefox かどうか」で分岐すると、対応状況が変わるたびに判定を書き直すことになる。

| | デスクトップ版 | Web 版（File System Access API あり） | Web 版（無し） |
| --- | --- | --- | --- |
| `saveInPlace` | ✓ | ✓ | — （ダウンロード） |
| `recentFiles` | ✓ | ✓ | — |
| `networkDefWritable` | ✓ | — | — |

**取り消しは例外ではなく `null` で表す。** 利用者がダイアログを閉じるのは正常な操作であり、異常として扱うと呼び出し側が毎回 try/catch を書くことになる。例外は本当に失敗したとき（読めない・書けない）だけに残す。

**`FileHandle.ref` を解釈してよいのは、その値を作ったアダプタだけである。** 別の環境のハンドルを渡されたことに気づけるよう `kind` で作り主を名乗らせ、食い違えば失敗させる。黙って `name` で代用すると、別のファイルを上書きしかねない。

**アダプタは React のコンテキストで上から渡す。** import した時点で環境を判定する方式だと、テストが本物の環境を掴んでしまい、差し替えにモジュールのモックが要る。

**境界は ESLint で機械的に守る。** `src/domain/` と `src/features/` からの `@tauri-apps/*` の import、および永続化・通信に関わるブラウザ API（`localStorage` / `indexedDB` / `fetch` など）の使用を禁じる。ドメイン層ではさらに DOM（`window` / `document`）も禁じる。フィーチャ層で DOM を許すのは、画面を描く以上避けられないためである。方針を文書に書くだけでは「ここだけ」の直接呼び出しが必ず入り込む。

| 機能 | デスクトップ版（Tauri） | Web 版 |
| --- | --- | --- |
| ファイルを開く / 保存 | Tauri コマンド + OS ダイアログ | File System Access API。非対応ブラウザでは `<input type="file">` とダウンロードにフォールバック |
| 最近使ったファイル | JSON ファイルに永続化 | IndexedDB に `FileSystemFileHandle` を保存。フォールバック時は無効 |
| `route.json` の読込 | ファイルから読込 | バンドルされた静的アセットとして取得 |
| `route.json` の書き戻し | ファイルへ書込 | 不可。編集結果をダウンロードで提供する（[§6.5.5](#655-web-版での制約)） |
| 自動バックアップ | アプリデータディレクトリ | IndexedDB |

**ビルド**

| コマンド | 成果物 |
| --- | --- |
| `npm run build:web` | Web 版の静的ファイル一式 |
| `npm run build:desktop` | 各 OS 向けインストーラ（Web 版と同じバンドルを Tauri で包む） |

Web 版の成果物は任意の静的ホスティングに配置できるものとする。**GitHub Pages は採用しない**（2026-07-25 決定）。具体的な配信先は未定であり（[§12](#12-未確定事項) Q-2）、決定するまで自動デプロイは行わない。
