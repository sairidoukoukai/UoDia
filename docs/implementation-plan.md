## 1. 本書の位置づけ

仕様書 v4.1 を実装に落とすための計画書である。**1 タスク = 1 GitHub issue** となる粒度で分解しており、次フェーズではそのまま issue 化できる。

各タスクには目的・作業内容・成果物・受入条件・依存関係・規模を記す。受入条件は issue のクローズ判定にそのまま使う。

## 2. 開発方針

### 2.1 ドメイン層を先に完成させる

仕様の中核（アンカー方式による時刻導出、区間表、運用の導出、検証）はすべて **UI に依存しない純関数**である。これらを最初に実装し、単体テストで固めてから UI に着手する。

理由: このアプリの難しさは描画でも UI でもなく、**データモデルの一貫性**にある。ドメイン層がテストで保証されていれば、UI 層のバグは「表示の問題」に限定され、切り分けが容易になる。

### 2.2 垂直スライスの到達点を明示する

以下の 3 点を「動くものが見える」マイルストーンとする。進捗はここで測る。

| 到達点 | 完了タスク | 何ができるか |
| --- | --- | --- |
| **第 1 到達点** | T-20 まで | 時刻表に時刻を入力し、他の停留所の時刻が自動計算されるのが見える |
| **第 2 到達点** | T-29 まで | ダイヤグラムにスジが描かれ、ドラッグで動かせる |
| **第 3 到達点** | T-38 まで | v1 の全機能が繋がった状態（仕上げ前） |

### 2.3 テスト方針

| 層 | 方針 |
| --- | --- |
| `src/domain/` | **Vitest による単体テストを必須とする。カバレッジ 80% 以上。** 純関数のみで構成し、モックを要さない設計にする。 |
| `src/store/` | コマンドの do/undo が対称であることを重点的にテストする。 |

- コミットメッセージの接頭辞は `feat:` / `fix:` / `refactor:` / `test:` / `chore:` / `docs:`。

## 3. 技術的な設計判断

計画段階で確定させておくべき事項を先に決める。実装時の手戻りを防ぐため。

### 3.1 時刻の型

仕様書 §9.3 の「不変条件を型で保証する」要件を、branded type で実装する。

```typescript
// src/domain/time/types.ts
declare const brand: unique symbol;
export type Seconds = number & { readonly [brand]: "Seconds" };

/** 5 分刻みでない値、負の値は例外を投げる。 */
export function seconds(value: number): Seconds;
/** 任意の秒数を 5 分に四捨五入して Seconds にする。 */
export function roundToGrain(value: number): Seconds;
```

生の `number` を時刻として関数に渡せなくすることで、丸め忘れをコンパイル時に検出する。

### 3.2 Undo/Redo の実装方式

**Immer の `produceWithPatches` によるパッチ方式を採用する。**

```typescript
interface HistoryEntry {
  label: string;
  patches: Patch[];         // 適用パッチ
  inversePatches: Patch[];  // 逆パッチ
  mergeKey?: string;        // 同一キーの連続操作は 1 エントリにまとめる
}
```

- スナップショット方式（状態全体を複製）も 100 便規模では成立するが、パッチ方式のほうがメモリ効率が良く、Immer を状態管理に使う以上追加コストがない。
- `mergeKey` により「同一セルへの連続入力」「ドラッグ中の中間状態」を 1 操作にまとめる（仕様書 §6.7）。
- **ストアの状態変更はすべてコマンド経由に強制する。** ストアの `set` を直接呼ぶことを禁止し、履歴に載らない変更が生まれないようにする。

### 3.3 `route.json` の配置と書き戻し

設定ダイアログから区間所要時間を書き換えるため（仕様書 §6.5.1）、`route.json` は書き込み可能な場所に置く必要がある。

| 環境 | 初期配置 | 読込元 | 書き戻し先 |
| --- | --- | --- | --- |
| デスクトップ | Tauri のリソースに既定値を同梱 | アプリ設定ディレクトリ（初回起動時にリソースからコピー） | アプリ設定ディレクトリ |
| Web | 静的アセットとして同梱 | 静的アセット → 以降は IndexedDB の上書き分を優先 | IndexedDB（+ ダウンロード提供） |

「既定値に戻す」操作を設定ダイアログに用意し、同梱のリソースから復元できるようにする。

### 3.4 Canvas 描画のアーキテクチャ

- **Canvas は React の管理外に置く。** `<canvas>` を ref で取得し、描画はストアの購読 → `requestAnimationFrame` でスケジュールする。React の再レンダリングと描画を連動させない。
- **レイヤ分割は行わない。** 100 便 × 約 4 区間 = 約 400 セグメントであり、毎フレーム全描画で 60fps を満たせる。分割はコードを複雑にするだけで、この規模では不要。
- **当たり判定は総当たりで行う。** 空間インデックス（quadtree 等）は不要。点と線分の距離を 400 回計算しても 1ms に満たない。

### 3.5 描画関数の引数化

**描画関数は「描画先コンテキスト」と「ビューポート」を引数に取る純関数とし、ストア・DOM・グローバル状態を直接参照しない。**

```typescript
// src/features/diagram/render/drawDiagram.ts
export function drawDiagram(
  ctx: CanvasRenderingContext2D,
  scene: DiagramScene,      // 描画に必要なデータのみを集約した不変オブジェクト
  viewport: Viewport,       // 時間範囲・拡大率・原点
): void;

export interface Viewport {
  startTime: Seconds;      // 左端の時刻
  startAxis: number;       // 上端の軸位置
  pxPerMinute: number;
  pxPerAxisUnit: number;
  originX: number;         // 描画領域の左端（縦軸ラベルの幅）
  originY: number;         // 描画領域の上端（横軸ラベルの高さ）
  width: number;
  height: number;
}
```

**右端の時刻は持たない**（T-24 で改めた）。`startTime` と `pxPerMinute` と `width` から決まる導出値であり、持てば 2 つの値が食い違う状態を作れてしまう。**導出値は状態に持たない**という本ソフトの方針（便番号・運用の順序・回送便）をここでも守る。書き出しのときは「出したい時間範囲と幅から `pxPerMinute` を決める」形になる。

**理由**: v2 で予定している画像・PDF の書き出しは、この形にしておけば「画面用 canvas の代わりに、任意の解像度・任意の時間範囲のオフスクリーン canvas を渡す」だけで実現できる。

```typescript
// 画面用
drawDiagram(screenCtx, scene, currentViewport);

// 書き出し用 — 同じ関数、引数が違うだけ
drawDiagram(offscreenCtx, scene, { startTime: t(7,0), endTime: t(22,0), pxPerMinute: 8, ... });
```

描画関数がストアや DOM を直接読む作りにすると、書き出し時にレンダラを書き直すことになる。**差は数行の設計判断と数日の書き直しである。** v1 の時点で守る。

副次的な利点として、描画関数が純関数であればビューポートを固定した回帰テスト（同じ入力に対する `ctx` 呼び出し列の検証）が可能になる。

### 3.6 状態の構造

```typescript
interface AppState {
  network: NetworkDef;          // route.json 由来。派生キャッシュを含む
  project: Project;             // 編集対象。Undo/Redo の対象はここのみ
  ui: {                         // Undo 対象外
    activeServiceId: string;
    activeDirection: 0 | 1;
    selectedTripIds: string[];
    viewport: { startTime: Seconds; pxPerMinute: number; ... };
    splitRatio: number;
  };
  history: HistoryEntry[];
}
```

`network` の変更（区間所要時間の編集）は `project` の変更ではないが、**Undo 対象に含める**（仕様書 §6.7）。履歴エントリに対象（`network` / `project`）を持たせる。

描画関数へ渡す `DiagramScene` は、この `AppState` から描画に必要な部分だけを抽出した不変オブジェクトとする（[§3.5](#35-描画関数の引数化)）。`AppState` をそのまま渡すと、描画関数がストアの構造に依存してしまうため。

**目的**: 描画のインフラを整える（[§3.4](#34-canvas-描画のアーキテクチャ)、[§3.5](#35-描画関数の引数化)）。

**作業内容**
- `Viewport` 型と `DiagramScene` 型を定義する（[§3.5](#35-描画関数の引数化)）

#### T-28 当たり判定と選択

**目的**: 仕様書 §6.3.1 を実装する。

**作業内容**
- 点と線分の距離による当たり判定を実装する（総当たり、[§3.4](#34-canvas-描画のアーキテクチャ)）
- クリックで選択、<kbd>Ctrl</kbd> + クリックで複数選択
- 矩形選択（ドラッグで範囲指定）
- 選択中のスジを太線 + 端点ハンドルで描画する

**受入条件**
- 密集した領域でも意図したスジが選択できる（最も近いものを選ぶ）
- 400 セグメントの判定が 1ms 以内

**実装で定めた点**（仕様書 v4.18）
- **当たり判定は描画と同じ座標列を使う**（`tripPolylines`）。別々に組むと、拡大率や折れ点の扱いを片方だけ直した日に**見えている線と掴める線がずれる**。利用者から見れば「クリックしても選べない」であり、原因は画面のどこにも現れない
- **層のあいだの譲り合いは `preventDefault` で行う。** 送り（T-27）と選択は同じ押し下げを受け取る。送りの側が掴んだときに `preventDefault` を立て、選択の側はそれを見て譲る。DOM に元からある約束事であり、層どうしが互いを知らずに済む
- 囲んでいる最中の枠は `ui.selectionRect` に置き、**描くものの座標（時刻と軸位置）で持つ**。px で持つと、拡大率や canvas の大きさが変わった瞬間に別の便を指す
- 性能の試験は**最も速かった 1 回**を採る。他の試験と並んで走るため、平均は「判定にかかる時間」ではなく「そのとき機械が空いていたか」を測ってしまう

**規模**: M ／ **優先度**: MVP ／ **依存**: T-27

- 最大化トグル（<kbd>Ctrl</kbd>+<kbd>1</kbd> / <kbd>Ctrl</kbd>+<kbd>2</kbd>）
- ツールバー、ステータスバーの枠を配置する
- ステータスバー: カーソル位置の時刻・停留所、便数、運用数

**受入条件**
- 境界のドラッグでリサイズでき、比率が保存・復元される
- リサイズ時に Canvas が正しく再描画される

**実装で定めた点**（仕様書 v4.20）
- **分割比率も `ui` に持たせなかった。** T-27 の視野と同じ理由である（[§3.6](#36-状態設計)）。`project.view.splitRatio` の 1 か所に置き、履歴に載せず未保存にもしない操作（`setSplitRatio`）で書き換える。視野と同じ規則になるため、保存済みの参照を進める処理は `setView` として 1 つにまとめた
- **最大化だけは `ui` に置く。** 比率と違って保存しない——開き直した画面が片側の潰れた形で始まると、壊れたように見える。比率を 0 や 1 に書き込んで表さないのは、最大化を解いたときに**戻る先が消える**ためである。実際の高さは 2 つから導く（`effectiveRatio`）
- 比率は 0.1〜0.9 に収める。スキーマが縛っている範囲であり、**収めずに書き込むと書き出せても読み込めないファイルができる**（`clampSplitRatio`）
- 高さは `flex-grow` に比率をそのまま渡す。px で持つと、窓の大きさが変わるたびに計算し直す必要があり、保存された値と画面が食い違う瞬間ができる
- **canvas の再描画に手を入れていない。** 高さを CSS に任せたことで `ResizeObserver`（T-24）がそのまま働く。境界を動かす側が「描き直せ」と伝える道を作ると、伝え忘れが起きうる箇所が 1 つ増える
- **カーソルの位置は状態に置かない。** 置くと、指を動かすだけで購読が動き、ダイヤグラムが 1 秒に 60 回描き直される。ダイヤグラムから直に受け取り（`DiagramCanvas` の `onCursor`）、**指すものが変わったときだけ**伝える
- 境界は `role="separator"` とし、矢印・<kbd>Home</kbd>・<kbd>End</kbd> で動かせるようにした（仕様書 §9.4）。最大化している間は出さない
- 仮の操作列（文書名・バックアップ・最近使ったファイル）はツールバーの右端へ移した。本来の置き場所は T-35 と T-37 である

**規模**: M ／ **優先度**: MVP ／ **依存**: T-20, T-26

#### T-33 サイドパネル

**目的**: ダイヤ・パターン・運用・表示フィルタの操作面を提供する。

**作業内容**

- 着色モードの切替

**受入条件**
- フィルタの変更がダイヤグラムに即座に反映される

**実装で定めた点**（仕様書 v4.21）
- **表示・非表示の切替をそれぞれの一覧に置いた。** 作業内容は「表示フィルタのチェックボックス群」を独立した節として挙げていたが、パターンと運用は一覧として並ぶため、**同じものが 2 か所に出る**。行にチェックを置き、一覧を持たない方向・回送・着色モードだけを「表示」の節に残した

- 名前の欄は打ちながら書き込むが、**空の途中経過は画面の上だけに留める**（`ServiceList`）。離れたときに元の名前へ戻す
- 色は `blockColorsOf` / `assignPatternDashes` を時刻表・ダイヤグラムと共有した。同じ規則を書き直すと、一覧と画面の色がいつか食い違う

- **回送のパターンを一覧から外した。** 画面で押してみて気づいた——パターンの絞り込みは保存されている便に掛かり（`scene.ts` の `shownTrips`）、回送はその後に展開されるため、**チェックしても何も起きない**。回送の表示はまとめて 1 つの切替で行う
- サイドパネルは上下 2 分割の**外**に置いた。中に入れると、片方を最大化したとき（T-32）に消える
- T-26 の仮の操作列（`DiagramControls`）を削除した

#### T-34 検証パネル

**目的**: T-10 の検証結果を表示する。

**作業内容**
- 画面下部の折りたたみ可能なパネル
- 重大度（エラー / 警告 / 情報）ごとにアイコンと色で区別し、件数を表示する
- 項目のクリックで該当する便を選択し、ダイヤグラムと時刻表をスクロールする
- 300ms のデバウンスで再検証する
- 重大度によるフィルタ

**受入条件**
- 編集後 300ms で検証結果が更新される
- 項目クリックで該当箇所へジャンプする
- エラーが 0 件のとき、その旨が明示される

**実装で定めた点**（仕様書 v4.22）
- **検証結果は状態に持たない。** デバウンスが持つのは「いつ計算し直したか」だけであり、指摘そのものは今までどおりセレクタが導く（`selectValidation`）。待っている間に起きた変更を取りこぼさないよう、**時間切れの時点の状態から**計算する
- **パネルの開閉は履歴に載せない**（`setValidationPanelOpen`）。T-32 で引いた線をここでも使う——どこを見ているか（送り・分割・開閉）は編集ではなく、何を見るか（着色・フィルタ・ダイヤ・方向）は編集である
- 飛び先の決定を純関数に切り出した（`jump.ts`）。飛ぶことは選択・方向・送りの 3 つを同時に書き換える操作であり、画面の側で組み立てると「方向だけ切り替わって選択が付いてこない」半端な移動が生まれる
- 運用を指す指摘では**その運用の便をすべて選ぶ**。2 便の関係が問題であるため
- 時刻表側の寄せは、**選択が変わったら選ばれた列を画面に入れる**形にした（`TimetableGrid`）。検証パネルが時刻表の内部を知る必要が無く、T-38 の双方向同期でもそのまま働く。焦点は移さない——利用者の手はまだそこに無い
- 重大度の絞り込みは保存しない。並べ替えは重い順・項目番号順で固定した（実行順に並べると、便を 1 つ足すたびに一覧が動く）
- **一覧が空のとき、「無い」のか「隠している」のかを言い分ける。** 絞り込みで消えているのに「指摘はありません」と出ると、直すべきものが無いと受け取られる
- **V-01 の指摘文が停留所 ID を出していたのを名前に改めた**（T-10 の積み残し）。画面に出して初めて分かった——「前の便は 4_0 着です」では、読んでも直せない

**規模**: M ／ **優先度**: v1 ／ **依存**: T-10, T-32

#### T-38 選択状態の双方向同期

**目的**: 仕様書 §6.3.1 の同期を仕上げる。**本タスク完了が第 3 到達点。**

**作業内容**
- ダイヤグラムでの選択 → 時刻表の該当列をハイライトしスクロール表示する
- 時刻表での選択 → ダイヤグラムの該当スジをハイライトし、必要ならビューポートを移動する
- 選択状態を `ui.selectedTripIds` に一元化する

**受入条件**
- どちらで選択しても他方が追従する
- スクロールが無限ループしない

**実装で定めた点**（仕様書 v4.23）
- **同期のための状態を足していない。** 選択は初めから `ui.selectedTripIds` の 1 つだけであり（T-15 から）、双方向同期とは「両方がそれを見ている」ことに他ならない。足したのは**見せ方の追随**だけである
- **循環しないことを型と純関数で担保した。** `viewToReveal` は見えていれば `null`、寄せた結果が今と同じでも `null` を返す（べき等）。`directionToShow` も切り替えたあとは `null` を返す。**往復して揺れ続ける経路が存在しない**ことが、この 2 つの性質から言える
- **選択がどこで起きたかを知らずに済ませた。** ダイヤグラムで押して選んだスジは定義により見えているため、「見えていなければ寄せる」だけで両方向を賄える
- **方向タブを履歴に載せない操作に改めた**（`setActiveDirection`）。選択に追随して自動で切り替わるようになったため、履歴に載せると利用者が押していない操作が取り消しの段に積まれる。T-32・T-34 で引いた線（どこを見ているかは編集ではない）をここでも使う
- 押して切り替えたときだけ選択を解く。追随して切り替わったときに解くと、**寄せた先で選択が消える**（自分で自分を打ち消す）
- T-34 のジャンプから方向の切り替えを外した。同じ規則が 2 か所に書かれるのを避け、`JumpTarget` から `directionId` を落とした
- **V-06 の指摘文にも停留所 ID が漏れていたのを名前に改めた**（T-34 で V-01 を直したのと同じ）。画面を見て気づいた。名前を引く道具を `stopNameOf` として 1 か所にまとめた

**規模**: S ／ **優先度**: v1 ／ **依存**: T-28, T-32
