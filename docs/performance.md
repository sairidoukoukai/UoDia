# 性能の計測結果

| 項目 | 内容 |
| --- | --- |
| 対象 | UoDia v1.0（T-40 時点） |
| 計測日 | 2026-08-02 |
| 仕様書 | [specification.md](specification.md) §9.1 |

## 1. 何を、どこで測るか

**計算の速さと、画面の速さは別に測る。**

| 測る場所 | 何を測るか | 繰り返せるか |
| --- | --- | --- |
| `src/app/performance.test.ts` | 読込・検証・場面の組み立て | **CI で毎回走る。** 目標値をそのまま検証にしてある |
| `verify-t40.mjs`（使い捨て） | 起動・パン/ズーム・打鍵から反映まで | 実機（headless Chromium）で手元から走らせる |

画面の速さは**実際に描いてみないと分からない**。逆に、計算の速さは画面を組まずに測れるうえ、遅くなった日に気づけるほうが値打ちがある。

## 2. 計測環境

| 項目 | 内容 |
| --- | --- |
| OS | Linux 6.18（WSL2） |
| ブラウザ | Chromium 1228（headless、`--no-sandbox`、**GPU 無し**） |
| ビルド | `npm run build:web` の成果物を `vite preview` で配信 |
| データ | 150 便・10 運用・8 パターン（`scripts/generate-sample.mjs` で生成） |

**この環境は実機より不利である。** GPU が無く、仮想化を 1 枚挟んでいる。デスクトップ版（T-41）での再計測は、パッケージングが済んでから行う。

## 3. 結果

### 3.1 目標を満たしたもの

| 項目 | 目標 | 実測 | 判定 |
| --- | --- | --- | --- |
| アプリ起動時間 | 2 秒以内 | **1.18 / 1.28 / 2.34 秒**（3 回） | ✓（下記の注） |
| プロジェクト読込（150 便） | 300ms 以内 | **174 / 226 / 336ms**（状態に入るまで） | ✓（下記の注） |
| 検証の実行時間（150 便） | 50ms 以内 | **1.9ms** | ✓ |
| 時刻セル入力から画面反映まで | 16ms 以内 | **8.3〜20.9ms**（最小値の 3 回分） | △（下記の注） |
| Web 版の初回ロード | 1MB 以内（gzip 後） | **107KB** | ✓ |

- **起動と読込は回によって目標をまたぐ。** 3 回のうち 1 回ずつ超えた。超えた回はどちらも他の処理と重なったときであり、**同じ操作で 2 倍の開きが出る**ことがこの環境の性質である。実機での再計測を T-41 に送る。
- 打鍵から反映までは、**1 フレーム（16.7ms）を挟むかどうか**で倍近く変わる。打鍵を受けてから次の描画までを測っているため、下限は 1 フレームである。

### 3.2 60fps の維持

| 操作 | フレーム時間の中央値 | 95 パーセンタイル | 17ms 以内の割合 |
| --- | --- | --- | --- |
| パン（中ボタンの引きずり） | 16.7〜17.2ms | 23.3ms | 51〜57% |
| ズーム（ホイール） | 16.7ms | 17.7ms | 73〜75% |

**中央値は毎回 16.7〜17.2ms**、つまり垂直同期（60Hz = 16.67ms）のすぐ上に張り付いている。60fps に届く回と、1 フレーム落とす回が交互に来ている状態であり、**この環境では 60fps を厳密に保証できない**。

判定は **△**（実機での再計測を T-41 に送る）。GPU の無い headless では、canvas の転送自体が CPU に乗る。

### 3.3 デスクトップ版の大きさ（T-41 で計測）

**実行ファイルで測る。** インストーラは圧縮の効き方が OS ごとに違い、同じ数字として比べられない。CI が 3 OS で毎回確かめる（`scripts/check-bundle-size.mjs`）。

| OS | 実行ファイル | 配布物 |
| --- | --- | --- |
| Linux | **3.5MB** | `.deb` 1.5MB / `.rpm` 1.5MB / `.AppImage` 75.7MB |
| Windows | **3.2MB** | `.msi` 1.7MB / NSIS `.exe` 1.2MB |
| macOS | **3.1MB** | `.dmg` 1.7MB（aarch64） |

目標（30MB）に対して 1 割程度に収まっている。**WebView を OS のものに任せている**ためで、これは Tauri を選んだ理由そのものである（仕様書 §10.1）。

**AppImage だけが 75.7MB ある。** これは WebKitGTK を丸ごと抱き込む形式であり、「アプリのバイナリ」とは別物である。同じ理由で `.deb` / `.rpm` は 1.5MB に収まる——システムの WebKitGTK を使うためである。配るなら `.deb` / `.rpm` を勧める。

### 3.4 測っていないもの

| 項目 | 理由 |
| --- | --- |
| デスクトップ版での起動・パン/ズーム | **クリーンな環境での実機が要る**（T-41 の受入条件と同じ）。CI の成果物を入れて確かめる |

## 4. 直したこと

### サイドパネルが送りのたびに描き直されていた

ダイヤグラムの送り・拡げは `project.view.diagram` を書き換える。サイドパネルの 3 つの節は `view` を**丸ごと**購読していたため、**1 秒に 60 回、中身の変わらない一覧を作り直していた。**

必要な項目だけを購読するよう改めた（`hiddenPatternIds` など）。

```ts
// 前: 送りのたびに変わる
const view = useAppStore(selectView);
// 後: 隠しているものが変わったときだけ
const hidden = useAppStore((state) => selectView(state)?.hiddenPatternIds ?? NO_IDS);
```

`?? []` を書かないのは、**毎回新しい配列を返すと購読が必ず動く**ためである。空の一覧は 1 つだけ作って使い回す。

## 5. 記憶化が効いていることの確認

「送りだけなら組み立て直さない」ことを検証に固定した（`performance.test.ts`）。視野を変えても、場面の `trips` と `stops` は**同じ参照のまま**返る。ここが崩れると、送りのたびに 150 便ぶんの折れ点を作り直すことになる。

| 計測項目 | 実測 |
| --- | --- |
| プロジェクト読込（150 便） | 1.8ms |
| 検証（150 便） | 1.9ms |
| 場面の組み立て（150 便） | 1.4ms |
| 運用の導出（150 便） | 0.7ms |

**計算はどれも 1 フレームの 1/8 以下**に収まっている。重いのは描画と DOM であり、計算ではない。
