## 3. GTFS 入力画面（#198, #163）

### 3.1 設定ダイアログに入れない

設定ダイアログ（仕様書 §6.5）は既に 4 タブある（区間・動作・表示・パターン）。そこへ 3 つ足すと 7 タブになる。

**それ以上に、扱っているものが違う。**

| | 設定ダイアログ | GTFS 画面 |
| --- | --- | --- |
| 何を決めるか | **今の見え方と、区間の値** | **外へ出すときにだけ要る値** |
| 変えると何が動くか | 画面がすぐ変わる | **画面は何も変わらない** |
| 開く頻度 | 作図のたび | 出すときだけ |

**画面が何も変わらない値を、画面を変える場所に置かない。** 設定を開いた利用者は「変えたら何かが変わる」ものを探しており、そこに緯度経度が並んでいると、何のための欄なのかが読めない。

### 3.2 構成

**メニュー**: `ファイル > GTFS…`（[§9](#9-画面と操作の変更)）

```
┌─ GTFS ─────────────────────────────────────────┐
│ [事業者] [停留所] [カレンダー] [書き出し]         │
├────────────────────────────────────────────────┤
│                                                │
│   （選ばれたタブの中身）                          │
│                                                │
├────────────────────────────────────────────────┤
│                          [閉じる]               │
└────────────────────────────────────────────────┘
```

| タブ | 中身 | 保存先 |
| --- | --- | --- |
| 事業者 | `agency.txt` の項目 | `route.json` |
| 停留所 | 停留所ごとの緯度経度 | `route.json` |
| カレンダー | ダイヤごとの運行日 | `.uodia`（プロジェクト） |
| 書き出し | GTFS を出すボタンと、足りないものの一覧 | — |

**閉じるとき、書き戻しは設定ダイアログと同じ作法に従う**（仕様書 §6.5.1）。検証を通ったときだけ `route.json` へ書き、通らなければ状態を変えない。**書き戻せない環境（Web 版）では書き出す**（§6.5.5）。

### 3.3 事業者（agency）

| 項目 | GTFS | 備考 |
| --- | --- | --- |
| 事業者名 | `agency_name` | **実例に合わせる**（下記） |
| URL | `agency_url` | 必須項目である |
| タイムゾーン | `agency_timezone` | `Asia/Tokyo`。既定値を入れておく |
| 言語 | `agency_lang` | `ja`。既定値を入れておく |
| 電話番号 | `agency_phone` | 任意 |

**値は、後から与えられる GTFS の実例に従って固定する**（Q-19、2026-08-07 決定）。

**誰を事業者とするかを本ソフトが決めない。** 出した GTFS は既存のものと並べて使われる。そこで事業者名が食い違うと、**同じバスが 2 つの事業者のものとして現れる。** 名乗り方は既に決まっているはずであり、決まっているものを決め直す理由が無い。

**それでも入力欄は作る**（固定値を書き込むだけの画面にしない）。実例が変わったときに、コードを書き換えずに直せる。

**タイムゾーンと言語も欄として出す。** 隠すと、GTFS を読む側が「なぜこの値なのか」を確かめる手立てが無くなる。既定値を入れておけば、打つ手間は発生しない。

### 3.4 停留所の緯度経度

停留所の一覧に、緯度と経度の欄を並べる。**停留所そのもの（名称・順序・軸位置）はここでは編集できない**——設定ダイアログのパターンタブと同じ扱いとし、`route.json` を直接編集させる（仕様書 §6.5.4）。

| 停留所 | 緯度 | 経度 |
| --- | --- | --- |
| 豊中学舎 | `34.xxxxx` | `135.xxxxx` |
| 箕面学舎 | | ← 空欄のまま出せる |
| 千里営業所（車庫） | — | **欄そのものを出さない** |

**車庫には欄を出さない。** `Stop.isDepot: true` は `stops.txt` に出さないと決めてある（仕様書 §5.9）。**出さないものに欄があると、埋めなければならないように見える。**

**微生物研究所前には欄を出す。** `hiddenInEditor: true` だが `stops.txt` には出す停留所である（同上）。**時刻表に出ないことと、GTFS に出ないことは別である。**

### 3.5 事業者と緯度経度を `route.json` に置く

**どちらも路線の事実である。** 停留所がどこにあるかは、どのプロジェクトを開いていても同じであり、ダイヤの検討によって変わらない。

これは v1.0 で停車パターンの色を設定に、運用の色をプロジェクトに置き分けた判断（仕様書 §5.8）と同じ筋である。**その文書の中だけの名前はプロジェクトへ、路線の事実は `route.json` へ。**

**カレンダーだけは逆になる**（[§4.4](#44-データモデル)）。運行日はダイヤに属し、ダイヤはプロジェクトにある。

## 4. 運行日カレンダー（#197）

### 4.1 日の種類は 2 つしかない

**「授業期間平日ダイヤの日」と「休業期間ダイヤの日」のような分け方をしない。** バスは走るか、走らないかのどちらかである。

この決めは、`Service`（ダイヤ）が複数あってもよいことと矛盾しない。**プロジェクトの中に複数のダイヤを置けるのは、案を並べて比べるためである**（UC-2 増発案の検討）。**同時に走る 2 つのダイヤ**を表すためではない。

### 4.2 「運行なし」だけを持つ

**少ないほうを持つ。** 年間 365 日のうち走る日はおよそ 200 日ある。走る日を並べると 200 行、走らない日を並べると数十行になる。

**それ以上に、入力の意味が違う。** 走る日を数え上げる作業には終わりがあるかどうかが分からない（打ち漏らした日は「走らない日」として静かに消える）。走らない日を挙げる作業は、学年暦の休業期間を写すことであり、**元になる紙がある。**

### 4.3 曜日は範囲で持たない

**「運行なしの範囲だけを持つ」を素直に受けると、土日が範囲になる。** 1 年で 104 個の範囲を打つことになり、翌年また打ち直すことになる。

**曜日は繰り返しであって範囲ではない。** そこで持つものを 2 段にする。

| 段 | 持つもの | 例 |
| --- | --- | --- |
| 1. 走る曜日 | 月〜日のうちどれに走るか | 月・火・水・木・金 |
| 2. 運行なしの範囲 | 1 の曜日に当たっていても走らない期間 | 8/6〜9/30（夏季休業） |

**この 2 段は GTFS の作りと同じである。** `calendar.txt` が曜日と有効期間を、`calendar_dates.txt` が例外日を持つ（[§4.6](#46-gtfs-への写し方)）。**変換が要らない形で持つ**という v1.0 からの設計目標（仕様書 §5.9）をここでも守る。

### 4.4 データモデル

`Service` に `calendar` を足す。**任意項目とする**——持たないダイヤ（案を並べているだけのもの）が普通にあるため。

```typescript
interface Service {
  serviceId: string;
  serviceName: string;
  trips: Trip[];
  calendar?: ServiceCalendar;   // ← v2 で追加
}

interface ServiceCalendar {
  /** 有効期間の開始日（`YYYY-MM-DD`）。 */
  startDate: string;
  /** 有効期間の終了日（同上。**当日を含む**）。 */
  endDate: string;
  /** 走る曜日。空にはできない（§8.3）。 */
  weekdays: readonly Weekday[];
  /** 運行なしの期間。重なっていてもよい。 */
  closedRanges: readonly ClosedRange[];
}

type Weekday = 'mon' | 'tue' | 'wed' | 'thu' | 'fri' | 'sat' | 'sun';

interface ClosedRange {
  from: string;      // YYYY-MM-DD
  to: string;        // YYYY-MM-DD（当日を含む）
  note?: string;     // 「夏季休業」など。GTFS には出ない
}
```

**日付は文字列で持つ。** `Date` を持つと、保存のたびにタイムゾーンの解釈が挟まる。時刻ではなく暦の上の日を指しているのだから、`2026-08-06` という文字列がそのまま値である。これは時刻を秒で持っている（仕様書 §2.1）ことと矛盾しない——**あちらは 1 日の中の位置、こちらは暦の上の日**であり、別のものである。

**`note` は GTFS に出ない。** それでも持つのは、**半年後に自分の入力を読み返すため**である。`2026-08-06〜2026-09-30` とだけ並んでいると、なぜその範囲なのかが分からない。

**範囲は重なっていてよい。** 重なりを禁じると、「夏季休業」と「お盆」を別々に書けなくなる。**どちらも書いてある状態のほうが、後から読んで分かる。** 走る日を数えるときは和集合を取る。

```
│ 運行なしの期間                                    │
│   2026-08-06 〜 2026-09-30  夏季休業      [削除]  │
│   2026-12-26 〜 2027-01-05  年末年始      [削除]  │
│                                    [範囲を足す]   │
└────────────────────────────────────────────────┘
```

**カレンダーの上をドラッグして範囲を選ぶ。** 選び終えると下の一覧に行が増える。一覧からも直接打てる。

**曜日で外れる日と、範囲で外れる日を描き分ける。** どちらも「走らない日」だが、**直し方が違う**——前者は曜日のチェックを、後者は範囲を触ることになる。同じ見た目にすると、消せない日をクリックし続けることになる。

**1 日だけを消すときも範囲で表す**（`from` と `to` が同じ日）。**種類を 2 つに増やさない。**

#### 4.5.1 履歴に載せる

カレンダーの変更は**取り消せる**（仕様書 §6.7）。範囲の追加・削除・曜日の変更は、それぞれ履歴の 1 段とする。

**ドラッグで選んでいる最中は積まない。** 積むのは指を離したときの 1 回である。積み方を誤ると、範囲を 1 つ引くのに 30 回の取り消しが要る。

#### 4.5.2 月の送り

**有効期間の外へは送れない。** `startDate` の前月と `endDate` の翌月で止める。**送り続けられると、自分がどこを見ているのか分からなくなる。**

### 4.6 GTFS への写し方

| 持っているもの | GTFS |
| --- | --- |
| `startDate` / `endDate` | `calendar.txt` の `start_date` / `end_date` |
| `weekdays` | `calendar.txt` の `monday`〜`sunday`（走る曜日を `1`、他を `0`） |
| `closedRanges` を 1 日ずつ展開したもの | `calendar_dates.txt` の `exception_type: 2`（運休） |

**`exception_type: 1`（臨時運行）は出さない。** 持っていないためである（[§4.1](#41-日の種類は-2-つしかない)、[§4.7](#47-土曜に走る日は無いq-17)）。

**展開するときに、曜日で既に外れている日は出さない。** 夏季休業の中の日曜を `exception_type: 2` として出しても意味は変わらないが、**`calendar_dates.txt` の行数が 3 倍近くになる。** 読む側が「なぜこの日が 2 回外れているのか」を確かめる羽目になる。

### 4.7 土曜に走る日は無い（Q-17）

**振替授業であっても、このバスは土曜に走らない**（2026-08-07 確認）。

**よって [§4.3](#43-曜日は範囲で持たない) の 2 段で完結する。** 「運行あり」の例外日を表す手立ては要らず、`exception_type: 1` も出さない。

> **決めた内容を残しておく。** 初版では、走る日があった場合に取り得る道を 3 つ挙げていた（運行する範囲も選べるようにする / 走る曜日に土を入れて土曜を範囲で埋める / 表せないままにする）。**走らないと分かったため、どれも要らなくなった。**
>
> 同じ問いが将来また立つとすれば、それは**運行の実態が変わったとき**である。そのときは 1 つめ（運行する範囲も選べるようにする）から検討する——2 つめは §4.3 で避けたはずの形に戻り、3 つめは間違った GTFS を出す。

## 5. 一斉出力（#192, #193, #194, #196）

### 5.1 ボタンは 1 つ

**メニュー**: `ファイル > 書き出し…`

**形式を選ばせない。** 押すと保存先を尋ね、すべてを書き出す。

理由は 2 つある。

1. **選ばせるほど、選び忘れが起きる。** ダイヤグラムだけ出して配ったあとに「箱ダイヤも要る」と言われる。全部出るなら、要るものは必ず入っている
2. **出す作業は 1 回で終わる。** 5 つの形式に 5 回の保存先指定を求めると、出すこと自体が面倒になり、**古いまま配られたファイルが残る**

### 5.2 出るもの

| 中身 | 形式 | issue |
| --- | --- | --- |
| ダイヤグラム | PNG | #192 |
| ダイヤグラム | PDF | #192 |
| 箱ダイヤ（全運用を 1 枚に） | PDF | #194 |
| 箱ダイヤ（運用ごとに 1 枚） | PDF | #193 |
| 時刻表（豊中方面） | CSV | #196 |
| 時刻表（吹田方面） | CSV | #196 |

**GTFS は含めない**（[§5.7](#57-gtfs-を含めない)）。

**編集中のダイヤ 1 つだけを出す。** プロジェクトに複数のダイヤがあっても、出るのは今開いているものである。**全部を出すと、案として置いてあるだけのダイヤが配布物に混ざる。**

### 5.3 1 つの zip にまとめる

```
2026年度授業期間ダイヤ_20260807.zip
├── ダイヤグラム.png
├── ダイヤグラム.pdf
├── 箱ダイヤ_全体.pdf
├── 箱ダイヤ_運用A.pdf
├── 箱ダイヤ_運用B.pdf
├── 時刻表_豊中方面.csv
└── 時刻表_吹田方面.csv
```

**zip の名前は「文書名_日付」とする。** 文書名は文書情報（仕様書 §6.4）のものを使い、無ければファイル名を使う。**日付を入れるのは、配った先で新旧が並ぶため**である。中身を開かずに、どちらが新しいかが分かる。

**理由は Web 版である。** ブラウザにはフォルダへ書き込む手立てが無く（`PlatformAdapter` が持っているのはダウンロードだけ。仕様書 §10.4）、8 つのファイルを出せば 8 回のダウンロードになる。**zip にすれば、デスクトップ版と Web 版が同じ 1 つの道を通る。**

デスクトップ版だけフォルダに直接書く形も採れるが、**環境で振る舞いが変わると、片方でしか起きない不具合が生まれる。**

**全部を作り終えてから書く。** 途中で失敗したときに、半分だけ入った zip を残さない。これはファイル保存が既にアトミック書き込みで行われていること（`src-tauri/src/atomic.rs`）と同じ考え方である。

**圧縮しない（store）。** 中身の大半は PNG と PDF であり、**どちらも既に圧縮されている。** 再度縮めても数 % しか減らず、そのために圧縮の実装を持ち込む理由が無い。CSV だけは縮むが、量が小さい。

### 5.4 ダイヤグラム（#192）

#### 5.4.1 新しい描画コードを書かない

v1.0 の実装計画書 §3.5 は、まさにこのために描画関数を `(ctx, scene, viewport)` の 3 引数にしてある。

```typescript
// 画面用
drawDiagram(screenCtx, scene, currentViewport);

// 書き出し用 — 同じ関数、引数が違うだけ
drawDiagram(offscreenCtx, scene, { startTime: t(5,0), endTime: t(24,0), pxPerMinute: 8, ... });
```

| 項目 | 決め |
| --- | --- |
| 時間範囲 | **全便が入る範囲**。画面の視野ではない。書き出したものを見る人に「画面をどこまでスクロールしていたか」は関係が無い |
| 解像度 | **A4 横 300dpi 相当**（3508 × 2480px）。紙に載せることを前提とする |
| 表示設定 | **画面のものをそのまま使う**（色・線種・フィルタ）。見えているものが出る |
| 配色 | **明るいほうで固定する。** 画面が暗い配色でも、紙に黒地は刷らない |

#### 5.4.2 PDF はベクタで描く（Q-20、2026-08-07 改め）

> **決め: PDF の文字は字として入れる。ラスタ化しない。日本語フォントを同梱する。**

**なぜラスタでは足りないか。**

| | 画像を貼った PDF | 字が字として入った PDF |
| --- | --- | --- |
| 拡大 | ぼやける | **どこまでも滲まない** |
| 停留所名の検索 | **できない** | できる |
| 文字の選択・コピー | **できない** | できる |
| 大きさ | 300dpi の画像ぶん | **線と字だけ** |

**受け取った人が停留所名で検索できることに意味がある。** 掲示するだけなら画像で足りるが、PDF は配って読まれるものであり、**読む側の道具（検索・選択）を潰さない。**

##### フォントを同梱する

PDF が何も埋めずに使える書体（標準 14 書体）に日本語は無い。**フォントを埋めない限り、字は出ないか化ける。**

**本ソフトはこれまでフォントを 1 つも同梱していない**（画面の指定は `system-ui` から始まり、環境のものを使う。`src/app/styles.css`）。v2 で初めて 1 つ持つ。

| もの | 大きさ（実測） |
| --- | --- |
| Noto Sans JP Regular（1 ウェイト） | **約 3.9MB**（woff2 全域の合計。TTF ではおよそ 5.7MB） |
| `pdf-lib` | 523KB → **206KB**（gzip 後） |
| `@pdf-lib/fontkit`（サブセット化に要る） | 714KB → **329KB**（gzip 後） |
| （参考）現在の Web 版の初回ロード | **45KB**（gzip 後） |
| （参考）目標（仕様書 §9.1） | **初回ロード** 1MB 以内 |

##### 初回ロードには載せない

**§9.1 が言っているのは初回ロードである。** 書き出しを押すまで読まないものは、そこに入らない。

```typescript
// 書き出しが押されて初めて読む。Vite が別のチャンクに切る。
const { PDFDocument } = await import('pdf-lib');
const font = await fetch(fontUrl).then((r) => r.arrayBuffer());
```

**初回ロードは 45KB のままである。** 一度読めばブラウザが持つため、2 回目以降の書き出しでは落ちてこない。

**版数 2.1 で「Web 版とデスクトップ版で作りを分けることになる」と書いたのは誤りだった。** 分ける必要は無い——**遅延して読むという 1 つの道を、両方が通る。** デスクトップ版では同梱リソースから読み（`route.json` と同じ仕組み）、Web 版では資産として落とす。

##### 出来上がる PDF は小さい

**埋めるのは使った字だけである。** `pdf-lib` は `embedFont(bytes, { subset: true })` で、その文書に出てくる字だけを取り出して埋める。停留所名・便番号・運用番号を合わせても数百字であり、**PDF に入るフォントは数十 KB に収まる。**

**同梱するフォントが 3.9MB あることと、出来上がる PDF が大きいことは別である。**

##### 描画関数は書き直さない

**`DrawContext` を満たす PDF 用の実装を 1 つ書く。**

```typescript
// 画面用（canvas）
drawDiagram(screenCtx, scene, viewport);

// PNG 用（オフスクリーン canvas）
drawDiagram(offscreenCtx, scene, exportViewport);

// PDF 用 — 同じ関数。器だけが違う
drawDiagram(new PdfDrawContext(page, font), scene, exportViewport);
```

`DrawContext` は 14 のメソッドしか持たない狭い型である（`src/features/diagram/drawContext.ts`）。**そのすべてが PDF の描画命令に写せる。**

| `DrawContext` | PDF |
| --- | --- |
| `moveTo` / `lineTo` / `stroke` | `m` / `l` / `S` |
| `arc` / `fill` | ベジエ 4 本 / `f` |
| `fillText` | `Tj`（**埋めたフォントで**） |
| `rect` / `clip` | `re` / `W n` |
| `setLineDash` | `d` |
| `save` / `restore` | `q` / `Q` |
| `fillStyle` / `strokeStyle` | `rg` / `RG` |

**PNG と PDF が同じ関数から出るため、絵が食い違わない。** 片方だけを直して見た目がずれることが、構造上起きない。

**箱ダイヤも同じ器を通る**（[§5.5.5](#555-ダイヤグラムと同じ道を通る)）。

##### 確かめること

- [ ] **Web 版の初回ロードが 45KB のまま**であること（フォントもライブラリも別チャンクに出ていること）
- [ ] **デスクトップ版のバイナリが 30MB 以内**であること（`scripts/check-bundle-size.mjs`。フォントで約 5.7MB 増える）
- [ ] 出来上がる PDF で、停留所名を検索できること
- [ ] **OFL-1.1 の本文を配布物に同梱していること**（[§5.4.3](#543-フォントのライセンス)）

#### 5.4.3 フォントのライセンス

| 項目 | 内容 |
| --- | --- |
| 書体 | **Noto Sans JP Regular** |
| ライセンス | **SIL Open Font License 1.1**（OFL-1.1） |
| 置き場所 | リポジトリ直下に置き、デスクトップ版は `bundle.resources` で同梱する |

**OFL は同梱と再配布を認めている。** 条件は**ライセンス本文を一緒に配ること**であり、書体そのものを単体で売らないことである。どちらも本ソフトの配り方に反しない。

**本ソフト自体を再配布禁止とすること（仕様書 v1.1 §12）と両立する。** 自分の著作物をどう配るかは自分の権利、同梱した他人の著作物の条件を守るのは他人への義務であり、**別のことである。** これは依存パッケージ（React・Zod ほか）の表示義務と同じ扱いになる。

**画面には使わない。** 画面は今までどおり環境のフォントを使う（`system-ui`）。**同梱したフォントを画面にも使うと、初回ロードに 3.9MB が乗る。** 使うのは PDF に埋めるときだけである。

### 5.5 箱ダイヤ（#193, #194）

> **版数 2.0 の記述は誤りだった。** 「箱ダイヤとは時刻表を紙に組み直した表である」と書いたが、**箱ダイヤは表ではない。** 表として扱うと、下に述べる情報がひとつも出ない図が出来上がる。

#### 5.5.1 箱ダイヤは仕業の絵である

**表すのは、車 1 台が 1 日をどう過ごすかである。**

| 読み取れること | |
| --- | --- |
| どの時間帯に、どの区間を走っているか | 走っていない時間がそのまま隙間に出る |
| どこで休憩しているか | 折返し時分と営業所待機（仕様書 §5.8） |
| いつ出庫し、いつ入庫するか | 車庫への出入り |

**まとめて「仕業」——業務のひとまとまり——を表す。** ダイヤグラム（仕様書 §6.2）が**便**を主役に置いて全便を重ねるのに対し、箱ダイヤは**車**を主役に置く。同じデータの別の見方であり、どちらか一方では足りない。

#### 5.5.2 形

> **横軸は時刻ではない。停留所である**（2026-08-07 訂正。版数 2.1 の図は誤り）。

**横軸に停留所を取る。左が豊中、真ん中が箕面、右が吹田。** ダイヤグラム（仕様書 §6.2）の縦軸に並ぶものが、ここでは横に寝る。

**便は水平の棒**として描く。棒の左端と右端がその便の始発・終着の停留所であり、**棒はどこまで走るかを表す。**

**方向で段が変わり、折り返しを縦線が繋ぐ。** 便が 1 本進むごとに段が 1 つ下りる。

```
        豊中      箕面      吹田
         │        │        │
運用A    ├─────────────────┤        ← 1 便目（豊中 → 吹田）
         │                 │
         │        ┌────────┤        ← 2 便目（吹田 → 箕面）
         │        │
         ├────────┘                 ← 3 便目（箕面 → 豊中）
         │
```

**往復すると閉じて四角形になり、途中で折り返せば「コ」の字になる。** これが「箱」と呼ばれる所以である。

**形が意味を持っている。** 四角が横に広ければ端から端まで走っており、狭ければ区間便である。**表に組み直すと、この形が消える。**

##### 段の間隔は一定とする（Q-24、2026-08-07 決定）

**折返しが長い便ほど深く下ろす、ということはしない。** 段は 1 便につき 1 つであり、間隔はどこでも同じである。

**縦は時間ではなく、便の順序である。** そう決めた結果は 2 つある。

| | |
| --- | --- |
| **図の高さが便の数だけで決まる** | 運用を並べたときに段が揃う。**何便の運用かが、高さを見るだけで比べられる** |
| **休憩の長さは形に出ない** | 30 分の折返しと 3 時間の営業所待機が同じ間隔で描かれる |

**後者は時刻を字で添えて補う。** 形で表せないものを形で表そうとすると、**便の多い運用ほど縦に伸び、運用どうしを見比べられなくなる**（[§5.5.6](#556-全体と運用系統別) の「全体」が成り立たなくなる）。**縦の意味を 1 つに保つ**——段は順序であって、時間ではない。

#### 5.5.3 回送はマークで表す

**出庫と入庫は棒にしない。**

| | 描き方 |
| --- | --- |
| 出庫 | **最初の便の始発停留所の上**にマークを付ける |
| 入庫 | **最後の便の終着停留所の下**にマークを付ける |

**回送に段を割かない。** 回送も棒で描くと、車庫（横軸のどこにも無い）まで棒を伸ばすことになり、**横軸が停留所であるという決めが崩れる。** 出入庫は「ここで始まり、ここで終わる」という印であって、走った区間を読むものではない。

**版数 2.1 で「回送も出す」と書いたことは変わらない。** 出すが、**出し方が棒ではなくマークである。**

#### 5.5.4 描くのに要る値は既に導出されている

**新しい導出を書かない。** `deriveBlocks`（`src/domain/block/derive.ts`）が既に、箱ダイヤが必要とするものをすべて出している。

| 導出済みのもの | 箱ダイヤでの役割 |
| --- | --- |
| `Block.trips`（始発時刻順） | **段の並び。** 上から順に 1 段ずつ下りる |
| `BlockTrip.originStopId` / `terminalStopId` | **棒の左端と右端**（横軸が停留所であるため） |
| `BlockTrip.originTime` / `terminalTime` | 棒に添える時刻 |
| `BlockTrip.isDeadhead` | **回送を棒にしない**ための判定（[§5.5.3](#553-回送はマークで表す)） |
| `BlockTrip.layoverMinutes` | 折返しの待ち。**段の間隔には使わない**（[§5.5.2](#552-形)）。添える字に使う |
| `Block.pullOutTime` / `pullInTime` | 出庫・入庫のマーク |
| `Block.standbys` | 営業所待機 |

**横軸の位置は `Stop.axisPosition` から取る**（仕様書 §5.3）。ダイヤグラムの縦軸が既にこの値を使っており、**箱ダイヤはそれを横に寝かせるだけである。** 停留所の間隔が 2 つの図で食い違わない。

**運用の色も既にある**（`src/domain/block/colors.ts`、仕様書 §5.8）。**画面と同じ色で出る。**

#### 5.5.5 ダイヤグラムと同じ道を通る

**箱ダイヤは絵であるから、`DrawContext` で描く**（`src/features/diagram/drawContext.ts`）。

```typescript
drawBlockChart(ctx, blocks, viewport);   // ダイヤグラムと同じ 3 引数の形
```

**[§5.4.2](#542-pdf-はベクタで描くq-20-2026-08-07-改め) の決めがそのまま効く。** `PdfDrawContext` を渡せば、**箱ダイヤの停留所名も字として PDF に入る。** ダイヤグラムのために書く器を、箱ダイヤがそのまま使う。

**描画関数そのものは新しく書く。** ダイヤグラムは横軸が時刻・縦軸が停留所でスジが斜めに走る。箱ダイヤは**横軸が停留所・縦に段が下り、便は水平の棒**である。**軸が入れ替わっており、描き方を共有できない。** 共有するのは器（`DrawContext`・オフスクリーン canvas・`PdfDrawContext`）だけである。

#### 5.5.6 全体と運用系統別

| | 全体（#194） | 運用系統別（#193） |
| --- | --- | --- |
| 何を出すか | **全運用を並べた 1 枚** | **運用 1 つにつき 1 枚** |
| 何枚出るか | 1 つ | 運用の数だけ |
| 用途 | 車が何台要るか、運用どうしを見比べる | 1 台の 1 日を細かく追う |
| 出入庫のマーク | **出す** | **出す** |

**どちらも出入庫を出す**（版数 2.0 の「全体では回送を出さない」を取り消す）。**出入庫は仕業の一部である。** 抜くと、車がどこから現れてどこへ消えるのかが分からない図になり、**箱ダイヤであることをやめる。**

**方向で分けない。** 1 つの運用は両方向を走るのであり、方向で切ると**同じ車の 1 日が 2 枚に割れる。** それ以前に、**方向は横軸の左右で読める**（[§5.5.2](#552-形)）。これは時刻表 CSV（[§5.6](#56-csv196)）が方向で分かれるのとは逆であり、理由も逆である——**あちらは停留所ごとの時刻を読むもの、こちらは車の動きを追うものである。**

#### 5.5.7 決まっていないこと

| | 内容 |
| --- | --- |
| **Q-21** | **版面。** 用紙の大きさ・向き・**1 枚に何段まで載せるか。** 横軸は停留所であり幅は決まっているため、**溢れるのは縦である** |

**版数 2.1 では「1 枚に何時間ぶんを載せるか」と書いていたが、横軸を時刻だと思っていたことによる誤りである。** 横軸が停留所である以上、**横は決して溢れない。** 切れ目は段（縦）に入る。

### 5.6 CSV（#196）

**合わせる相手は無い**（2026-08-07 確認。Q-22）。#195 が言う「別プログラム」は存在しなかった。

> **決め: 時刻表タブに出ているものを、そのまま CSV にする。豊中方面と吹田方面で 2 つのファイルに分ける。**

**画面の写しとする。** 行も列も並びも、時刻表タブで見えているものと同じにする。**別の並びを発明すると、画面と突き合わせられなくなる**——CSV を開いた人が確かめたいのは、たいてい「画面と同じか」である。

#### 5.6.1 行の並び

時刻表タブと同じ順に並べる（`TimetableGrid.tsx`）。

| 行 | 内容 |
| --- | --- |
| 便番号 | 導出値（仕様書 §6.1.6） |
| パターン | `S1` などの記号 |
| 運用 | 運用番号 |
| 前運用 | 出区、または前の便の便番号 |
| （停留所ごとに 1 行） | 時刻。**方向によって並びが逆になる**（T-48。画面と同じ） |
| 次運用 | 入区、または次の便の便番号 |

**1 列目は行の名前**（`便番号` / `パターン` / 停留所の短縮名 など）とする。画面の左端の列がそのまま 1 列目になる。

**回送便は列にならない。** 前運用・次運用の行に畳んである（仕様書 §6.1.7）ためであり、**画面がそうしている以上、写しもそうなる。**

#### 5.6.2 升目の中身

| 画面 | CSV |
| --- | --- |
| 時刻 | `7:40` のまま。**24 時を超える表記もそのまま**（`25:30`。仕様書 §2.1） |
| 経由しない停留所 | 空欄 |
| 時刻が未入力 | 空欄 |

**経由しないことと未入力を区別しない。** どちらも「その便のその停留所に時刻が無い」であり、**受け取る側にとって違いが無い。** 区別する記号を置くと、その記号の意味を説明する必要が生まれる。

#### 5.6.3 文字コードと改行

| 項目 | 決め | 理由 |
| --- | --- | --- |
| 文字コード | **UTF-8（BOM 付き）** | **BOM を付けないと Excel が文字化けさせる。** 停留所名が読めなければ CSV の意味が無い |
| 改行 | CRLF | RFC 4180 |
| 引用符 | 値に `,` `"` 改行が含まれるときだけ `"` で囲む | 同上 |

**`.uodia` は BOM なしと決めてある**（仕様書 §7.1）。**逆にするのは、読む相手が違うからである**——`.uodia` を読むのはこのアプリ、CSV を読むのは表計算ソフトと人である。

> **表計算が `25:30` を時刻として解釈し、`1:30` に変えてしまう場合がある。** これは受け取る側の設定の問題であり、CSV の側でできることは無い（`="25:30"` のような書き方は Excel 以外で壊れる）。**24 時を超える表記を使うことは v1.0 からの決めであり、変えない。**

### 5.7 GTFS を含めない

**一斉出力に GTFS を入れると、出力ボタン全体が Q-12 待ちになる。** 画像も箱ダイヤも CSV も、要件は揃っている。**揃っているものを、揃っていないものと同じ包みに入れない**——v1.1 が GTFS を切り離した判断（§7.4）と同じである。

GTFS は GTFS 画面の「書き出し」タブから出す（[§3.2](#32-構成)）。

### 5.8 失敗したとき

| 起きること | どうするか |
| --- | --- |
| 便が 1 つも無い | **書き出さない。** 「便がありません」と伝える |
| 描画に失敗した | **何も書かない。** どこで失敗したかを伝える |
| 保存先が選ばれなかった | 何もしない（取り消し） |
| 書き込みに失敗した | **元のファイルを壊さない**（アトミック書き込み。仕様書 §10.3） |

**半分だけ入った zip を残さない**（[§5.3](#53-1-つの-zip-にまとめる)）。

### 5.9 待ち時間

**300dpi の画像を 4 枚以上作る。** 画面の描画（T-40 で実測済み）とは桁が違う。

| 決め | 内容 |
| --- | --- |
| 進み具合を出す | 「箱ダイヤを作っています（3/9）」のように、何を作っているかを出す。**枚数は運用の数で変わる**（[§5.5.6](#556-全体と運用系統別)） |
| 画面を止めない | 作っているあいだも窓は動く |
| 目標 | **10 秒以内**（100 便・運用 5 つ = 9 ファイル） |
