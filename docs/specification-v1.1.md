## 1. 本書の位置づけ

**本書は[仕様書](specification.md)を置き換えない。** v1.0 の仕様書は「確定」であり、そこに書かれた決めと理由はそのまま生きている。本書はその上に**足すもの・改めるもの**だけを書く。

節の見出しには、本体のどの節に対応するかを併記する。実装が済んだ項目は本体へ畳み込み、本書からは落とす。

**本書はまだ確定していない。** ただし 2026-08-04 の判断で、**やるかどうかを決める必要のあった 3 件は片付いた**——アンカーの色付けは廃止し（[§5.1](#51-アンカーの色付けを廃止する164)）、未保存の問いは選択肢を「保存する / 保存しない / キャンセル」に改め（[§3.3](#33-未保存の変更を尋ねる文言168)）、**GTFS 書き出しは v1.1 から外して別の仕様書を起こす**（[§7.4](#74-本書での扱い2026-08-04-決定)）。

残る未確定は**数値と外部の事実だけ**である（区間距離の実測値・既定の定員・既存 GTFS の形式）。いずれも実装を止めない。[§10](#10-未確定事項) にまとめる。

#### 3.1.1 `publisher` は表示名だけの値ではない（2026-08-05 決定）

**`publisher` を変えると、Windows では既に入れた版とは別物として入る。**

Tauri の NSIS インストーラは既定のインストール先を `%LOCALAPPDATA%\<publisher>\<product>` に取り、アンインストール情報のレジストリキーもここから作る。`再履同好会` → `再履バス同好会` の変更は、**インストール先とレジストリキーの両方を変える。**

| 起きること | 内容 |
| --- | --- |
| 新しい場所へ入る | `%LOCALAPPDATA%\再履バス同好会\UoDia` |
| **旧版が残る** | `%LOCALAPPDATA%\再履同好会\UoDia` は消えない。「プログラムの追加と削除」に 2 つ並ぶ |
| 上書き更新にならない | インストーラから見て別の製品であり、旧版を認識しない |

**決め: `publisher` を変える。旧版は入れ直してもらう。**

v1.0.0 は**下書きのリリース**として存在し（README の「配布物」参照）、関係者は取得できる状態にある。入れた人がいることを前提に、次の扱いとする。

| 決め | 理由 |
| --- | --- |
| **`publisher` を `再履バス同好会` に変える** | 表示名の誤りを残さない。**据え置くと、インストーラのプロパティと画面の表示が食い違ったままになる** |
| **v1.1 のリリースノートに「旧版を削除してから入れる」と書く** | 黙って変えると、2 つ並んだうちどちらが新しいのかを利用者が判断することになる。**手間を掛けてもらう以上、掛かることを先に伝える** |
| 旧版を消す仕組みは作らない | インストーラに旧キーの掃除を書かせると、**その掃除の正しさを確かめる手立てが要る。** 入れている人数が数えられる規模であり、手で消してもらうほうが確かである |
| macOS・Linux では入れ替えの問題にならない | `.app` は差し替え、`.deb` / `.rpm` はパッケージ名（`uo-dia`）で同一性が決まる。**ただし表記は別の場所から来る**——[§3.1.2](#312-deb-の-maintainer-は-publisher-から来ない2026-08-05) |

#### 3.1.2 `.deb` の `Maintainer` は `publisher` から来ない（2026-08-05）

**`tauri.conf.json` を直しただけでは、Linux の配布物の表記は変わらなかった。**

`publisher` を変えたあとに CI が作った配布物を実際に開いて確かめた結果:

```
$ dpkg-deb -f UoDia_1.0.0_amd64.deb Package Maintainer
Package: uo-dia
Maintainer: sairidoukoukai      ← 再履バス同好会 ではない
```

**`Maintainer` は `Cargo.toml` の `authors` から作られ、`bundle.publisher` より優先される。** `.rpm` の `Packager` も同じ経路である。

| 決め | 理由 |
| --- | --- |
| `src-tauri/Cargo.toml` の `authors` を `再履バス同好会` にする | **表記を直す場所が 2 つある。** 片方だけ直すと、画面とインストーラは正しいのに配布物の中身だけ古い名前が残る |
| `Cargo.toml` に**理由をコメントで残す** | `authors` が配布物のどこに出るかは、書いてないと次に見た人には分からない。**ここを直す理由が消えると、次の整理で元に戻される** |

**設定を読むだけでは分からなかった。** `bundle.publisher` を直せば足りるはずだと考えていたが、実際に作った `.deb` を開くまで気づけなかった。**配布物にしか現れない値は、配布物を見て確かめる。**

### 3.2 「後運用」→「次運用」（#159）

**対応する本体の節: [§6.1.7](specification.md)**

時刻表の上端・下端に置いた出入区の欄（仕様書 §6.1.7）のうち、**下端の呼び名を「後運用」から「次運用」に改める。**

| 位置 | 現在 | 改める先 |
| --- | --- | --- |
| 表の上端 | 前運用 | **前運用**（変えない） |
| 表の下端 | 後運用 | **次運用** |

**なぜ「後」ではいけないのか。** 「後」は時間的な後（あと）とも、順序上の後ろ（うしろ）とも読める。運用の話をしているときに「後」と書くと、**「あとで走る便」なのか「この便の後ろに繋がっている便」なのか**が字面から決まらない。「次」は順序の話しかしていない。

**「前運用」は変えない。** 「前」に同じ曖昧さが無いわけではないが、「次」の対として自然に読めるのは「前」である。「先運用」は先（さき）が未来と過去の両方を指すため、直すつもりで悪くする。

**直す場所は文字列だけではない。** 画面に出る文字（`title`）のほか、支援技術に読ませる名前（`aria-label`）にも同じ語が入っている。

| 種別 | 場所 |
| --- | --- |
| 見出しの文字 | [src/features/timetable/TimetableGrid.tsx:498](src/features/timetable/TimetableGrid.tsx#L498) |
| `aria-label` | [src/features/timetable/TimetableGrid.tsx](src/features/timetable/TimetableGrid.tsx)（`〜の後運用`） |
| コメント・型名 | `src/features/timetable/model.ts` ほか |
| テスト | `TimetableGrid.test.tsx` / `Timetable.test.tsx` |

**コード上の識別子（`before` / `after` 等）は改名の対象としない。** 英語の識別子は日本語の呼称と 1 対 1 で対応しておらず、`after` を `next` に直しても読み手が得るものが無い。**直すのは利用者が読む文字である。**

### 3.3 未保存の変更を尋ねる文言（#168）

**対応する本体の節: [§6.8](specification.md)**

issue の求めるところは次のとおり。

| 現在 | 改める先 |
| --- | --- |
| 保存して続ける | 保存して終了 |
| 破棄して続ける | 破棄して終了 |
| やめる | キャンセル |

**「続ける」が何を指すのか分からない、という指摘は正しい。** 保存したあと何が起きるのかを言っていないため、押す前には分からない。

#### 3.3.1 ただし、この問いは終了のときだけ出るのではない

**同じ問いを 4 か所から出している。** [src/features/file/fileService.ts:105](src/features/file/fileService.ts#L105) の `ensureSaved()` を呼ぶのは次の 4 つである。

| 呼び出し元 | 未保存を捨てたあと何が起きるか |
| --- | --- |
| `newProject()`（[fileService.ts:149](src/features/file/fileService.ts#L149)） | **新しいプロジェクトを作る** |
| `open()`（[fileService.ts:166](src/features/file/fileService.ts#L166)） | **別のファイルを開く** |
| `openRecent()`（[fileService.ts:181](src/features/file/fileService.ts#L181)） | **最近使ったファイルを開く** |
| `confirmClose()`（[fileService.ts:202](src/features/file/fileService.ts#L202)） | **アプリを終了する** |

**そのまま「保存して終了」にすると、4 つのうち 3 つで嘘になる。** 「ファイルを開く」を押して「保存して終了」と出たら、押した人は終了すると思う。押しても終了しないなら、次からその表示は信じられなくなる。

#### 3.3.2 決め: このあと何が起きるかを言わない（2026-08-04）

**選択肢から「続ける」も「終了」も落とし、保存するかどうかだけを問う。**

| 現在 | 改める先 |
| --- | --- |
| 保存して続ける | **保存する** |
| 破棄して続ける | **保存しない** |
| やめる | **キャンセル** |

**このあと何が起きるかを選択肢に書かないことで、4 つの呼び出し元すべてで正しくなる。** 「保存する」は新規作成でも終了でも同じだけ正しい。§3.3.1 の食い違いは、文言が**問いの範囲を超えたことを言おうとして**生まれていた。

| 決め | 理由 |
| --- | --- |
| **問うているのは保存の可否だけである** | この問いが決めるのは「保存するか」の 1 点であり、そのあと何をするかは呼び出し元が既に決めている。**問いが決めていないことを選択肢に書かない** |
| 「破棄して続ける」→「**保存しない**」 | 「破棄」は編集内容を捨てる操作の名前に聞こえる。実際にはファイルへ書かないだけであり、選ばなかった側の言い方として「保存しない」が正確である |
| 「やめる」→「**キャンセル**」 | 「やめる」は**編集をやめる**とも読める。取り消しの意味で最も広く通じるのは「キャンセル」である |
| **3 択のままとする** | 仕様書 §6.8 の判断を引き継ぐ。2 択にすると、続ける気が無いときにも保存か破棄かを選ばされる |
| **`DiscardIntent` は導入しない** | 呼び出し元ごとに文言を変える必要が無くなった。型も 4 か所の呼び出しも変わらず、**直すのは文字列 3 つだけ**になる |
| `DialogAnswer` は変えない | 返る値は `save` / `discard` / `cancel` のまま。`discard` という識別子は「保存しない」を指し続ける——**画面の言葉と内部の名前は別物でよい** |

**本文は「このあと何が起きるか」を担う。** 選択肢が言わなくなったぶん、本文に出す。

| 呼び出し元 | 本文 |
| --- | --- |
| `close` | `{ファイル名} の変更が保存されていません。保存せずに終了しますか。` |
| `open` / `openRecent` | `{ファイル名} の変更が保存されていません。保存せずに別のファイルを開きますか。` |
| `new` | `{ファイル名} の変更が保存されていません。保存せずに新規作成しますか。` |

**本文を分けるのに型は要らない。** `confirmDiscard` を呼ぶ 4 か所が本文の文字列を渡せば足りる。選択肢が固定されたことで、**分岐が「文言の表」から「引数 1 つ」に縮んだ。**

**本文は分ける**（2026-08-04 決定、Q-13）。選択肢が固定されたため、分けるのに型は要らない——`confirmDiscard` を呼ぶ 4 か所が本文の文字列を渡せば足りる。**分岐が「文言の表」から「引数 1 つ」に縮んだ。**

## 4. 取り返しのつかなく見える操作（#160）

**対応する本体の節: [§6.4.1](specification.md)（サイドパネル）**

ダイヤの削除（[src/features/sidebar/ServiceList.tsx](src/features/sidebar/ServiceList.tsx) の `✕` ボタン）は、押した瞬間に消える。**確認を挟む。**

### 4.1 事実の確認

**この操作は取り消せる。** 削除は `editProject('ダイヤの削除', …)` を通っており、履歴に載る。<kbd>Ctrl</kbd>+<kbd>Z</kbd> で戻る。

**それでも確認を挟む。** 理由は「戻せないから」ではない。

| 理由 | 説明 |
| --- | --- |
| **戻せることが画面から読めない** | 消えた直後に画面に残るのは、消えたという事実だけである。<kbd>Ctrl</kbd>+<kbd>Z</kbd> で戻ると知っている人にしか戻せない |
| **`✕` は隣に並んでいる** | 一覧の各行には、選ぶラジオボタン・名前の欄・便数・`✕` が並ぶ。名前を直そうとして端まで動かした指が届く場所にある |
| **失うものの大きさが行から読めない** | `120 便` と書いてあっても、押す前にそれを読むとはかぎらない |

### 4.2 決め

| 決め | 理由 |
| --- | --- |
| **便が 0 件でも尋ねる**（2026-08-05 改め） | 当初は「便が 1 つ以上あるときだけ」としたが、issue #160 のコメントの判断を採る——**「空なら出ない」は覚えられず、出ない場合があると確認そのものを信用しなくなる。** 確認は「押すと消える」ことを伝える仕掛けであり、失うものの大きさとは別に働く |
| 問いに**便数を出す** | 「本当に削除しますか」だけでは、失うものの大きさが分からない。`授業期間平日ダイヤ（120 便）を削除します。` と書く |
| **答えるまで何も動かさない** | 選択も編集中のダイヤも履歴も、「削除する」を押すまで触らない。**尋ねている最中に状態が動くと、キャンセルしても元に戻らない** |
| 背景を押すのもキャンセル | <kbd>Esc</kbd> と揃える。閉じ方が違えば結果も違う、という覚え方をさせない |
| 問いは**サイドパネルが持つ** | ファイル操作の問い（`features/file`）に相乗りすると、サイドパネルがファイル機能に依存する。`showModal()` は他をすべて不活性にするため、**問いが重ならないことはブラウザが保証する**——「一度に出す問いは 1 つ」を、こちらで数えて守る必要が無い |
| 既定の焦点は**キャンセル** | <kbd>Enter</kbd> を続けて押したときに消えない。未保存の問い（§3.3）で「保存」に焦点があるのとは逆であり、**理由も逆である**——あちらは押し続けても何も失わない |
| 最後の 1 つは今までどおり**消せない** | 仕様書 §6.4.1。ボタンが `disabled` である状態は変えない。確認を出してから断るのは、押せると見せておいて断ることになる |
| 問いは既存の仕掛けに載せる | `FileDialogHost` が持つ `<dialog>` と同じ形にする。**一度に出す問いは 1 つ**（`prompts.ts`）という決めを崩さない |
| **履歴には今までどおり載せる** | 確認を足したことは、取り消せなくてよい理由にはならない |

### 4.3 ここまでにする

**ダイヤの追加には確認を出さない。** 足すことで失われるものは無い。

**便の削除には確認を出さない**（<kbd>Delete</kbd>・列見出しからの削除）。ダイヤの削除と違い、便の削除は**作図の途中で何度も起きる操作**である。ここに確認を挟むと、1 便消すたびに問いが出る。issue が指しているのは「ボタン 1 発で消える」ことであり、便の削除はボタンではなく<kbd>Delete</kbd>と選択の組み合わせで起きる——**押しただけでは起きない。**

### 5.1 アンカーの色付けを廃止する（#164）

**対応する本体の節: [§6.1.1](specification.md)**

時刻表で、アンカーの升目だけ地色が変わる（[src/app/styles.css:1170](src/app/styles.css#L1170) `.timetable__cell--anchor`）。**廃止する**（2026-08-04 決定）。

#### 5.1.1 何を示していたのか

アンカーは**その便の時刻を決めている 1 点**である（仕様書 §5.6）。ほかの升目の時刻は、そこから区間表を引いて導かれる。色は「この升目が入力で、ほかは計算結果である」ことを示していた。

#### 5.1.2 なぜ要らないのか

| 理由 | 説明 |
| --- | --- |
| **どの升目に打っても同じように打てる** | アンカーでない升目に時刻を打つと、その升目がアンカーになる（仕様書 §6.1.2）。**利用者から見て、色の付いた升目と付いていない升目は同じように振る舞う。** 振る舞いが同じものを色で分けている |
| **アンカー 1 点方式はデータモデルの都合である** | 「便は停車パターンと基準時刻 1 点で決まる」は、便内の時刻矛盾を構造的に起こさないための設計（仕様書 §1.2）であって、利用者が意識すべき概念ではない |
| **色数を 1 つ使っている** | 時刻表には既に、選択・複製の行・方向タブがそれぞれの色を持つ。[§5.2](#52-エラーの色付け165) でエラーの色が加わると、**アンカーの黄色と重なる**。`.timetable__cell--selected.timetable__cell--anchor` という組み合わせ用の規則が既にあり、これが 3 つに増える |
| **意味を説明しない色である** | 凡例がどこにも無い。色の理由を知らない人には「なぜこの升目だけ黄色いのか」が最後まで分からない |

#### 5.1.3 廃止すると失われるもの

**区間所要時間を変えたとき、どの時刻が動かないかが読めなくなる。** 区間表を改定すると、各便の時刻はアンカーを基準に引き直される（仕様書 §6.5.1）。アンカーの升目だけは動かない。

**これは失ってよい。** 区間所要時間の改定は年に数えるほどの操作であり、時刻表を開いているあいだ常に色を出しておく理由にならない。改定の影響は設定ダイアログが「何便に効くか」として事前に出しており（仕様書 §6.5.1）、そこで確かめられる。

**なぜ印が無いのかは、コードにも残す。** `TimetableCell` の定義（`features/timetable/model.ts`）に、基準の位置を持たない理由を書く。**次に見た人が「なぜアンカーが見えないのか」で止まらないようにする**（#164 のコメントの受入条件）。

#### 5.1.4 決め

| 決め | 理由 |
| --- | --- |
| `.timetable__cell--anchor` を**消す** | 使い道が残らない |
| **`--color-anchor` は消さず、`--color-attention` に改める**（2026-08-05 訂正） | 当初は「消す」としたが、**この変数は非対応ブラウザの案内帯（`.notice`）でも使われていた。** 消せば案内帯の地色が失われる。#164 のコメントが「`styles.css:173` もアンカー由来か確認してから消す」と釘を刺していたとおりである。**役割を表す名前に付け替えることで、次に色が要ったときに意味の合わない名前で使い回されることも防ぐ** |
| **`TimetableCell.isAnchor` も落とす** | 読んでいたのは消したクラス 1 か所だけであり、残せば**何も読まない項目**になる。次に見た人が「何のためにあるのか」を調べることになる |
| `Trip.anchor` は**残す**（当然） | データモデルは何も変わらない。画面に出さなくなるだけである |
| **隠し設定で戻せるようにはしない** | 隠し設定（仕様書 §6.5.4）は路線の定義を触るためのものであり、見た目の好みを溜める場所ではない |
| **設定で戻せるようにもしない** | 消すと決めたものを設定で戻せるようにするのは、消していないのと同じである。**選択肢を残すと、[§5.2](#52-エラーの色付け165) の色との重なりが「設定次第で起きる」ことになり、確かめる組み合わせが倍になる** |

### 5.2 エラーの色付け（#165）

**対応する本体の節: [§6.6.1](specification.md)（検証パネル）・[§6.1.1](specification.md)（時刻表）**

**検証で指摘されている便を、時刻表の上で見分けられるようにする。**

#### 5.2.1 いま何が起きているか

検証の指摘は検証パネル（画面の下）にしか出ていない。時刻表を見ているあいだ、**どの列に問題があるのかは分からない。** パネルの項目を押せばその便へ飛べるが（仕様書 §6.6.1）、それは**一覧を読んでいるときの動線**であり、時刻表を読んでいるときの動線ではない。

#### 5.2.2 決め: 列見出しに印を付ける

| 決め | 理由 |
| --- | --- |
| **地色を変えるのはエラーだけ** | 情報（V-07 運用番号が空欄・V-08 時刻が未入力）は、白紙から作っているあいだほぼ全列に付く。**全部塗ると表が塗り絵になり、塗ってあることが情報でなくなる** |
| 警告・情報は**記号だけ**出す | 出さないのではない。エラー（`✕`）・警告（`!`）・情報（`i`）を列見出しに置く |
| 印を付けるのは**列見出し**であり、升目ではない | 指摘は便に対して出る。升目に塗ると「この時刻が悪い」と読めるが、悪いのは便の位置であって特定の停留所の時刻ではない |
| **色・記号・言葉の 3 つで示す** | 仕様書 §9.4 の決めをそのまま引く。印には `title` を付け、指摘の文言をそのまま出す |
| 2 件以上の指摘が付く便は、**最も重い 1 つ**で示す | 印を並べると列が広がる。列の幅を決めるのは時刻である（仕様書 v4.37） |

#### 5.2.3 2 便が絡む指摘は双方に付ける

**issue の核心はここである。** 前便との干渉は 2 便の関係であり、片方だけを塗ると「どちらが悪いのか」を探すことになる。

現在、2 便が絡む指摘でも `ValidationTarget` は**後の便しか指していない**。

| ID | 内容 | 現在の `target` |
| --- | --- | --- |
| V-01 | 前便の終着と次便の始発が不一致 | 次便のみ（[validate.ts:139](src/domain/validation/validate.ts#L139)） |
| V-02 | 折返し時分が負 | 次便のみ（[validate.ts:148](src/domain/validation/validate.ts#L148)） |
| V-03 | 運行時間帯の重複 | 後の便のみ（[validate.ts:177](src/domain/validation/validate.ts#L177)） |
| V-06 | 同方向の便間隔が極端 | 後の便のみ（[validate.ts:276](src/domain/validation/validate.ts#L276)） |

##### 決め: 型を変えず、**もう片方からも指摘を出す**（2026-08-04）

**`ValidationTarget` は今のまま（`tripId?: string`）とする。** 代わりに、2 便が絡む項目は**前から見た指摘と後ろから見た指摘の 2 件**を出す。

| ID | 前の便に出す | 後の便に出す |
| --- | --- | --- |
| V-01 | 次の便は {停留所} 発ですが、この便は {停留所} 着です | 前の便は {停留所} 着ですが、この便は {停留所} 発です |
| V-02 | 次の便がこの便の終着 {時刻} より前に発車します | 前の便の終着 {時刻} より前に発車します |
| V-03 | {時刻}〜{時刻} の便と運行時間帯が重複しています | （同じ文。相手の時間帯を出す） |
| V-06 | {停留所} で次の便との間隔が {N} 分しかありません | {停留所} で前の便との間隔が {N} 分しかありません |

| 決め | 理由 |
| --- | --- |
| **型を変えない** | 読み手（`ValidationPanel`・`jump.ts`）に手が入らない。**ジャンプの寄せ先を「2 つのうちどちらか」と決める必要も無い**——1 件が 1 便を指す関係が保たれる |
| **文面がその便の視点で書ける** | 型で 2 便を持つ形では、前の便の列に「前の便の終着より前に発車します」と出る。**その便は早発していないのに、その便の説明として読める。** 時刻表の色付けは列ごとに理由を示すため、視点の食い違いがそのまま出る |
| **件数が倍になることを受け入れる** | 1 つの破綻が 2 件として数えられる。仕様書 §6.6 が V-02 と V-03 の分担で退けた形だが、**あちらは「別の項目番号で 2 度並ぶ」であり、こちらは「同じ項目が両側から 1 度ずつ」である**。どちらの便を直せばよいかは、どちらの列から見ても分かる必要がある |
| 運用を指す指摘（V-05・V-09）は今までどおり `blockId` | その運用の便をすべて選ぶ挙動（仕様書 §6.6.1）は既にある。こちらは 2 便の関係ではない |

##### 件数が倍になることの代償を、重大度の見直しで受け止める

**倍になるのは V-01・V-02・V-03（エラー）と V-06（警告）である。** エラーが倍に見えることは、**そのまま時刻表の塗り面積が倍になる**ことでもある（[§5.2.2](#522-決め-列見出しに印を付ける) で地色を変えるのはエラーだけとしたため）。

**重大度の割り当てを見直す**（Q-14）。見直しの軸は 2 つある。

| 問い | 検討 |
| --- | --- |
| **どれをエラーのままにするか** | V-01〜V-04 はいずれも「実運行できない」に当たる（車が瞬間移動する・時間をさかのぼる・同時に 2 か所に居る・時刻が導出できない）。**重大度の定義に照らすかぎり、情報へ落とす理由は見つかっていない** |
| **地色を塗る条件を「エラー」と別に定義するか** | こちらのほうが効く。たとえば**運用の破綻（V-01〜V-03）だけを塗り、V-04 は記号のみ**とする。V-04 は 1 便で閉じており、隣の列を巻き込まない |

**この見直しは §5.2 の実装より先に決める。** 塗る条件を後から変えると、塗り方を作り直すことになる。

##### V-03 も両側から出す（2026-08-04 決定、Q-15）

**V-03 は 1 つ以上離れた便との重複を見る項目であり、重なりの組み合わせの数だけ増える。** 長い便 1 本に短い便が 2 本収まっていれば 4 件になる。それでも V-01・V-02 と揃える——**V-03 が大量に出る状態はダイヤが壊れているのであり、そのとき件数が多いのは正しい。**

##### 同じ便を 2 度指すことは起こらない

展開した回送便は保存されている便へ戻されるため（`sourceTripId`）、便とその出入区が対になれば同じ列を 2 度指すことになる。**その対が指摘されることはない。**

| 項目 | 出ない理由 |
| --- | --- |
| V-01 | 出入区は `createPullOut` / `createPullIn` が作る。接続する停留所は必ず一致する |
| V-02 | 出入区は 0 分折返しである（仕様書 §6.1.7） |
| V-03 | 出区と入区が重なるには、便の終着が始発より前になる必要がある |

**起こり得ない場合のために分岐を書かない。** 重複を畳む処理を置くと、到達しない道が 1 本増える。

#### 5.2.4 ダイヤグラムには出さない

**スジの色は変えない。** ダイヤグラムのスジは既に、パターンか運用のどちらかで着色されている（仕様書 §6.2.4）。ここへ検証の色を混ぜると、**着色モードが 3 つ目を持つか、色が二重に意味を持つか**のどちらかになる。前者は「エラーを見るために運用の色を捨てる」ことになり、後者は読めない。

エラーのある便へは検証パネルから飛べる。**時刻表とダイヤグラムの両方に同じ印を出す必要は無い。**

### 5.3 折返しの接続線（#167）

**対応する本体の節: [§6.2.2](specification.md)（描画要素）**

同一運用の連続する 2 便を、ダイヤグラム上で線で繋ぐ。

#### 5.3.1 いま何が読めないか

運用で着色すれば（仕様書 §6.2.4）、同じ運用の便は同じ色になる。**それでも、どの便がどの便に繋がるかは読めない。** 同じ色のスジが画面に何本もあり、折返しで時間が空くほど、繋がる相手が遠くなる。

#### 5.3.2 決め: 水平線で繋ぐ

**前便の終着点から、次便の始発点まで、水平に線を引く。**

```
軸位置
  0  豊中 ─╮                     ╭─
           ╰╮                  ╭╯
            ╰╮      接続線     ╭╯
 40  工学部  ╰──────────────────╯
             9:20            9:45
```

**結果として台形に見える。** 便のスジが下り、水平に留まり、また上る——issue が「台形」と呼んでいるのはこの形である。台形を描く仕掛けを別に持つのではなく、**留まっているあいだを正直に描くと台形になる。**

| 決め | 理由 |
| --- | --- |
| **曲線は採らない** | ダイヤグラムでは**線の傾きが移動の速さを表す**。意味の無い曲率を描くと、そこで速さが変わったように読める。折返しのあいだバスは動いていないのだから、傾きは 0 である |
| 引く条件は「**同一運用の連続する 2 便で、前便の終着停留所と次便の始発停留所が一致し、折返し時分が正**」 | 停留所が一致しないのは V-01（エラー）であり、繋がっていない。負なのは V-02（エラー）である。**破綻したダイヤに線を引いて繋がっているように見せない** |
| 折返し時分が **0 分なら引かない** | 長さ 0 の線は描いても見えない。出区・入区が 0 分折返しである（仕様書 §6.1.7）ため、ここを描こうとすると点だけが残る |
| 色は**前便の色**（2026-08-05 改め） | 当初は「運用の色（着色モードによらず）」としたが、実機で見て改めた。**接続線は前便の終着点から伸びる線であり、そこから続いているものとして読めるほうがよい。** 運用の色に決め打ちすると、パターンで着色しているときに前便のスジと違う色の線が生える。運用番号が空欄の便には**引かない**——繋ぐ相手が定義されていない |
| **実線で引く**（2026-08-05 改め） | 当初は破線としたが、停留所線・格子・回送のヒゲと刻みが混ざって読みにくかった。**見分けるのは太さと位置である**——ヒゲは停留所線の上から伸び、接続線は段のぶんだけ離れた場所を水平に走る |
| **掴めない** | 選択の単位は保存されている便である（仕様書 §6.3.1）。接続線は 2 便の関係であって、それ自体は便ではない。掴めるようにすると「どちらの便を選んだのか」が決まらない |
| 表示の切替をサイドパネルに置く | 便が増えると水平線も増える。**既定はオン**とし、切る道を用意する（回送の表示・非表示と同じ場所） |
| 表示範囲（7:00〜22:00）の外へは描かない | 格子・スジと同じ範囲に収める（仕様書 §6.2.2） |

#### 5.3.3 同じ停留所で複数の運用が留まるとき（2026-08-04）

**2 台以上が同じ停留所に同時に留まると、接続線は同じ高さに重なる。** 豊中学舎は `axisPosition: 0` であり、そこに留まる運用がいくつあっても線は 1 本の上に集まる。**重ねて描けば、最後に描いたものしか見えない。**

**決め: 重なる接続線は px でずらして積む。**

| 決め | 理由 |
| --- | --- |
| ずらす単位は **7px 固定**（拡大率によらない。2026-08-05 改め） | 回送のヒゲ（仕様書 v4.27）と同じ考え方である。**これは絵の記号の大きさであって、距離でも時間でもない。** 当初 4px としたが、停車点の丸（半径 3.5px）と線幅を跨いで離れないと、**何段あるのかも、どれが停留所線なのかも読めなかった** |
| ずらす向きは**軸の外側** | 軸位置が中点（20）以下なら上、大きければ下。**豊中（0）は上、工学部（40）は下へ積む。** 内側へ積むと、便のスジが走っている場所に線を重ねることになり、どちらも読みにくくなる。**外側に必要な場所は `AXIS_EDGE_MARGIN` を広げて確保する**（8px → 24px。3 段ぶん。#171 で入れた余白の幅は「そこに何が積まれるか」で決まる） |
| 段は**滞泊の開始時刻の昇順**に 1・2・3… と割り当てる | **0 段（停留所の線の上）は使わない**（2026-08-05 改め）——線そのものと重なって、どちらも読めない。1 台しか留まっていなくても 1 段ずらす。割り当てを運用番号順にしないのは、番号を打ち替えただけで絵が組み替わるのを避けるため |
| 重なりの判定は**時間帯が交わるかどうか**だけを見る | 同じ停留所の接続線どうしで、時間帯が 1 分も交わらないなら同じ段でよい。段を運用ごとに固定すると、**留まっていない時間まで段を占める** |

**停留所の点まで繋ぐ**（2026-08-05）。段のぶんだけ離した水平線だけを引くと、**便の端点と接続線のあいだが空いて、どの便から続いているのかが読めない。** 端点から斜めに上がり、水平に走り、また端点へ降りる——**これが台形である。** 斜めは段のずらし幅と同じだけ横に取るため 45 度になり、どの段でも同じ角度で降りる。滞泊が短くて幅が足りないときは半分ずつに詰め、水平部分が無くなっても三角形として繋がる。

**箕面学舎で 2 台が同時に留まることは無いものとして扱う**（2026-08-04 確認）。箕面は軸の途中（20）にあり、そこで積むと上下いずれの向きでも他の停留所の線を横切る。**起こらない前提を置くことで、途中の停留所を積む規則を持たずに済む。** 万一起きた場合は中点の規則により下へ積むが、**その状態は運用として想定されていない。**

#### 5.3.4 営業所へ帰る折返しには引かない

**入区して出区する（車庫へ帰って出直す）あいだには線を引かない。** 営業所には縦軸上の置き場所が無く（仕様書 §6.2.1、v4.27）、そこへ向かう線を引くと**意味の無い位置へ引いた線**になる。回送はヒゲとして端点に残っており、車庫へ帰ったことは絵から読める。

営業所待機のあいだの繋がりは、**運用の色**が示している。それ以上を絵に足さない。

### 5.4 回送スジの見え方（#179）

**回送だけが例外扱いになっていたところを、他のパターンと揃える。**

#### 5.4.1 色と線種を設定から選べるようにする（2026-08-05 改め）

v1.0 の §6.5.3 は、パターンの色と線種の上書きから**回送を外していた**。

> **回送の線種は選べない**（回送かどうかはパターンの好みではない）

**この理由は誤りだった。** 回送が回送であることは `isDeadhead` が決めているが、**その線をどう見分けたいかはその人の目の話**であり、営業パターンと変わらない。停留所の線種（v4.35）とパターンの色（v4.40）を上書きできるようにしたのと、同じ理屈である。

| 決め | 理由 |
| --- | --- |
| 上書きの対象を**全パターン**に広げる | 色も線種も選べる。既定は `route.json` のまま（回送は破線、営業は種別から決まる） |
| **補いたいのは着色モードの副作用である** | 運用で着色すると回送は元の便と同じ色になり（§6.2.4）、**太さの違いだけが手掛かりになる。** そこを利用者が補えるようにする |
| 設定ダイアログの一覧に**回送も並べる** | 「（回送）」の注記は残す。並べないと、選べることが分からない |
| **サイドパネルの凡例には並べない**（変えない） | v4.21 の決めをそのまま引く。あちらはパターンごとの表示・非表示を切る場所であり、回送は `showDeadhead` の 1 つで切る |
| `route.json` は書き換わらない | 上書きは設定に持つ（§6.5.3）。同じファイルを渡した相手の画面が、こちらの好みで変わることもない |

#### 5.4.2 ヒゲの長さを倍にする

回送スジは営業便の端から一定の px だけ伸ばして打ち切る「ヒゲ」である（v4.27、#118）。**15px から 30px に改める。**

出入区の有無を絵から読み取るための記号でありながら、**停車点の丸（半径 3.5px）や選択のつまみ（7px）と同じ桁では、線が少し飛び出しただけに見えていた。**

| 決め | 理由 |
| --- | --- |
| 長さは **30px** | 記号として読める大きさにする。隣の停留所線までの隔たり（既定の拡大率で 120px）には十分収まり、**停留所線を横切らない**という条件は保たれる |
| **px で持つ**（変えない） | 線幅や点の半径と同じ絵の記号の大きさであって、距離でも時間でもない。軸の単位で持つと、縦に拡げるたびにヒゲが伸びる |
| **端の余白を 32px に広げる** | ヒゲは下へしか伸びない。余白がヒゲより短いと、**一番下まで送ったときに先が描画領域の外に出る**（[§5.3.3](#533-同じ停留所で複数の運用が留まるとき2026-08-04) の接続線と同じ場所を取り合う） |

**余白の幅は「そこに何が積まれるか」で決まる**（§5.3.3、#171）。端の外側に出るものを数え、最も遠いものに合わせる。

| 積まれるもの | はみ出し |
| --- | --- |
| 選択のつまみ・停車点の丸 | 3.5px |
| 折返しの接続線（7px × 3 段） | 21px |
| **回送のヒゲ** | **30px** |

**上下で違う値にはしない。** ヒゲは下へしか伸びず接続線は両方へ積まれるが、**余白を上下で違えると送りの範囲の引き算が 2 通りになる**——1 つの値で足りるなら 1 つにする。

## 6. 新しく計算する

**この節の 3 件（#161・#162・#166）は互いに依存する。** 距離も輸送力も「どの範囲を数えるか」を必要とし、それがフォーカス範囲である。**計算の置き場所を先に決め、そこへ 2 つの数を載せる。**

### 6.1 区間距離（#161）

**対応する本体の節: [§5.2](specification.md)（区間所要時間）・[§6.5.1](specification.md)（区間所要時間タブ）**

#### 6.1.1 距離は区間が持つ

**所要時間と同じ理由で、距離も区間が持つ。** 仕様書 §5.2 の議論はそのまま距離にも当てはまる——停留所が持つ設計では「次まで何 km」と書けず、停車パターンが持つ設計では同じ区間の距離が重複する。

```typescript
interface Segment {
  fromStopId: string;
  toStopId: string;
  runMinutes: number;          // 5 の倍数
  distanceMeters: number;      // 0 以上の整数。**メートルで持つ**
}
```

| 決め | 理由 |
| --- | --- |
| **メートルの整数で持つ** | km の小数で持つと、足し合わせるたびに丸め誤差が乗る。10 区間を足して `12.299999999999999 km` と出るのは、ダイヤの検討に使う数として信用されない |
| **画面には km で小数第 1 位まで出す** | 100m 単位。バスの走行距離を語る粒度である。`12.3 km` |
| **5 の倍数のような刻みは設けない** | 所要時間が 5 分刻みなのは、ダイヤ全体が 5 分刻みだからである（仕様書 §2.1）。距離にその制約は無く、実測値を丸める理由も無い |
| 有向である | 所要時間と同じく、往復で距離が違う可能性を排除しない（一方通行を通る経路がある） |
| **回送区間も距離を持つ** | 運用の走行距離には回送も含まれる。距離を持たない区間を作ると、そこを通る運用だけ計算できなくなる |

#### 6.1.2 導出される値

```
便の距離        = Σ（その便が通る区間の distanceMeters）
運用の走行距離  = Σ（その運用の便の距離）。**回送便を含む**
```

| 値 | 数え方 |
| --- | --- |
| 便の距離 | 停車パターンの停留所列に沿って区間表を引き、累積する（累積所要時間と同じ道筋。仕様書 §5.2） |
| **走行距離** | 回送便を展開したうえで（仕様書 §6.1.7）足す。**回送を含む** |
| **営業距離** | 営業便だけを足す。**回送を含まない** |

**回送込みと回送抜きの 2 つを並べて出す**（2026-08-04 決定、Q-11）。片方だけでは答えられない問いがそれぞれにある——**車がその日に何 km 走ったか**（燃料・車両の傷み）は回送を含み、**客をどれだけ運ぶために走ったか**（1 便あたりの効率）は含まない。導出はどちらも同じ和であり、足す対象が違うだけである。

**「営業キロ」とは呼ばない。** 営業キロは運賃計算のための擬制キロを指す語であり、本ソフトに運賃の概念は無い。ここで出すのは**実際に走る距離**である。

**どれも永続化しない。** 区間表と便から毎回導ける値であり、保存すると区間表を直したときに古い値が残る（仕様書 §5.8 と同じ方針）。

#### 6.1.3 設定ダイアログ

**「区間所要時間タブ」を「区間タブ」に改める。** 所要時間と距離を同じ表に並べる。

```
 区間                                    所要時間      距離
 ──────────────────────────────────────────────────────────
 豊中学舎          →  箕面学舎            [20] 分   [ 5.4] km
 箕面学舎          →  豊中学舎            [20] 分   [ 5.4] km
 豊中学舎          →  コンベ前            [25] 分   [ 7.1] km
 ...
```

| 決め | 理由 |
| --- | --- |
| **同じ表に並べる** | 区間は 15 件しかない。タブを分けると、同じ区間を直すのに 2 か所を行き来する |
| 打った値は**適用するまで状態に触れない** | 仕様書 §6.5.1 の決めをそのまま引く |
| **距離を変えても便の時刻は動かない** | 時刻を決めるのは所要時間だけである。適用前に出す「何便に効くか」は所要時間を変えたときだけ出す |
| 書き戻し先は `route.json` | 所要時間と同じ。Web 版ではダウンロード（仕様書 §6.5.5） |

#### 6.1.4 距離が入っていない `route.json`

**版数 1 の `route.json` には距離が無い。** 版数を 2 に上げる（[§8.1](#81-routejson-版数-2)）。

| 決め | 理由 |
| --- | --- |
| 版数 1 を読んだら、距離を **`null`（未設定）** として扱う | `0` に倒すと「距離 0 の区間」と見分けが付かず、**合計が静かに小さく出る** |
| 未設定の区間を含む計算結果は **`—`** と出す | 数を出さない。「一部が抜けた合計」は、抜けていることに気づかないまま読まれる |
| どの区間が未設定かを**区間タブに出す** | 直せる場所へ案内する。計算パネルに「距離が未設定の区間があります」とだけ出しても、どこを直せばよいか分からない |
| ネットワーク定義の検証に **R-13** を足す | 「すべての区間が `distanceMeters` を持つ」。版数 2 を名乗る `route.json` にのみ適用する（[§9](#9-検証項目の追加)） |

### 6.2 輸送能力（#162）

**対応する本体の節: [§5.8](specification.md)（運用の導出）**

#### 6.2.1 定員は停車パターンが持つ（2026-08-04 改め）

**乗車可能人員は系統によって異なる。** issue は「各運用に対して」と書いているが、実際に定員を決めているのは**その便がどの系統を走るか**である。系統ごとに入る車両の型式が違う。

**定員は停車パターン（`patternId`）に紐づける。**

| 検討した置き場所 | 採否 |
| --- | --- |
| **運用（`blockId`）** | **採らない。** 運用番号はその文書の中だけの名前であり（仕様書 §5.8）、`A` の定員という概念が文書をまたいで意味を持たない |
| 路線名（`routeName`） | **採らない。** 複数のパターンが文字列の一致で共有しているだけで、ID を持たない。**路線名を直した瞬間に定員が迷子になる** |
| **停車パターン（`patternId`）** | **採る。** `route.json` の安定した ID であり、系統と 1 対 1 で対応する |

**置き場所はプロジェクト（`.uodia`）である。`route.json` は変えない。**

```typescript
// Project（トップレベル）
/** 停車パターンごとの定員。**上書きしたものだけを入れる。** */
patternCapacities: Record<string, number>;
```

| 決め | 理由 |
| --- | --- |
| **`route.json` に定員を置かない** | `defaultCapacity` の追加を取り下げる。`route.json` を版数 2 に上げる理由は**距離だけ**になる |
| **プロジェクトに置く** | `.uodia` はデスクトップ版でも Web 版でも書ける。**`route.json` を書き戻せない Web 版でも定員を変えられる**（仕様書 §6.5.5 の制約を回避する）。issue が「どの版であっても変更できるようにしたい」と求めているのはこれである |
| **設定（`settings.json`）には置かない** | 輸送力は計算結果として人に見せる数である。設定に置くと、**同じファイルを開いた相手が違う数を見る。** 運用の色をプロジェクトに置いた理由（仕様書 §5.8）と同じである |
| **上書きしたパターンだけを持つ** | 疎に持つ。`route.json` にパターンが増えても、既定で数えられる |
| 未設定のパターンは**アプリ内の既定値 72 人**で数える | 白紙のプロジェクトでも輸送力が出る。既定値は計算の出発点であって、路線の事実ではない。**72 は暫定値であり、そうと分かるようコメントに残す**（2026-08-04、Q-7）——暫定であることが読めないと、実測値と区別が付かなくなる |
| 立ち席を分けない | 定員は 1 つの数とし、着席定員・立席定員を分けない。**分けると、輸送力をどちらで数えるかを毎回決めることになる** |
| **回送パターンには定員を持たせない** | 客を乗せない。一覧にも並べない（サイドパネルが回送パターンを並べないのと同じ。仕様書 v4.21） |

**帰結: 同じ車が便によって違う定員になり得る。** 運用は方向も系統もまたぐため、1 つの運用の中で定員が変わる場合がある。**これは受け入れる**——本ソフトに車両エンティティは無く（仕様書 §1.2）、「同じ車である」ことを表すのは運用番号だけである。系統で定員が違うという事実のほうを優先する。

#### 6.2.2 何を計算するか

**「何人輸送できるか」には 2 つの読み方があり、両方出す。**

| 値 | 定義 | 何のための数か |
| --- | --- | --- |
| **延べ輸送力** | Σ（営業便の定員）。運用ごと・全体 | 1 日で何人ぶんの席を出したか |
| **断面輸送力** | ある区間を、ある時間範囲・ある方向に通る営業便の定員の合計 | **その区間のその時間帯に何人運べるか** |

**断面輸送力のほうが検討に使える。** 「豊中学舎 → コンベ前 を 8:30〜9:30 に何人運べるか」が答えられる。issue #166 のフォーカス範囲は、まさにこの「ある時間範囲」を指定するためのものである。

| 決め | 理由 |
| --- | --- |
| **回送便は数えない** | 客を乗せていない。距離（[§6.1.2](#612-導出される値)）が回送を数えるのとは逆であり、**理由も逆である**——走った距離は事実だが、運べた人数ではない |
| **運用番号が空欄の便は数えない** | 定員が決まらない。数えないことと、数えなかった件数を出すことをセットにする（`3 便が運用未割当のため数えていません`） |
| 断面は**区間ごと**に出す | 便によって始発停留所が違うため（豊中発・箕面発・工学部発）、路線全体で 1 つの数にすると意味を失う。V-06 が便間隔を停留所ごとに測る（仕様書 §6.6）のと同じ理由 |
| **時間範囲に入るかは「その区間を通る時刻」で判定する** | 便の始発時刻で判定すると、8:55 発の便が 9:20 に通る区間の輸送力に数えられない |

### 6.3 `route.json` の差し替え（#162）

**対応する本体の節: [§10.4](specification.md)（プラットフォーム抽象化）**

issue は「変更できる方がいい気がするので、`route.json` を外部読み込み可能にした方がいいかもしれない」と書いている。

> **v1.1 では実装しない**（2026-08-04 決定）。
>
> この節の動機は「定員をどの版でも変えられるようにする」ことだけだった。定員をプロジェクトに置くことにしたため（[§6.2.1](#621-定員は停車パターンが持つ2026-08-04-改め)）、**`route.json` を差し替えられなくても目的が達せられる。** 目的の消えた手段は作らない。
>
> **§6.3.1〜§6.3.2 は記録として残す。** 現状を調べた結果には、差し替えを実装するかどうかと無関係に効く事実が 2 つある——**デスクトップ版が既に差し替え可能であること**と、**Web 版に到達し得ないコードがあること**である。§6.3.3〜§6.3.4（実装の決め）は、必要になった時点で読み直す。

#### 6.3.1 今どうなっているか

**読む口は 1 つ、`PlatformAdapter.loadNetworkDef(): Promise<string>` である**（[src/platform/types.ts:85](src/platform/types.ts#L85)）。ドメイン層は I/O を持たず、`loadNetworkDef(json: string)`（[src/domain/network/load.ts](src/domain/network/load.ts)）は文字列を受け取るだけである。**どこから来た文字列かをドメインは知らない。**

その文字列をどこから取るかが、プラットフォームごとに違う。

| 版 | 実際の取得元 | 差し替えられるか |
| --- | --- | --- |
| **デスクトップ** | **設定ディレクトリの `route.json`**（同梱物ではない） | **できる。ファイルを置き換えるだけ** |
| **Web** | ビルドに焼き込まれた `data/route.json` | **できない**（後述の穴を除く） |

**デスクトップ版は既に外から差し替えられる。**

1. 同梱リソースとして `data/route.json` が入る（[src-tauri/tauri.conf.json](src-tauri/tauri.conf.json) の `bundle.resources`）
2. **初回起動時に設定ディレクトリへ複製する**（[src-tauri/src/paths.rs](src-tauri/src/paths.rs) の `ensure_route_file` / `seed_if_absent`）
3. 以後、読むのも書くのも**設定ディレクトリの側**である（[src-tauri/src/commands.rs:61](src-tauri/src/commands.rs#L61) `read_route_def`）
4. **既にあるものは上書きしない。** アプリを更新しても利用者の編集は残る（`seed_if_absent`）

複製する理由は、インストール先が書き込み不可のことがあるためである（Windows の Program Files、macOS のアプリバンドル）。**その副作用として、設定ディレクトリの `route.json` を差し替えれば任意の定義を読ませられる状態になっている。**

**Web 版は焼き込みである。** [src/platform/web/browser.ts:150](src/platform/web/browser.ts#L150) が `import('../../../data/route.json?url')` でビルド時アセットの URL を取り、`fetch` で読む。`public/` へ置く方式を採らなかったため（`data/route.json` を唯一の置き場所に保つため）、**配布物の中の `route.json` はハッシュ付きの名前になり、手で置き換えられない。**

#### 6.3.2 Web 版の「編集分」は保存されていない

**[src/platform/web/adapter.ts:141](src/platform/web/adapter.ts#L141) は IndexedDB の `networkDef` を読むが、この鍵を書く場所がどこにも無い。**

```typescript
// 編集分があればそれを使う。無ければ同梱のものを読む。
const edited = await store.get<string>(NETWORK_DEF_KEY);
return edited ?? (await environment.loadBundledNetworkDef());
```

`saveNetworkDef` は**必ず失敗する**よう書かれており（[adapter.ts:145](src/platform/web/adapter.ts#L145)）、`settingsService` はそれを避けて `saveProjectAs` へ回してダウンロードさせる（[settingsService.ts:124](src/features/settings/settingsService.ts#L124)）。`networkDef` を書いているのは[テスト](src/platform/web/adapter.test.ts)だけである。

| 帰結 | 内容 |
| --- | --- |
| 動作としては仕様どおり | 仕様書 §6.5.5 は「編集内容はセッション中のみ有効」と定めている。**再読込で同梱の定義に戻るのは正しい** |
| **コードは仕様より 1 歩先を書いている** | 読む側だけが「保存された編集分」を前提にしている。**書く側が現れないかぎり、この分岐は永遠に `null` を返す** |
| §6.3.3 で書く側が現れる | 外から読み込んだ定義を IndexedDB に置けば、この分岐がそのまま生きる。**新しく作るのは書く側だけである** |

#### 6.3.3 決め: 読み込みと書き出しを対にする

| 操作 | 場所 | 内容 |
| --- | --- | --- |
| **路線定義を読み込む** | ファイルメニュー | `route.json` を選んで読ませる |
| **路線定義を書き出す** | ファイルメニュー | 今の路線定義をファイルとして出す |

**足すのは口 1 つである。**

```typescript
// PlatformAdapter に足す
/** 外から読ませた路線定義を、次回以降も使うよう置く。 */
storeNetworkDef(content: string): Promise<void>;
/** 置いたものを捨て、同梱のものに戻す。 */
clearStoredNetworkDef(): Promise<void>;
```

| 版 | `storeNetworkDef` の実装 |
| --- | --- |
| デスクトップ | 設定ディレクトリの `route.json` へ書く。**既にある `write_route_def` がそのまま使える**（[commands.rs:68](src-tauri/src/commands.rs#L68)） |
| Web | IndexedDB の `networkDef` へ置く。**[§6.3.2](#632-web-版の編集分は保存されていない) の読む側がそのまま生きる** |

| 決め | 理由 |
| --- | --- |
| **読み込んだ定義は同梱のものを置き換えない** | 同梱の `route.json` は常に残す。**壊れた定義を読ませたときに戻る先が要る**。デスクトップ版の `seed_if_absent` が既にこの形である |
| 読み込んだ定義の置き場所は**プラットフォームごと**に決める | デスクトップ版は設定ディレクトリ、Web 版は IndexedDB。既存の `PlatformAdapter` の背後に隠す（仕様書 §10.4） |
| **`networkDefWritable` は「書き戻せるか」のままにする** | Web 版はこれを `false` としており、設定ダイアログからの書き戻しをダウンロードへ倒している（仕様書 §6.5.5）。**外から読ませた定義を置くことは、書き戻すこととは別である**——後者は「元の場所へ返す」であり、前者は「手元に覚える」である |
| **プロジェクトには保存しない** | `.uodia` が持つのは `meta.routeVersion` だけである（仕様書 §5.10）。路線定義を丸ごと抱き込むと、ファイルを渡すたびに相手の路線定義が置き換わる |
| **読む前に検証する**（仕様書 §5.5.2 の R-01〜R-13） | 違反があれば読み込まない。壊れた定義で起動できなくなるのは、失うものに対して代償が大きい（仕様書 §6.5.3 の設定と同じ方針） |
| 読み込んだ定義を使っていることを**画面に出す** | ステータスバーに印を出す。**同梱のものと思って使い続けるのが最も悪い** |
| 「同梱のものに戻す」を用意する | 読み込んだものを捨てる道。これが無いと、一度読ませたら戻れない |

#### 6.3.4 開いているプロジェクトとの関係

**路線定義を差し替えると、開いているプロジェクトの時刻は引き直される。** アンカーは動かないため、各便の基準停留所の時刻は変わらない（仕様書 §7.3 の `routeVersion` 不一致と同じ状況）。

| 決め | 理由 |
| --- | --- |
| **差し替えの前に未保存を確かめる** | 開いているプロジェクトが未保存なら、[§3.3](#33-未保存の変更を尋ねる文言168) の問いを出す。**選択肢が固定されたため、呼び出し元が 1 つ増えても文言は変わらない**——本文だけを足す |
| 参照が壊れた便は**既定へ倒す**（W-02・W-03） | 読込時の警告と同じ規則を使う（仕様書 §7.4）。差し替えは「開き直し」に近い |
| **この操作は Undo できない** | 路線定義はプロジェクトの外にある。履歴に載せると、取り消しがプロジェクトの外へ及ぶ |

### 6.4 フォーカス範囲（#166）

**対応する本体の節: [§6.2.3](specification.md)（拡大縮小・スクロール）・[§6.4](specification.md)（画面レイアウト）**

**「丸 1 日全部を調べたいわけじゃない」——計算する時間の範囲を指定する。**

#### 6.4.1 フォーカスは視野ではない

**最も大事な決めがこれである。**

| | 何を決めるか | 変えると何が起きるか |
| --- | --- | --- |
| **視野**（`scrollTime` / `pxPerMinute`） | 画面のどこを見ているか | 絵が動く。**数は変わらない** |
| **フォーカス範囲**（新設） | どこを数えるか | **数が変わる。** 絵は動かない |

**別のものとして持つ。** 視野に連動させると、拡大しただけで輸送力の数が変わる。**画面を送るたびに数が動く表は読めない。**

| 決め | 理由 |
| --- | --- |
| フォーカス範囲は**始まりと終わりの時刻**（5 分刻み） | 時刻の刻みは仕様書 §2.1 に従う。範囲の指定だけ別の刻みにする理由が無い |
| 既定は **無効**（1 日全部） | 何も指定していない状態で数が絞られていると、合計が合わない理由を探すことになる |
| **有効にしているあいだ、範囲の外を薄く落とす** | ダイヤグラムで範囲の外のスジを薄く描く。**どこを数えているかが絵から読める**必要がある。数だけが変わって絵が同じでは、絞ったことを忘れる |
| 範囲の外の便を**隠さない** | 表示フィルタ（仕様書 §6.2.4）とは別物である。隠すと、範囲の境目をまたぐ便の繋がりが読めなくなる |
| **編集には一切影響しない** | 範囲の外の便も、今までどおり選べる・動かせる・消せる。フォーカスは**数えるための範囲**であって、触れる範囲ではない |
| **検証にも影響しない** | 範囲の外のエラーが消えては、絞っているあいだに壊したことに気づけない |
| 24 時をまたぐ範囲を許す | 時刻は 24 時を超える（仕様書 §2.1）。`22:00〜25:00` と書ける |

#### 6.4.2 便が範囲を跨ぐとき

**按分しない。**

| 数 | 数え方 |
| --- | --- |
| 距離 | **その区間を通る時刻が範囲に入る区間だけ**を足す。便を途中で切る |
| 断面輸送力 | **その区間を通る時刻が範囲に入る便**の定員を足す。定員は切らない |

| 決め | 理由 |
| --- | --- |
| 距離は**区間単位で切る** | 区間の途中で切ると、その区間の何割を走ったかを時刻から按分することになる。**バスが等速で走っている前提を持ち込むことになり、持ち込む理由が無い** |
| 定員は**切らない** | 定員を按分すると `37.5 人` が出る。人は割れない |
| 判定は**その区間を通る時刻**で行う | 便の始発時刻でも終着時刻でもない。[§6.2.2](#622-何を計算するか) の断面の考え方と揃える |

#### 6.4.3 置き場所と保存

```typescript
// ViewSettings に足す
focus: {
  enabled: boolean;      // 既定 false
  from: number;          // 秒。既定 7:00
  to: number;            // 秒。既定 22:00
}
```

| 決め | 理由 |
| --- | --- |
| **プロジェクトに保存する** | 開き直したときに同じ範囲を見たい。視野（`diagram`）が保存されるのと同じ |
| **履歴に載せない・未保存にもしない** | 視野と同じ扱い（仕様書 §6.2.3）。**どこを数えているかは編集ではない。** 範囲を動かしただけで閉じるたびに保存を尋ねられるのは誤りである |
| `view` に置く | 何を計画したかではなく、どこを見ているかである。定員（[§6.2.1](#621-定員は停車パターンが持つ2026-08-04-改め)）をプロジェクト直下に置くのとは逆であり、**理由も逆である** |

### 6.5 計算パネル

**対応する本体の節: [§6.4](specification.md)（画面レイアウト）**

**距離も輸送力も、出す場所が要る。**

| 決め | 理由 |
| --- | --- |
| **サイドパネルに節を足す** | 検証パネル（下）は指摘の一覧であり、数を並べる場所ではない。運用の一覧が既にサイドパネルにあり、運用ごとの数はその隣に出るのが素直である |
| 運用の一覧に**走行距離を出す** | 既に `120 便` を出している行の隣。**行を増やさずに済む** |
| 断面輸送力は**別の節**に出す | 区間 × 方向の表になり、運用の一覧には収まらない |
| フォーカス範囲の指定も**この節に置く** | 数を出す場所と、範囲を決める場所を離さない。**離すと、絞ったことを忘れたまま数を読む** |
| **区間の距離が未設定なら数を出さない**（`—`） | [§6.1.4](#614-距離が入っていない-routejson) の決めをそのまま引く |
| **数えなかった便の件数を必ず出す** | 運用番号が空欄・時刻が未入力の便は数に入らない。**合計だけを出すと、抜けていることに気づかないまま読まれる** |

## 7. GTFS 書き出し（#163）

**対応する本体の節: [§5.9](specification.md)（GTFS との対応）・[§11](specification.md)（将来計画）**

**issue が「要件はまた後で決める」と書いているとおり、本節は枠だけである。**

### 7.1 既に決まっていること

データモデルは v1.0 の時点で GTFS に準拠している（仕様書 §5.9）。**構造変換を要さないことを設計目標として作ってある。**

| 決まっていること | 出典 |
| --- | --- |
| どのフィールドがどの GTFS 項目に対応するか | 仕様書 §5.9 の表 |
| 回送便は出力しない | 仕様書 §5.9（回送は公共サービスではない。そもそも保存されていない） |
| `Stop.isDepot: true` は `stops.txt` に出さない | 仕様書 §5.9 |
| `Stop.hiddenInEditor: true` は**出す** | 仕様書 §5.9（微生物研究所前は実際の運行経路上の停留所） |
| `Handling` が `pickup_type` / `drop_off_type` になる | 仕様書 §5.4 |

### 7.2 足りないもの

| 不足 | 埋め方 |
| --- | --- |
| `agency.txt` の全項目 | `route.json` に静的データとして足す。モデル変更を伴わない |
| `stops.txt` の `stop_lat` / `stop_lon` | 同上。`Stop` に 2 項目足す |
| `calendar.txt` の運行日情報 | **`Service` が運行日を持っていない。** 名前（`授業期間平日ダイヤ`）しか無く、どの曜日に走るかがデータに無い |

**`calendar.txt` が最も重い。** 運行日カレンダーは仕様書 §11 で v2 の別項目として挙がっており、GTFS 出力とは独立に決める必要がある。

### 7.3 決めなければならないこと

**issue は「すでに別で使用している形式があるのでそれに合わせる部分は合わせる。合わせない部分については合わせない」と書いている。**

**その「別で使用している形式」が何を指すのかが分からないかぎり、本節は書けない。** 以下を確かめてから起草する。

| 問い | なぜ要るか |
| --- | --- |
| **既存の GTFS はどこにあるか** | 実物を見ないと「合わせる部分」が決まらない |
| `agency_id` / `route_id` / `stop_id` の採番規則 | 既存と揃えないと、同じ停留所が別 ID で 2 つ現れる |
| `stop_id` は既存のものと一致するか | `route.json` の `1_0` `2_0` が既存の ID なのか、本ソフトで付けた ID なのか |
| **合わせないと決めた部分は何か** | issue が「合わせない部分については合わせない」と書いている以上、既に判断がある |
| 出力の単位 | zip 1 つか、`.txt` の集まりか |
| 運行日をどう埋めるか | `calendar.txt` を出すのか、`calendar_dates.txt` だけで済ませるのか |

### 7.4 本書での扱い（2026-08-04 決定）

**GTFS 書き出しを v1.1 に含めない。** 要件が決まっていない機能を、決まっている 10 件と同じリリースに載せると、10 件が待たされる。

**§7.3 の問いに答えが出た時点で、独立した仕様書（`docs/specification-gtfs.md`）を起こす。** 本書に書き足さない理由は次のとおり。

| 理由 | 説明 |
| --- | --- |
| **入出力の形式そのものが仕様である** | GTFS 出力は「どのファイルにどの列をどう並べるか」が中身であり、本書のような「既存の決めをどう改めるか」の追補には収まらない |
| **既存形式との突き合わせが要る** | 合わせる部分と合わせない部分を 1 項目ずつ書き下すことになる。分量が本書の残り全部を超える |
| **リリースの単位が違う** | v1.1 の 10 件はどれも数日で入る。GTFS は要件確定から数えて別の期間になる |

**本節（§7.1〜§7.3）は残す。** 「何が既に決まっていて、何を確かめる必要があるか」は、仕様書を起こす前に要る。起こした時点で §7 はその文書への案内に置き換える。

### 9.1 ネットワーク定義の検証（R-xx）

### 9.2 ダイヤ検証（V-xx）

**項目は追加しない。** ただし[§5.2.3](#523-2-便が絡む指摘は双方に付ける) により、**既存の V-01・V-02・V-03・V-06 は 1 つの事象につき 2 件を出すようになる。**

| 検討したが足さないもの | 理由 |
| --- | --- |
| 「定員を超える便がある」 | **需要データを持っていない**（仕様書 §11「需要データの重畳表示: 予定なし」）。何人乗るかを知らないのだから、超えているかは判定できない |
| 「距離が未設定の区間を通る便がある」 | 便の問題ではなく路線定義の問題である。R-13 が既に指摘しており、**同じことを 2 か所で言わない** |
| 「運用の走行距離が長すぎる」 | 閾値を決める根拠が無い。**根拠の無い閾値は、警告が出るたびに閾値のほうを疑われる** |
| 「1 つの運用の中で定員が変わる」 | 系統ごとに車両の型式が違うことの帰結であり（[§6.2.1](#621-定員は停車パターンが持つ2026-08-04-改め)）、異常ではない |

### 9.3 重大度の見直し（Q-14）

**見直した結果、変えない**（2026-08-04 決定）。

[§5.2.3](#523-2-便が絡む指摘は双方に付ける) の 2 件出しにより、エラーの件数と時刻表の塗り面積は倍になる。それでも**重大度をそのまま塗る条件として使う**。

| 決め | 理由 |
| --- | --- |
| **重大度は下げない** | V-01〜V-04 はいずれも仕様書 §6.6 の `error` の定義（「ダイヤとして成立していない。実運行できない」）に当てはまる。**当てはまるものを見た目の都合で下げると、重大度が「どれくらい目立たせたいか」の指標に変わる** |
| **塗る条件を重大度から切り離さない** | 「V-01〜V-03 は塗るが V-04 は塗らない」という表を持つと、**項目が増えるたびにその表を更新しなければならない。** 更新を忘れた項目は黙って塗られなくなり、それに気づく手立てが無い |
| 塗るのは**エラーだけ**（[§5.2.2](#522-決め-列見出しに印を付ける) のまま） | 警告・情報は記号だけ出す。ここは変えない |
| **V-03 も両側から出す**（Q-15） | V-01・V-02 と揃える。V-03 が大量に出る状態はダイヤが壊れているのであり、**そのとき件数が多いのは正しい** |

**塗り面積が問題になったら、そのときに測って決める。** いま予防的に仕組みを足すと、使われないかもしれない分岐を先に抱えることになる。重大度と塗る条件が同じものを指しているかぎり、**決める場所は 1 つで済む。**

## 12. ライセンス（2026-08-04 方針決定）

**再配布を禁止する**（v1.0 仕様書 Q-2 への回答）。

LICENSE が無い状態は、既定で「All rights reserved」である。**方針としては現状と同じ結果になる。** それでも文書として置くのは、**黙っているのと、意図してそう決めたと示すのとは違う**からである。無いままだと、決め忘れたのか決めた結果なのかが読む側に分からない。

| 決め | 内容 |
| --- | --- |

| 著作権者 | 再履バス同好会（[§3.1](#31-コピーライトの表記158)） |

### 12.2 決まっていないこと（Q-16）

**本文の起草が残る。** あわせて、本文を書く前に次の 2 点を確かめること。

| 論点 | 内容 |
| --- | --- |
| **公開リポジトリであることとの兼ね合い** | GitHub の利用規約は、**公開リポジトリを置いた時点で、他の利用者に閲覧とフォークを認めたものとみなす**（Terms of Service, D.5）。**利用規約が先に認めているものを、後から LICENSE で禁じることはできない。** 本文でフォークをどう扱うかを決めるか、リポジトリを非公開にするかのいずれかが要る |
| **依存パッケージの表示義務** | React・Zustand・Zod・Tauri はいずれも MIT / Apache-2.0 であり、**配布物に著作権表示を同梱する義務がある。** 自分のソフトを再配布禁止にすることと、依存の表示義務を果たすことは両立する（前者は自分の権利、後者は他人への義務）。デスクトップ版の配布物と Web 版の `dist` の両方に、依存の一覧が要る |

**どちらも法的な判断を含む。** 本書は論点を挙げるところまでとし、本文は起草しない。

### B.4 微研 → 工学部を 0.0 km と置いたこと

**唯一の置いた値である。** 提出されたのは「コンベ前 → 工学部 1.3 km」であり、これは #3（コンベ前 → 微研）と #4（微研 → 工学部）の合計である。2 つへの割り方は与えられていない。

**#4 を 0.0 km とした。** 根拠は 2 つあり、どちらも同じ答えを出す。

| 根拠 | 説明 |
| --- | --- |
| 所要時間が 0 分である | 微研と工学部は軸位置がどちらも 40 であり、ダイヤグラム上でも同じ高さに描かれる。時間で按分すれば 1.3 : 0.0 になる |
| **どの計算にも現れない** | 吹田方面の停車パターンは**すべて微研を含む**（`S1` = 豊中→コンベ前→微研→工学部、`S3` = 豊中→箕面→コンベ前→微研→工学部）。区間表にコンベ前→工学部を直接結ぶ区間は無く、**微研を飛ばす経路が存在しない。** #3 と #4 の割り方は、どの便の距離にも運用の走行距離にも影響しない |

**影響するのは区間タブの表示だけである。** 実測が判明したら、#3 と #4 の合計を 1.3 km に保ったまま割り直せばよい——**そのとき他の 13 区間は動かない。**

### B.5 単位と反映

`route.json` にはメートルの整数で書く（[§6.1.1](#611-距離は区間が持つ)）。`8.5 km` → `8500`。

**まだ `data/route.json` には書き込んでいない。** 書き込むと `meta.routeVersion` が 2 になり、既存のプロジェクトを開くたびに W-01 の警告が出る。スキーマ（`networkDefSchema`）が `distanceMeters` を受け付けるようになり、R-13 が実装された後に、[§6.1](#61-区間距離161) の実装とまとめて入れる。
